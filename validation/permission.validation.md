# Permission Contract — Validation Rules (VAL-157 – VAL-168)

Governs: [`permission.contract.md`](../contracts/permission.contract.md) · Schemas: [`permission.schema.yaml`](../schemas/permission.schema.yaml), [`permission.schema.json`](../schemas/permission.schema.json)

| ID      | Rule                                                                                                                                                                                                       | Severity | Governing Source                        |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------- |
| VAL-157 | `id`, `role`, `action`, `resource`, `tenant`, `granted_by`, `effective_from`, `break_glass`, `state` MUST all be present; a Permission Grant missing any required field is unresolvable and unpublishable. | Blocking | Schema constraint                       |
| VAL-158 | `action` MUST be exactly one of `C`, `R`, `U`, `A`, `X` per the DDD §24 legend.                                                                                                                            | Blocking | DDD §24                                 |
| VAL-159 | `resource` MUST match `^[a-z][a-z0-9_]*$` (snake_case Capability/Aggregate slug).                                                                                                                          | Blocking | Schema constraint                       |
| VAL-160 | `role` in `{ceo_ai, coo_ai}` MUST NOT hold `action = A` on `quotation`, `spk`, `delivery`, `appointment`, or `test_drive`.                                                                                 | Blocking | Permission Contract §4                  |
| VAL-161 | Absence of an explicit `active` grant for a (`role`,`action`,`resource`,`tenant`) tuple MUST be treated as denied by every consumer; no consumer may default-allow.                                        | Blocking | Constitution §20.4                      |
| VAL-162 | An `action = X` grant MUST take precedence over any co-existing broader allow grant for the identical tuple.                                                                                               | Blocking | DDD §24 Notes                           |
| VAL-163 | Every `permission_scope` token declared in a Tool Contract instance MUST resolve to at least one `active` Permission Grant.                                                                                | Blocking | Permission Contract §4                  |
| VAL-164 | `action = A` grants for `role = sales_staff` MUST carry `condition.scope = own_records_only` unless the DDD §24 row lists the resource without an "(own)" qualifier.                                       | Blocking | DDD §24 Notes                           |
| VAL-165 | If `break_glass = true`, `effective_until` and `audit_ref` MUST both be non-null.                                                                                                                          | Blocking | Constitution RULE-066                   |
| VAL-166 | `tenant` MUST equal `global` or reference an existing Tenant Aggregate ID; cross-tenant grants are structurally forbidden.                                                                                 | Blocking | DDD §25                                 |
| VAL-167 | `state = revoked` grants MUST NOT be referenced as authorizing any new action; consumers MUST re-check `state` on every authorization decision, never cache indefinitely.                                  | Blocking | Constitution §20.4                      |
| VAL-168 | A grant with `effective_until` in the past but `state` still `active` is a data-integrity Warning — the Registry publish pipeline SHOULD auto-transition it to `revoked`.                                  | Warning  | Registry Contract lifecycle consistency |
