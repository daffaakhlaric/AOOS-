# Benchmark Reference — Programming Languages & Runtimes

Governs: [`docs/004-TECHNOLOGY-SELECTION-RECORD.md`](../docs/004-TECHNOLOGY-SELECTION-RECORD.md) §3.1, [`tech-stack/programming-language.md`](../tech-stack/programming-language.md)

**Note on methodology:** figures below are directional, drawn from widely-cited public benchmark sources (TechEmpower Web Framework Benchmarks, language-vendor published documentation, common industry-reported orders of magnitude) as of this writing — not AOS's own measured numbers. They inform relative positioning, not absolute capacity planning.

| Dimension                                                            | TypeScript (Node.js)                                           | Go                                          | Rust                                  | Python (asyncio)                                                  |
| -------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| Raw request throughput (simple JSON API, TechEmpower-class workload) | Medium-High                                                    | High                                        | Very High                             | Medium                                                            |
| Cold start (serverless/container)                                    | Fast                                                           | Very Fast                                   | Very Fast                             | Medium                                                            |
| Memory footprint per request-handling process                        | Medium (V8 heap overhead)                                      | Low                                         | Very Low                              | Medium-High (interpreter overhead)                                |
| Concurrency ceiling (single node, I/O-bound workload)                | High (event loop, non-blocking I/O)                            | Very High (goroutines, cheap green threads) | Very High (async runtimes e.g. Tokio) | Medium (GIL constrains CPU-bound concurrency; fine for I/O-bound) |
| GC pause characteristics                                             | Generational GC, generally low-pause for typical web workloads | Low-pause concurrent GC                     | No GC (ownership model)               | Generational GC, generally low-pause                              |

**Relevance to AOS decision (§3.1):** the Core Runtime's dominant workload is I/O-bound (LLM API calls, database queries, Tool invocations awaiting external systems), not CPU-bound compute — this favors TypeScript/Node's event-loop model and Go's goroutines roughly equally for the platform's actual bottleneck, which is why raw throughput differences did not become the deciding factor; ecosystem fit (§3.1 Final Recommendation) was. Go is reserved specifically for the narrow set of services (Event Bus consumer fan-out, API Gateway hot edge) where per-request memory footprint and tail latency at very high fan-out genuinely matter.
