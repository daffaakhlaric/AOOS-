# ADR-TSR-016 — Authentication: Keycloak (Self-Hosted)

**Status:** Accepted

**Context:** AOS requires an identity/authentication/authorization technology satisfying Constitution §20 (Security Standards) and RULE-062 (every API endpoint MUST enforce RBAC with least-privilege defaults), structurally compatible with the Tenant/Branch/User/Role model (DDD §9) and its eight-role-class Permission Matrix (DDD §24). The platform targets thousands of dealer tenants, each with roughly fifteen users (`cost-analysis/cost-model-100-1000-10000-dealers.md` §1), a shape in which per-MAU/per-tenant SaaS identity pricing (Auth0, Clerk, Supabase Auth) grows linearly with a metric — total seats — that is structurally large for AOS's business model, in tension with Constitution §33 Cost Optimization. Identity is a Generic Domain (DDD §4): AOS does not differentiate on identity UX, so operational soundness and cost control outweigh best-in-class managed convenience.

**Decision:** Adopt **Keycloak**, self-hosted on the platform's own Kubernetes infrastructure (Architecture §11 Deployment Diagram), as the identity/authentication/authorization provider for all dealer-tenant and AOS-internal identities. Use a **shared realm with per-tenant Groups** as the default multi-tenancy pattern (mirroring the RLS-default / database-per-tenant-escape-hatch pattern of Architecture ADR-012), with a dedicated realm reserved as an Enterprise-tier escape hatch for tenants requiring full identity-plane isolation or corporate IdP federation. Express the DDD §24 Permission Matrix's role classes as Keycloak Client Roles/Composite Roles, with capability-level (C/R/U/A/X) and "own"-scoped enforcement performed downstream at the API/Tool Manager layer (RULE-009, RULE-062), not inside Keycloak itself. Deploy Keycloak multi-replica with an HA-backed persistence store from the first production environment (no deferred hardening).

**Consequences:** AOS owns Keycloak's patch cycles, upgrade testing, and HA operations — a security-critical operational responsibility that a managed IDaaS would otherwise absorb (mitigated via IaC-managed realm/client configuration per Constitution RULE-086, and named explicitly in `risk/risk-register.md` RISK-007 as a High-severity risk if HA discipline is skipped). In exchange, AOS avoids a per-MAU/per-tenant cost structure that would scale unfavorably against its own dealer-tenant economics, and avoids lock-in to a proprietary vendor's Rules/Actions/Management API surface, since OIDC/OAuth2/SAML are standards every downstream service (Kong, Dashboard, Agent Runtime) integrates against rather than a vendor-specific SDK. Initial engineering setup cost is higher than a managed SDK-first competitor; amortized via a shared, documented Keycloak client library and seeded dev-realm export used across services.

**Alternatives Considered:**

- **Auth0** — superior turnkey developer experience and managed reliability SLA; rejected as the production default because its MAU-tiered/enterprise-custom pricing crosses into a disqualifying cost band well before AOS's 10,000-dealer tier (`tech-stack/authentication.md` §17), and its proprietary Rules/Actions/Management API surface raises switching cost beyond a standards-based OIDC re-point.
- **Clerk** — excellent DX and fast MVP integration, particularly for Next.js-based frontends; endorsed explicitly as an early-prototype-only option, not adopted for production due to the same per-MAU cost-at-scale reasoning plus a shorter enterprise-deployment track record than Keycloak.
- **Supabase Auth (GoTrue)** — open-core (Apache 2.0) and genuinely self-hostable in principle, but typically consumed bundled with the commercial, usage-metered Supabase platform in practice; endorsed as an early-prototype-only option for the same reasons as Clerk, not adopted for production.
