# ADR-TSR-022 — Secret Management: HashiCorp Vault

**Status:** Accepted

**Context:** The Tool Contract (doc 003.5 §3) requires per-invocation, per-Tool credential resolution via its `authentication`/`authorization` fields, and Constitution RULE-060 mandates that secrets never live in code or static configuration. AOS's multi-tenant model additionally requires fine-grained, per-tenant and per-Tool access policies (a Tool Adapter serving Tenant A must never be able to read Tenant B's third-party API credentials), and Constitution §20 (Security Standards) requires audit logging of every credential access. Candidates evaluated: HashiCorp Vault, AWS Secrets Manager, Doppler.

**Decision:** Adopt **HashiCorp Vault** (self-hosted, or HCP Vault managed) as the primary secret store for production. Vault's dynamic secrets capability (short-lived, automatically-rotated credentials rather than static long-lived tokens), its fine-grained policy engine (mappable directly onto per-tenant/per-Tool access boundaries), and its native audit-logging device most completely satisfy the Tool Contract's per-invocation resolution model and Constitution §20's least-privilege mandate. **A cloud-native Secrets Manager (e.g., AWS Secrets Manager)** is documented as an acceptable simpler default specifically for a team fully committed to a single cloud provider early on and wanting to defer Vault's operational complexity — this is a legitimate staged-adoption path, not a rejected alternative. **Doppler** is adopted for **development-environment secret distribution only** — its local-dev developer experience is genuinely superior, but production secret custody for a multi-tenant enterprise SaaS should not sit with a smaller third-party vendor by default, per the vendor-lock-in-avoidance principle stated in TSR §1.

**Consequences:** The platform takes on the operational responsibility of running (or subscribing to a managed instance of) Vault — unseal/HA/backup procedures, upgrade cadence — as a Tier-0 dependency (per the Dependency Matrix, TSR §7, nearly every other service depends on it). In exchange, credential rotation, per-tenant isolation of third-party API keys, and audit trails become structural properties of the secret store itself rather than something each service must separately implement. Doppler's dev-only scope must be enforced by policy (no production credential ever originates from or is proxied through Doppler), not merely convention.

**Alternatives Considered:**

- **AWS Secrets Manager (as sole/primary store)** — not rejected, but demoted to "acceptable simpler default" rather than the primary recommendation, because it ties the platform's secret custody to a single cloud vendor more tightly than Vault's cloud-agnostic model, in tension with the platform's multi-cloud object-storage/Kubernetes posture (TSR §3.13, §3.20).
- **Doppler (for production use)** — rejected for production secret custody; third-party vendor custody of production credentials for an enterprise multi-tenant SaaS is a materially different risk profile than its excellent dev-environment use case.
