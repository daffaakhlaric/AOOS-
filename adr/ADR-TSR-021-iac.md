# ADR-TSR-021 — Infrastructure as Code: Terraform

**Status:** Accepted

**Context:** Every infrastructure component named across this TSR (Kubernetes clusters, managed PostgreSQL/CockroachDB, Valkey, NATS JetStream, Vault, Kong, Keycloak, the Grafana LGTM stack, object storage buckets, and underlying network/VPC/IAM primitives) must be defined as code, not provisioned via manual console changes, per Constitution RULE-086 and §24.1. Architecture §32's disaster-recovery requirement additionally demands that infrastructure be deterministically rebuildable in a standby region by any qualified engineer, not only the original author — ruling out any provisioning approach that depends on undocumented manual steps or tribal knowledge. The platform's infrastructure spans more than one cloud vendor's API surface by design (Cloudflare R2 default object storage + AWS S3 fallback + potential multi-cloud Kubernetes hosting), so the chosen tool must be genuinely multi-cloud capable, not single-vendor-scoped.

**Decision:** Adopt **Terraform** (HCL-based, HashiCorp) as the binding Infrastructure-as-Code tool for all AOS infrastructure provisioning. **Pulumi** is documented as a valid, explicitly acknowledged alternative — its general-purpose-language (including TypeScript) authoring model offers a materially better developer experience for AOS's TypeScript-first engineering team — but is not adopted for v1 because Terraform's decade-longer ecosystem maturity, larger provider/module registry, and deeper, wider-available operational talent pool more directly serve Architecture §32's DR-rebuildability requirement, which this TSR weights above authoring convenience for this specific category.

**Consequences:** The team maintains infrastructure code in HCL, a second declarative configuration language distinct from the platform's primary TypeScript codebase — a real, accepted context-switching cost. In exchange, the platform gains the largest available library of pre-built, community-and-vendor-maintained provider integrations for every technology named in this TSR, and the widest available hiring pool for infrastructure engineers capable of maintaining and, if ever necessary, rebuilding the platform's infrastructure from source. Terraform's 2023 relicensing to the Business Source License (BSL 1.1) is noted as a standing, monitored consideration; **OpenTofu** (the Apache-2.0-licensed, Linux-Foundation-governed fork) is the documented, low-friction fallback if BSL terms ever become a practical concern for AOS's usage.

**Alternatives Considered:**

- **Pulumi** — rejected for v1 (not disqualified) on ecosystem/community-maturity/hiring-pool grounds relative to Terraform; explicitly flagged for revisit if Terraform/HCL friction becomes a measured productivity problem for the team.
- **AWS CloudFormation / AWS CDK** — rejected outright as single-cloud-only (AWS-scoped), incompatible with the platform's stated multi-cloud object-storage and Kubernetes-hosting posture (R2 + S3 + MinIO, §3.13; Kubernetes managed across EKS/GKE-class providers, §3.20).
- **Manual/console-driven provisioning** — rejected as a direct violation of Constitution RULE-086 and §24.1, and structurally incompatible with Architecture §32's deterministic-rebuild DR requirement.
