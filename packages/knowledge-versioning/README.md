# @aos/knowledge-versioning

The AOS Enterprise Knowledge Versioning Platform — manages the complete lifecycle of
every Knowledge Asset revision inside AOS: version lifecycle, version metadata, revision
history, branches, snapshots, lineage, merge contracts, rollback contracts, comparison
metadata, version statistics, and version audit metadata **only**. This package
implements no retrieval, no synchronization, no indexing, no search, no chunking, no
embedding, no vector search, no RAG, no AI, no LLM, no prompt engineering, no workflow
execution, no connector execution, no file parsing, no merge algorithms, and no diff
engines. See `docs/PROMPT-005.7H-KNOWLEDGE-VERSIONING.md` for the explicit scope boundary
and `docs/005.7H-KNOWLEDGE-VERSIONING-REPORT.md` for the readiness checklist handed to the
next Knowledge Policy phase.

## Public API

`KnowledgeVersioning`, `KnowledgeVersion`, `KnowledgeVersionManager`,
`KnowledgeVersionRegistry`, `KnowledgeVersionResolver`, `KnowledgeVersionValidator`,
`KnowledgeVersionPipeline`, `KnowledgeVersionMiddleware`, `KnowledgeVersionFactory`,
`KnowledgeVersionContext`, `KnowledgeVersionSession`, `KnowledgeVersionLifecycle`,
`KnowledgeVersionStateMachine`, `KnowledgeVersionEvents`, `KnowledgeVersionMetrics`,
`KnowledgeVersionHealth`, `KnowledgeVersionMonitoring`, `KnowledgeVersionStatistics`,
`KnowledgeVersionSystem` — the 18 names required by the prompt. `src/index.ts` also
re-exports the full Domain/Contracts/Errors/Validator-stage surface a caller needs to
actually build and use them, matching the curation style of
`@aos/knowledge-source-manager`/`@aos/knowledge-provider`.

## Quick example

```ts
import {
  KnowledgeVersioning,
  KnowledgeVersionEvents,
  KnowledgeVersionType,
  createKnowledgeVersionContext,
} from "@aos/knowledge-versioning";

const versioning = new KnowledgeVersioning({ events: new KnowledgeVersionEvents(publisher) });

const context = createKnowledgeVersionContext({
  versionId: "v1",
  assetId: "marketing-sop",
  tenantId: "tenant-1",
});

const metadata = versioning.factory.version.create({
  versionId: "v1",
  assetId: "marketing-sop",
  versionType: KnowledgeVersionType.MAJOR,
  versionNumber: "1.0.0",
  tenantId: "tenant-1",
});

const configuration = versioning.factory.configuration.create({ versionId: "v1" });

const version = await versioning.createVersion({ metadata, configuration, context });
// version.state === "validated" — Draft -> Created -> Validated already driven

const published = await versioning.publishVersion({ token: version.token });
// published.state === "published"
```

## Architecture

```
KnowledgeVersioning (versioning/) — the public façade, composition root
  owns StateMachine + Pipeline + Middleware + Manager + Resolver + Policy + Permission
        │
        ▼
KnowledgeVersionPipeline (pipeline/) — 8 fixed stages
  Validation → Permission → Policy → Tracing → Metrics → Lifecycle → Audit → Logging
        │
        ▼
KnowledgeVersionStateMachine — the only code allowed to mutate KnowledgeVersionInstance.state
        │
        ▼
KnowledgeVersionResolver — resolve Version/Snapshot/Branch/History/Lineage/Comparison
        │
        ▼
KnowledgeVersionRegistry (8 generic buckets) + KnowledgeVersionManager (token-keyed ledger)
        │
        ▼
KnowledgeVersionMiddleware — version.use() extensibility, separate from the Pipeline
        │
        ▼
contracts/ — 10 interface-only extension points, zero implementations
```

`KnowledgeVersioning` implements each of the 11 Version Operations
(CreateVersion/PublishVersion/ArchiveVersion/RestoreVersion/RollbackVersion/
MergeVersion/CompareVersion/CloneVersion/ForkVersion/SnapshotVersion/DestroyVersion) as:
validate → drive the State Machine to the correct target state via one atomic Pipeline
call → record the relevant domain metadata (history entry, lineage edge,
branch/snapshot/merge/comparison record as applicable) → update statistics → publish the
matching event → return the updated `KnowledgeVersion`. `KnowledgeVersionManager` is a
distinct, mid-level class — composing Registry + Session + Statistics + a token-keyed
execution ledger — mirroring `@aos/knowledge-provider`'s `KnowledgeProvider`/
`KnowledgeProviderManager` split.

## Domain Model

`KnowledgeVersion`, `KnowledgeRevision`, `KnowledgeBranch`, `KnowledgeSnapshot`,
`KnowledgeHistory`, `KnowledgeLineage`, `KnowledgeRollback`, `KnowledgeMerge`,
`KnowledgeComparison`, `KnowledgeVersionMetadata`, `KnowledgeVersionConfiguration`,
`KnowledgeVersionPermission`, `KnowledgeVersionPolicy` — the exact 13 aggregates named by
the prompt. `KnowledgeVersionType` covers the 10 required types (Major, Minor, Patch,
Draft, Snapshot, Release, Hotfix, Experimental, Temporary, AutoGenerated);
`KnowledgeBranchType` covers the 7 required types (Main, Development, Feature, Release,
Hotfix, Experiment, Archive).

## Lifecycle

11 states, in the prompt's own order: Draft, Created, Validated, Published, Superseded,
Deprecated, Archived, Restored, Merged, RolledBack, Destroyed. Only `Destroyed` is
hard-terminal. `KnowledgeVersionLifecycle` is a read-only, query-only companion
(`states()`/`transitionsFrom()`/`isTerminal()`/`isSettled()`) to the imperative
`KnowledgeVersionStateMachine`, which is the only code allowed to change
`KnowledgeVersionInstance.state` — every legal transition appends one immutable history
entry.

## Registry

One generic `KnowledgeVersionRegistry` class covers the exact 8 required buckets —
Version, Snapshot, Branch, History, Lineage, Metadata, Statistics, Session — as a
`Map<Bucket, Map<string, Identified>>`. Never scanned: every lookup is a direct Map read
by id via `KnowledgeVersionResolver`.

## Pipeline

Exactly 8 fixed stages, per the prompt: Validation → Permission → Policy → Tracing →
Metrics → Lifecycle → Audit → Logging. Validation runs the real 10-stage
`KnowledgeVersionValidator`; Permission/Policy run the real `KnowledgeVersionPermission`/
`KnowledgeVersionPolicy` evaluators; Tracing stamps a `KnowledgeVersionTrace`; Metrics
records a Validation-Count sample; Lifecycle drives the State Machine (when a
`targetState` is supplied); Audit appends a `KnowledgeVersionAuditEntry`; Logging appends
a `KnowledgeVersionLogEntry` — all onto the immutable `KnowledgeVersionExecution` record.

## Validator

A strict 10-stage validator, in the prompt's own order: Identity, Metadata, Version
Number, Lifecycle, Branch, Policy, Permission, Configuration, Dependency, Integrity. Every
stage runs and aggregates its issues — no short-circuiting within the Validator itself.

## Metrics

```
KnowledgeVersionMetrics
├── versionCount / snapshotCount / branchCount
├── rollbackCount / mergeCount / comparisonCount
├── archiveCount / publishCount
└── validationCount (+ an internal validationFailureCount for Health)
```

## Monitoring

`KnowledgeVersionMonitoring.sample()` combines a Metrics snapshot and a Health report into
one `KnowledgeVersionDashboard` — exact name `KnowledgeVersionMonitoring`, not
`...Monitor`, per the prompt's Public API list.

## Health

5 statuses (Healthy/Warning/Degraded/Unavailable/Unknown). `KnowledgeVersionHealth.check()`
derives Registry health from bucket occupancy and domain health from a caller-reported
success/failure ratio (the Pipeline's Validation outcomes, via
`KnowledgeVersionMonitoring`).

## Statistics

`KnowledgeVersionStatistics` — per-`KnowledgeVersionType` created/published counters, its
own private map, separate from the Registry's `STATISTICS` bucket (which exists for
callers registering their own externally computed statistics providers).

## Runtime Token

Every Version has a `KnowledgeVersionToken` (`kver_` prefix — every sibling Knowledge
package's prefix, `ptok_`/`rtok_`/`ktok_`/`stok_`/`ksrc_`, was already taken).
`KnowledgeVersionManager` looks up executions by token in an internal
`Map<token, KnowledgeVersionExecution>` — never a full-collection scan.

## Extension Points

10 interface-only contracts, zero implementations: `IKnowledgeMergeStrategy`,
`IKnowledgeComparisonEngine`, `IKnowledgeDiffProvider`, `IKnowledgeSnapshotProvider`,
`IKnowledgeRollbackProvider`, `IKnowledgeBranchProvider`, `IKnowledgeVersionStorage`,
`IKnowledgeAuditProvider`, `IKnowledgeConflictResolver`, `IKnowledgeVersionPublisher`.
Optionally wired via `KnowledgeVersioningConfig`; never required by any Version Operation.

## Known Limitations

- **All 10 named extension-point contracts have zero implementations** — by design. No
  merge algorithm, no diff engine, no real content rollback/snapshot storage exists
  anywhere in this package.
- **`KnowledgeVersionResolver` ships zero registered Versions** — a caller must
  `createVersion()` at least one Version before any `resolve*()` call can return results.
- **`KnowledgeVersionSession` is a separate access-window ledger from the Version
  Lifecycle State Machine** — the two are not automatically kept in sync.
- **Rollback/Merge/Compare only record metadata** — the actual content
  merge/diff/restore is delegated to an optional caller-supplied Extension Point.

## Dependency Rules

Allowed: `@aos/kernel`/`@aos/runtime-kernel`, `@aos/shared`/`@aos/common`,
`@aos/events`/`@aos/event-bus`, `@aos/knowledge-engine`. Read-only contracts only — never
another runtime's implementation classes, never a circular dependency.

## Persistence

None. `KnowledgeVersionRegistry`/`KnowledgeVersionSession`/`KnowledgeVersionManager`'s
execution ledger are in-memory only.
