# Migration & Upgrade Strategy

Governs: [`docs/004-TECHNOLOGY-SELECTION-RECORD.md`](../docs/004-TECHNOLOGY-SELECTION-RECORD.md) §9, applying Constitution §21 Versioning Strategy to infrastructure/technology choices.

## 1. Principle

Every "default + escape hatch" decision in the TSR has a **named trigger condition**, not an open-ended "revisit later." A migration is planned and rehearsed before it is needed, never improvised under production pressure. Every technology version is pinned explicitly; upgrades follow a staged soak period (dev → staging → canary tenant subset → general availability), mirroring the Simulation/Canary discipline already established for Agent/Workflow changes (Architecture doc 002 §30, ADR-013/ADR-014).

## 3. Upgrade Strategy (Version Currency, Not Just Migration)

- **Pin every dependency version explicitly** in IaC/manifests (Terraform, container base images, Kubernetes API versions) — no floating `latest` tags in any production-bound configuration (Constitution RULE-086 discipline extended to infra).
- **Staged rollout for every upgrade**: dev environment first, then staging with synthetic load (leveraging the Simulation Contract's sandboxed scenario infrastructure where applicable), then a canary tenant subset in production (mirroring ADR-014's canary pattern), then general availability.
- **Security patches are the exception to staged pacing** — critical CVEs affecting any TSR-selected technology are patched on an expedited track (dev→staging soak compressed to hours, not weeks), per Constitution §20 Security Standards priority.
- **Major version upgrades require a written upgrade note** (analogous to a mini-ADR) covering: breaking changes, the specific AOS components affected, and a rollback plan — filed alongside the relevant `tech-stack/<category>.md` file.
- **Deprecation windows** for any TSR technology being phased out follow the same 90-day minimum dual-support principle as Contract versioning (doc 003.5 §23), to avoid forcing a rushed cutover.

## 4. Explicitly Out of Scope for This Document

No migration in this file is executed as part of this Engineering Task — this document defines _when and how_ a future migration would be triggered and carried out, consistent with the TSR's "technology decisions only, no implementation" mandate.
