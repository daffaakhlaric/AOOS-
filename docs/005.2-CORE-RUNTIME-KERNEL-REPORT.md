**New third-party dependencies and their documented reasons** (per the Definition of Done's "every new dependency has a documented reason" requirement):

- **`semver` (^7.6.3)** — used in `version/version-check.ts` for `isVersionCompatible`/`compareVersions`. Reason: version-range compatibility checking is correctness-critical (a wrong hand-rolled comparison could silently accept an incompatible Module/Plugin version); `semver` is the de facto standard, dependency-free, MIT-licensed implementation, already implicitly trusted by the entire npm ecosystem's own version resolution.
- **`zod` (^3.23.8)**, declared directly (previously only a transitive dependency via `@aos/config`) — used in `contracts/kernel-options.ts` and `startup/configuration-service.ts` to accept a caller-supplied `ZodTypeAny` schema for `KernelOptions.configSchema`. Reason: the Kernel's Configuration Service must support typed, tenant/service-specific config extension beyond `@aos/config`'s generic `baseConfigSchema`, and depending on `zod` directly (rather than only transitively) is the honest declaration of that direct usage.

## 8. Known Limitations

1. **`os.loadavg()` always returns `[0, 0, 0]` on Windows** (documented Node.js behavior) — `KernelHealthService`'s CPU check is a real, working heuristic on Linux/macOS but is a structural no-op (always passes) on Windows. This was verified during implementation, not discovered later, and is called out in the source code comment.
2. **`@aos/logger` is a declared but unused dependency** — the Kernel does not yet emit any of its own structured logs (state transitions, hook failures, etc. currently surface only via thrown exceptions and Kernel Events). Wiring a `Logger` through `KernelDependencies` is deferred rather than half-implemented.
3. **No OpenTelemetry span/metric emission from the Kernel itself** — `@aos/telemetry`'s `initTracing`/`initMetrics` are not invoked anywhere in this package; `KernelMetricsCollector`'s snapshot is a pull-based, in-memory-only mechanism, consistent with `@aos/telemetry`'s own "mechanics only, no exporter" scoping (see `docs/005.1-CORE-RUNTIME-FOUNDATION-REPORT.md` §7).
4. **`KernelEventEmitter` is entirely in-process** — it does not persist events, does not survive a process restart, and has no cross-instance/cross-process delivery. This is intentional and documented in `events/kernel-event.ts`'s file-level comment, distinguishing it from the future platform Event Bus.
5. **`ModuleLoader`/`PluginLoader` have no unload-then-reload path exercised in integration** — `unload()` exists and is unit-tested in isolation, but `Kernel` itself never calls it (no "hot-unload a running module" capability yet).
6. **`ConfigurationService.get()` return type is not deeply frozen** — `override()` mutates the service's own state correctly, but a caller holding a reference to a previously-returned config object could still mutate it in place (TypeScript `readonly`-at-the-type-level only, not a runtime `Object.freeze`).
7. **Health/Diagnostics `getConfigurationStatus` in `bootstrap/kernel-builder.ts` never reports `"error"`** — the `ConfigurationStatus` type includes `"error"` (contracts §9 of doc 003.5's Health Contract concept) but the current wiring only ever produces `"loaded"`/`"not_loaded"`, since a configuration load failure currently throws (halting the Kernel) rather than being captured as a queryable status.

## 10. Readiness Checklist for ENGINEERING TASK 005.3 (Registry System)

This checklist assesses what the Kernel already provides that a Registry System implementation can build on, and what 005.3 will need to add — **nothing in this checklist is implemented as part of this report.**

- [x] A `ServiceContainer` (DI) exists for the Registry Service to register itself into and be resolved from by future Agent/Tool/Workflow loaders.
- [x] A `ModuleLoader`/`PluginLoader` mechanism exists that a Registry-backed module/plugin source could eventually populate dynamically (currently only supports statically-provided `KernelOptions.modules`/`.plugins`).
- [x] A `ConfigurationService` exists that the Registry Service's own connection config (e.g., to whatever storage backend 005.3 selects) can extend via `KernelOptions.configSchema`.
- [x] `KernelEventName.MODULE_LOADED` / `PLUGIN_LOADED` events already exist as the wiring point for a future `registry.<type>.published` event pattern (doc 003.5 §14) to hook into.
- [x] `CapabilityRegistry` already provides the "named, versioned thing" registration shape the Registry Contract's common envelope (doc 003.5 §13) can be modeled after or wrap.
- [x] `KernelException` hierarchy is extensible — Registry-specific exceptions should extend `KernelException` (or `@aos/errors`' `AosError` directly, following the same pattern) rather than introducing a parallel hierarchy.
- [ ] **Not yet provided:** any persistence/storage adapter — the Registry System will need to select and wire its own (per TSR §3.4/§3.6 decisions), independent of the Kernel.
- [ ] **Not yet provided:** the Registry Contract's versioning/immutability enforcement (doc 003.5 §13, §23) — this is 005.3's core responsibility, not something the Kernel pre-supplies.
- [ ] **Not yet provided:** any tenant-scoped override resolution (DDD §25, doc 003.5 §9.5) — the Kernel's `TenantContext` exists structurally but nothing yet resolves a tenant-specific Registry override through it.
- [ ] **Recommendation:** 005.3 should implement the Registry System as a `Module` (implementing `IModule`'s optional lifecycle hooks) registered into a `buildKernel({ modules: [registryModule] })` call, exercising the Kernel's existing Module Loader mechanics end-to-end for the first time with real (non-fake) content — this would also retroactively validate the current 95%+ Foundation-phase test coverage against a real consumer, per this task's Definition of Done principle of not treating a metric as sufficient proof on its own.
