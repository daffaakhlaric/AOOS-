KnowledgeQuality (quality/) — the public façade, composition root

  Configuration Resolution → Metadata → Metrics → Lifecycle → Audit → Logging

        │

## Domain Model

`KnowledgeQualityAssessment`, `KnowledgeQualityJob`, `KnowledgeQualitySession`,
`KnowledgeQualityFinding`, `KnowledgeQualityRule`, `KnowledgeQualityProfile`,
`KnowledgeQualityConfiguration`, `KnowledgeQualityMetadata`, `KnowledgeQualityReport`,
`KnowledgeQualityStatistics`, `KnowledgeQualityAudit`, `KnowledgeQualityScoreMetadata` —
the exact 12 aggregates named by the prompt, each backed by a Zod schema
(`domain/knowledge-quality-*.ts`).

**Finding-vs-score modeling (judgment call):** `KnowledgeQualityFinding` is a discrete
issue/observation — `{findingId, assessmentId, dimension, severity, description,
locationReference?, ruleId?}` — while `KnowledgeQualityScoreMetadata` is metadata ABOUT a
numeric/qualitative score a caller-supplied `IKnowledgeQualityScoringProvider` reported —
`{scoreId, assessmentId, dimension, value?, qualitativeValue?, providerId, recordedAt}`.
Neither is ever computed by this package.

**Rule-vs-Profile modeling:** `KnowledgeQualityRule` is a single named check definition
(metadata only — `{ruleId, name, dimension, severity, active}`, no executable rule
logic); `KnowledgeQualityProfile` bundles Rule ids plus per-Dimension weights
(`{ruleIds[], dimensionWeights}`) — also metadata only, never interpreted by this
package.

**Policy is not a Registry bucket (judgment call):** the spec's 8 Registry buckets
(`Assessment Registry, Session Registry, Finding Registry, Rule Registry, Profile
Registry, Statistics Registry, Audit Registry, Configuration Registry`) do not include
Policy — `KnowledgeQualityPolicy` records instead live in a dedicated
`Map<string, KnowledgeQualityPolicy>` on `KnowledgeQualityResolver`, resolved via
`resolvePolicy()`/`tryResolvePolicy()` and registered via `registerPolicy()`. This mirrors
how `KnowledgeQualityJob` similarly has no Registry bucket and instead lives on a
dedicated `jobsById` Map on `KnowledgeQualityManager`.

**Configuration DOES get its own Registry bucket (contrast with `@aos/knowledge-generator`
005.7K):** unlike Generator, which modeled `KnowledgeGenerationConfiguration` as an inline
execution-envelope field with no Registry bucket, this package's spec explicitly lists
"Configuration Registry" as one of the 8 buckets — so `KnowledgeQualityConfiguration` is a
first-class Registry-backed, Resolver-backed aggregate here.

## Quality Flow

`createAssessment()` (→ Draft) → `queue()` (→ Queued) → `prepare()` (→ Preparing,
resolves Rule/Profile/Policy/Configuration through the 10-stage Pipeline) → `start()`
(→ Assessing, invokes a configured `IKnowledgeQualityProvider.assess()`/
`IKnowledgeQualityScoringProvider.score()` if configured, recording any returned
Findings/Score Metadata) → `review()` (→ Reviewing) → `complete()` (→ Completed, records
statistics and a real average duration metric) — or `fail()`/`cancel()` at any earlier
point, then `archive()` → `destroy()`. Every operation is one atomic Pipeline call:
validate → drive State Machine → record metadata → update statistics → publish the
matching event → return the updated `KnowledgeQualityAssessmentRecord`. Findings can also
be recorded directly via `recordFinding()` while Assessing/Reviewing, and a
`KnowledgeQualityReport` aggregating recorded Finding/Score-Metadata ids is built via
`generateReport()`.

## Assessment Lifecycle

10 states, in the prompt's own order: Draft, Queued, Preparing, Assessing, Reviewing,
Completed, Cancelled, Failed, Archived, Destroyed. Only `Destroyed` is hard-terminal.

**Transition-table design (judgment call — the prompt lists the 10 states but not the
edges between them):**

```
Draft      -> Queued, Cancelled, Destroyed
Queued     -> Preparing, Cancelled, Failed, Destroyed
Preparing  -> Assessing, Cancelled, Failed, Destroyed
Assessing  -> Reviewing, Cancelled, Failed, Destroyed
Reviewing  -> Completed, Cancelled, Failed, Destroyed
Completed  -> Archived, Destroyed
Cancelled  -> Archived, Destroyed
Failed     -> Archived, Destroyed
Archived   -> Destroyed
Destroyed  -> (none — terminal)
```

`Draft -> Queued -> Preparing -> Assessing -> Reviewing -> Completed` is the mainline
path; every non-settled state can additionally be `Cancelled` or `Destroyed` directly;
`Queued`/`Preparing`/`Assessing`/`Reviewing` can fail into `Failed`; `Completed`/
`Cancelled`/`Failed` all fan into `Archived`; every state (including `Archived`) has an
edge into the hard-terminal `Destroyed`. A dedicated test proves every one of the 10
states is reachable from `Draft` via BFS over this table (both at the raw
`KNOWLEDGE_QUALITY_ASSESSMENT_STATE_TRANSITIONS` level and again through the façade's
actual operations in `test/quality/quality.spec.ts`), and a full 10×10 legality matrix
test (`test/state-machine/transition-table.spec.ts`, 100 assertions) locks the table down.

The façade adds a `review()` operation (`Assessing -> Reviewing`) — not explicitly named
in the prompt's operation list but required to reach `Reviewing` before `complete()`
(`Reviewing -> Completed`) can run, since `Assessing -> Completed` is intentionally NOT a
direct edge (Reviewing is meant as a real checkpoint, not a pass-through state). This
mirrors how `@aos/knowledge-generator` added its own `review()` beyond its named
Generation Operations list.

`KnowledgeQualityLifecycle` (`states()`/`transitionsFrom()`/`isTerminal()`/
`isSettled()`) is a read-only, query-only companion to the imperative
`KnowledgeQualityStateMachine`, which is the only code allowed to change
`KnowledgeQualityAssessment.state` — every legal transition appends one immutable history
entry and stamps `startedAt` (entering Assessing) / `completedAt` (entering Completed).
`KnowledgeQualityStateMachine.transition()` throws
`IllegalAssessmentTransitionException` for any edge not present in the table.

## Registry

One generic `KnowledgeQualityRegistry` class covers the exact 8 required buckets —
Assessment, Session, Finding, Rule, Profile, Statistics, Audit, Configuration — as a
`Map<Bucket, Map<string, Identified>>`. Never scanned: every read is a direct Map lookup
by id through `KnowledgeQualityResolver`; `list()`/`count()` exist only for
Metrics/Health sampling. Notably, JOB and POLICY are **not** Registry buckets in this
package — the spec enumerates exactly these 8 names and neither Job nor Policy appears —
so `KnowledgeQualityAssessmentJob` records live in a dedicated `jobsById` Map on
`KnowledgeQualityManager` and `KnowledgeQualityPolicy` records live in a dedicated
`policiesById` Map on `KnowledgeQualityResolver`, matching the Session-ledger convention
used for both.

## Resolver

`KnowledgeQualityResolver` — a single class implementing the exact 5 dimensions named by
the prompt (Assessment Resolver, Rule Resolver, Profile Resolver, Policy Resolver,
Configuration Resolver) as 5 method-groups, matching the sibling-package convention of
implementing multiple named "Resolvers" as one class with per-domain resolve methods —
each with a throwing `resolveX()` (raising `QualityNotFoundException`) and a
non-throwing `tryResolveX()`. Rule additionally exposes batch `resolveRules()`/
`tryResolveRules()` methods (the latter partitioning ids into `resolved`/`missing`),
since a single Assessment Request can declare many Rule ids at once.

## Validation

A strict 12-stage validator, in the prompt's own order: Identity, Metadata, Assessment,
Rule, Profile, Policy, Configuration, Lifecycle, Dependency, Statistics, Integrity, Audit.
Every stage runs and its issues are aggregated — no short-circuiting within the
Validator, matching every prior AOS Knowledge package's convention. The Dependency stage
(9) enforces real cross-field rules: every non-`Custom` Assessment Mode requires at least
one declared Rule or a Profile; a resolved Policy with `requireApproval` requires a
Configuration record. The Statistics stage (10) sanity-checks an optionally-supplied
`KnowledgeQualityAssessmentStatisticsSnapshot` for internal consistency (no negative
counts, `completedCount + failedCount` never exceeding `requestedCount`) — distinct from
the real `KnowledgeQualityStatistics` class, which owns the actual running counters this
stage merely validates a snapshot of. The Integrity stage (11) cross-checks `tenantId`
consistency between Context and Metadata, and Profile tenantId consistency.

**Validator "Audit" stage (12) vs. Pipeline "Audit" stage (9) — documented distinction:**
the Validator's Audit stage is a **pre-flight** field check — it confirms
`request.requestedBy` (the audit actor) and `request.createdAt` are present/well-formed
BEFORE an operation runs. The Pipeline's Audit stage is a **post-flight** side effect — it
APPENDS the actual `KnowledgeQualityAssessmentAudit` entry (with `fromState`/`toState`/
`occurredAt`, registered into the `AUDIT` Registry bucket) AFTER the operation completes.
The two never duplicate each other's work; both are required for the "12 Validator
stages" / "10 Pipeline stages" counts to be exact per the spec.

**Testing implication:** because the Validator's Rule/Profile/Policy/Configuration stages
(4/5/6/7) independently check the same resolvability facts the Pipeline's own Rule/
Profile/Policy/Configuration Resolution stages (2/3/4/5) compute, a malformed Request
normally fails fast at Pipeline Stage 1 (Validation) before ever reaching Stages 2-5's own
resolution code. `test/pipeline/pipeline.spec.ts` isolates Stages 2-5's own exception
paths (`QualityRuleException`/`QualityProfileException`/`QualityPolicyException`/
`QualityConfigurationException`) using a permissive stub Validator, so both layers'
independent logic are separately covered.

`KnowledgeQualityStatistics` maintains its own private
`Map<KnowledgeQualityAssessmentMode, KnowledgeQualityAssessmentStatisticsSnapshot>`

## Known Limitations

- **All 12 named extension-point contracts have zero implementations** — by design. No
  real scoring/evaluation exists anywhere in this package; they are invoked only when a
  caller supplies one via `KnowledgeQualityConfig` — this package never does so itself.
- **`review()` is a bare Lifecycle transition** — it records no reviewer decision payload;
  a caller wanting richer review metadata attaches it to
  `KnowledgeQualityAssessmentMetadata` before calling `review()`.
- **`KnowledgeQualityResolver` ships zero registered Rules/Profiles/Policies/
  Configurations** — a caller must `registerRule()`/`registerProfile()`/
  `registerPolicy()`/`registerConfiguration()` at least once before any `resolve*()` call
  for that dimension can succeed.
- **`KnowledgeQualitySession` is a separate access-window ledger from the Assessment
  Lifecycle State Machine** — the two are not automatically kept in sync; closing a
  Session does not cancel or otherwise affect the underlying Assessment's state.
- **No cost tracking, no streaming, no caching wired by default** —
  `IKnowledgeQualityCostProvider`/`IKnowledgeQualityStreamingProvider` exist purely as
  extension points.
- **`destroy()` is idempotent, not error-on-repeat** — calling `destroy()` a second time
  on an already-`Destroyed` Assessment is treated as a Lifecycle no-op (since
  `targetState === currentState` skips the State Machine stage) rather than throwing,
  matching the same-target-state convention every other Assessment Operation follows.

## Technical Debt

- The 12-stage Validator and the 10-stage Pipeline independently compute the same Rule/
  Profile/Policy/Configuration resolvability facts (see "Testing implication" above) —
  functionally correct and matches the sibling-package convention, but is duplicated work
  on every Pipeline run. A future optimization could thread the Validator's precomputed
  facts into the Pipeline's resolution stages instead of resolving twice.
- `KnowledgeQualityJob` scheduling is metadata-only (`createJob`/`completeJob`/
  `failJob`) — there is no real queueing/execution timing, matching
  `IKnowledgeQualityScheduler`'s extension-point-only status.
- `KnowledgeQualityPolicy` has no dedicated Registry bucket (the 8-bucket spec has no slot
  for it) — Policy records live only on a dedicated map on `KnowledgeQualityResolver`,
  not visible via `KnowledgeQualityRegistry.list()`/`count()` the way the other 8 bucket
  types are. A future phase wanting Policy visibility through the generic Registry
  surface would need an additive, non-breaking spec change.

## Non-obvious design/judgment calls (full list)

1. **Dependency-name mapping** — the prompt's "Allowed Dependencies" names
   `@aos/kernel`/`@aos/shared`/`@aos/events`/`@aos/knowledge-engine`/
   `@aos/knowledge-generator`/`@aos/knowledge-policy`. The real workspace packages are
   `@aos/runtime-kernel` (not `@aos/kernel`), `@aos/common` (not `@aos/shared`), and
   `@aos/event-bus` (not `@aos/events`) — the same mapping every prior sibling package
   used. `@aos/knowledge-engine`/`@aos/knowledge-generator`/`@aos/knowledge-policy` all
   exist as real workspace packages but, like every sibling package, this package imports
   zero concrete classes from any of them at runtime.
2. **Event-name mapping** — `AssessmentCreated`/`AssessmentQueued`/`AssessmentStarted`/
   `AssessmentCompleted`/`AssessmentFailed`/`AssessmentCancelled`/`AssessmentArchived`/
   `AssessmentDestroyed`/`FindingCreated`/`ReportGenerated` map onto dotted event-bus type
   strings under the `knowledge.quality.*` namespace, matching the
   `knowledge.generation.*`/`knowledge.marketplace.*` pattern established by sibling
   packages.
3. **Finding-vs-ScoreMetadata modeling** — see "Domain Model" above.
4. **Lifecycle transition-table design** — see "Assessment Lifecycle" above, including
   the addition of a `review()` facade operation not explicitly named in the prompt's
   operation list.
5. **Resolver shape** — one `KnowledgeQualityResolver` class with 5 method-groups rather
   than 5 separate classes, matching every prior sibling package's convention for
   multi-named "Resolvers".
6. **Future Readiness interpretation** — exactly 2 additional single-purpose interfaces
   (`IKnowledgeValidatorAiQuality` for 005.7M, `IEmbeddingManagerQuality` for 005.7N),
   matching the prompt's "Future Readiness" section naming exactly 2 downstream phases
   (unlike `@aos/knowledge-generator`, whose prompt named 3 downstream phases including
   itself as the first).
7. **Token prefix chosen** — `kqua_` (Knowledge QUAlity), confirmed collision-free against
   every existing prefix in the codebase (`ptok_`, `stok_`, `ksrc_`, `kver_`, `kpol_`,
   `kmkt_`, `kgen_`).
8. **Validator "Audit" stage vs. Pipeline "Audit" stage distinction** — see "Validation"
   above; documented explicitly to avoid the two being mistaken for duplicated scope.
9. **Policy and Job have no Registry bucket** — the spec's 8-bucket list has no slot for
   either; both are modeled as dedicated Maps instead (see "Registry" above) — a
   documented judgment call, contrasting with `KnowledgeQualityConfiguration`, which DOES
   get a bucket since the spec explicitly names "Configuration Registry".
10. **Session domain-record keying** — `KnowledgeQualityAssessmentSession` Registry
    entries are keyed by a freestanding `sessionId` (via `registry.require<...>(SESSION,
token)` where the session's `id` field equals the owning Assessment's token) —
    matching the token-keyed-lookup convention while still carrying its own `sessionId`
    for domain identity.
11. **Statistics keyed by Assessment Mode, not Quality Dimension** — a single Assessment
    always has exactly one Mode but may span many Dimensions, so Mode is the natural
    per-record statistics key; Dimension-level rollups are left to a caller aggregating
    over `KnowledgeQualityFinding`/`KnowledgeQualityScoreMetadata` records directly.
