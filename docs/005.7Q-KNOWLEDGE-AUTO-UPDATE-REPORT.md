# 005.7Q — Enterprise Knowledge Auto Update — Engineering Report

Status: **Complete**. Package: `packages/knowledge-auto-update` (`@aos/knowledge-auto-update`).

## Architecture Overview

`@aos/knowledge-auto-update` is a standalone, pure in-memory engine that detects, schedules,
validates, refreshes, synchronizes, and updates knowledge assets. It does not read from a
database, does not make network calls, does not persist to the filesystem, and — per the 005.7Q
constraint (identical to 005.7O `@aos/knowledge-graph` and 005.7P `@aos/knowledge-analytics`) —
imports **zero** other `@aos/*` packages at runtime.

This is the second package in the series (after `@aos/knowledge-graph`) where real algorithmic
correctness, not just orchestration, is the point, and the first where **full determinism** is a
first-class architectural constraint: nothing in this package calls `setTimeout`/`setInterval`/bare
`Date.now()` inside domain or scheduling logic. Every time-dependent computation depends on an
injected `IClock`, and the scheduler exposes an explicit `processDue(now)` entry point instead of
registering real timer callbacks.

## Determinism Design

The prompt's Critical Determinism Requirement was treated as the package's central engineering
constraint, on par with the standalone constraint:

- **`IClock` contract** (`src/contracts/i-clock.ts`): `{ now(): number }`. `SystemClock`
  (`src/utils/clock.ts`) is the only place `Date.now()` appears in `src/`, and it is wired in only
  as the default constructor argument at the outermost composition boundary
  (`KnowledgeAutoUpdateEngine`'s constructor, `InMemoryEventPublisher`'s constructor). Every
  service, stage, and the scheduler itself take an `IClock` via constructor/context injection.
- **`ManualClock`**: a hand-advanced fake with `.advance(ms)` and `.set(timestamp)`, used by all
  702 tests that need "time" — zero reliance on real wall-clock waiting anywhere in the suite.
- **Scheduler is pure data + decision logic.** `KnowledgeUpdateScheduler` never registers a real
  timer callback. `computeInitialRunAt`/`computeNextRunAt` are pure functions of
  `(scheduleDescriptor, now)`; `processDue(now)` is a pure(-ish, mutating only its own internal
  `Map`) function a caller or test invokes explicitly to advance processing.
- **Cron evaluation is pure.** `computeNextCronFireTime(expression, fromEpochMs)` and
  `computeNextCronFireTimeAtOrAfter(expression, fromEpochMs)` are pure functions with no timer
  involvement — they compute the answer by minute-stepping a `Date` object, never by waiting.
- **Backoff is pure.** `computeExponentialBackoffDelay(attempt, options)` is a pure function;
  optional jitter must be a caller-supplied pure function (never `Math.random()`).

Final self-check performed before completion:
`grep -rnE "setTimeout|setInterval|Date\.now\(\)" src` returns exactly one match —
`src/utils/clock.ts`'s `SystemClock.now()` implementation, the intended single real-clock
boundary — plus doc-comment mentions of `Date.now()`/`setTimeout`/`setInterval` in
`src/contracts/i-clock.ts` describing what the contract exists to avoid.

### 13 Supported Update Types — strategy dispatch

Each `KnowledgeUpdateType` has exactly one `IKnowledgeUpdateStrategy` implementation, resolved by
`KnowledgeUpdateStrategyRegistry` and dispatched from the pipeline's Execute Update stage (never an
if/else chain):

| Update Type     | Strategy                        | Behavior                                                       |
| --------------- | ------------------------------- | -------------------------------------------------------------- |
| Manual          | `ManualUpdateStrategy`          | Full replace with `task.payload`                               |
| Scheduled       | `ScheduledUpdateStrategy`       | Full replace with `task.payload`                               |
| Full            | `FullUpdateStrategy`            | Full replace with `task.payload`                               |
| Emergency       | `EmergencyUpdateStrategy`       | Full replace, tagged `emergency: true`                         |
| Incremental     | `IncrementalUpdateStrategy`     | Merge `task.payload` over `previousPayload`                    |
| Metadata        | `MetadataUpdateStrategy`        | Merge `task.payload` over `previousPayload`                    |
| Refresh         | `RefreshUpdateStrategy`         | Re-apply payload, stamp `refreshedAt`                          |
| Synchronization | `SynchronizationUpdateStrategy` | Re-apply payload, stamp `synchronizedAt`                       |
| Recovery        | `RecoveryUpdateStrategy`        | Merge over `previousPayload`, stamp `recoveredAt`              |
| Retry           | `RetryUpdateStrategy`           | Full replace, tagged with `task.attempt`                       |
| Policy          | `PolicyUpdateStrategy`          | Full replace, tagged `policyUpdated: true`                     |
| Dependency      | `DependencyUpdateStrategy`      | Full replace, tagged `dependencyUpdated: true`                 |
| Version         | `VersionUpdateStrategy`         | Requires a valid, strictly-newer `payload.version`, else fails |

`VersionUpdateStrategy` is the one strategy with genuine business-rule failure modes (missing or
non-newer version) — every other strategy is a pure, always-succeeding payload transformation,
since this package never touches real content/I/O and therefore has nothing else to fail on.

### Scheduler capabilities

`KnowledgeUpdateScheduler` supports every capability from the spec:

- **Immediate** — `computeInitialRunAt` returns `now`.
- **Scheduled** — one-shot at a fixed `runAt`.
- **Interval** — repeating every `intervalMs` from `startAt`.
- **Cron-style** — repeating per a 5-field cron-subset expression (see "Cron Subset" below).
- **Priority Queue** — due jobs are ordered by descending numeric priority via a real binary heap
  (`PriorityQueue`), FIFO tie-break.
- **Dependency-aware** — `processDue(now)` builds edges from each due job's `dependsOn` (restricted
  to other jobs in the same due batch) and orders the result with `priorityTopologicalSort`.
- **Retry / Backoff scheduling** — `KnowledgeUpdateCoordinator.handleFailure` re-registers (if the
  one-shot entry was already removed) or reschedules the job to `now + computeExponentialBackoffDelay(...)`.
- **Pause / Resume / Cancel** — `pause`/`resume`/`cancel`, all id-keyed `Map` operations.

### 10-stage Update Pipeline

`KnowledgeUpdatePipeline` runs the exact sequence per due job: Detect Changes → Analyze Changes →
Validate Update → Resolve Dependencies → Resolve Conflicts → Calculate Priority → Execute Update →
Validate Result → Generate Report → Publish Events. Each stage is a real class delegating to the
corresponding service — no stub stages. A thrown exception from any stage is wrapped in
`PipelineStageFailureException` naming the failing stage; `KnowledgeUpdateCoordinator`
special-cases a wrapped `DependencyNotSatisfiedException` (re-queue, no failure/attempt increment)
versus any other stage failure (routed through retry/backoff).

### 11 Policy categories

Modeled as `RetryPolicyRules` (covering Maximum Retry + Retry Delay + Exponential Backoff
together), plus 8 further small rules interfaces (`ConflictResolutionRules`, `PriorityRules`,
`DependencyRules`, `FreshnessRules`, `ExpirationRules`, `VersionCompatibilityRules`,
`UpdateWindowRules`, `RateLimitingRules`), all composed into one immutable `KnowledgeUpdatePolicy`
value object.

### 16 Metrics

`KnowledgeUpdateMetrics.compute()` is a pure function turning a `KnowledgeUpdateStatistics`
snapshot plus current job-status counts and scheduler queue size into all 16 named metrics (Update/
Success/Failure/Retry/Conflict Count, Average Update/Validation/Refresh Time, Pending/Completed/
Cancelled/Expired Jobs, Queue Size, Success/Failure/Retry Rate) — rates default to exactly `0` on a
`0` denominator, never `NaN`.

### 13 Events / 10 Report types

All 13 spec events (`UpdateStarted` … `ReportGenerated`) are published at the correct pipeline
stage or coordinator action; verified by dedicated event-flow tests per stage plus integration
tests. All 10 `KnowledgeUpdateReportType` values are buildable through the single fluent
`KnowledgeUpdateReportBuilder` (see README Design Decision 12 for the flexible-builder rationale,
same pattern as `knowledge-analytics`).

## Design Decisions

See the README's "Design Decisions" section for the full numbered list (14 items) — reproduced
here for completeness:

1. Folder-structure interpretation: real top-level `src/`+`test/`(singular)+`README.md` layout,
   Engineering Report at the monorepo root, matching every completed sibling.
2. Standalone architecture (own exception base, event-publisher contract, module contract).
3. Injectable `IClock` interface (not a bare function type) so `ManualClock` can expose
   `.advance()`/`.set()` as real methods.
4. Cron-subset scope: standard 5-field syntax with `*`/single/list/range/step, OR-vs-AND semantics
   matching real cron, UTC-only, bounded ~139-day search.
5. Priority queue + dependency ordering unified via `priorityTopologicalSort` (a priority-aware
   generalization of Kahn's algorithm).
6. Exponential backoff: pure function, capped, deterministic (no `Math.random()`).
7. Priority queue: real binary min-heap with FIFO tie-breaking.
8. Change detection operates only on caller-supplied metadata snapshots.
9. 1:1 update-type-to-strategy mapping via a shared template-method base class.
10. Conflict resolution: exactly 2 real strategies (`LastWriteWins`, `VersionPriority`).
11. `KnowledgeUpdateStatistics` (mutable counters) vs. `KnowledgeUpdateMetrics` (pure calculator).
12. 10 report types via one flexible builder, not 10 classes.
13. Per-job dependency resolution against the registry, composing correctly with the scheduler's
    own batch-level dependency-aware ordering.
14. `durationMs` is always `0` on every strategy result (synchronous, pure, no real I/O).

### Additional non-obvious judgment calls specific to this report

15. **`KnowledgeUpdateStrategy` (Core Component #10) implemented as an interface
    (`IKnowledgeUpdateStrategy`), not a class**, since "Strategy" in the Strategy pattern is
    canonically the shared interface every concrete strategy implements — the 13 concrete classes
    plus `BaseKnowledgeUpdateStrategy` are the "implementation" half of this one named component.
16. **`KnowledgeRetryPolicy`/`KnowledgeBackoffStrategy` placed in `strategies/`, not
    `value-objects/`**, per the spec's explicit folder listing ("`strategies/`: ...
    `KnowledgeRetryPolicy`, `KnowledgeBackoffStrategy`").
17. **Dependency edges from a job's `dependsOn` outside the current due batch are treated as
    already-satisfied at the scheduler level** (`KnowledgeUpdateScheduler.processDue` only builds
    edges between jobs both present in the current due set) — cross-batch enforcement is instead
    handled per-job by the pipeline's Resolve Dependencies stage against the live registry (see
    Design Decision 13), which is the layer that actually knows a dependency's real status.
18. **`KnowledgeUpdateValidator`'s cron-error handling was simplified during coverage closure.**
    An initial defensive `error instanceof InvalidCronExpressionException ? ... : "invalid cron
expression"` ternary had an unreachable else-branch (since `parseCronExpression` always throws
    that exact exception type), which showed up as a branch-coverage gap; rather than write a
    contrived test to hit dead code, the defensive branch was removed and the code now asserts the
    known exception type directly, with a comment explaining why that's safe.
19. **`KnowledgeDependencyAnalyzer`/`KnowledgeRefreshPlanner` reuse the same `topologicalSort`
    utility the scheduler's `priorityTopologicalSort` is built from** — both the plain
    (dependency-only) and priority-aware variants live together in `utils/topological-sort.ts` so
    the two related algorithms stay next to each other and share the `DependencyCycleException`
    error-reporting shape.
20. **Coordinator retry re-registration forces the exact backoff-computed `nextRunAt` after
    `register()`**, rather than relying on `register()`'s own initial-run-at computation (which,
    for a `Scheduled`-kind job, would incorrectly jump back to the job's original fixed `runAt`
    instead of `now + backoffDelay`). This was caught by the coordinator's own retry-cycle
    integration test failing with a `JobNotFoundException` on the second retry attempt (the
    scheduler had already removed the one-shot entry after the first dispatch) — root-caused and
    fixed rather than papered over.

## Known Technical Debt

- **Rate-limiting and update-window policy fields are advisory only.** `KnowledgeUpdatePolicy
.rateLimiting` and `.updateWindow` are readable (`isWithinUpdateWindow(hourUtc)`) but not
  automatically enforced anywhere in the scheduler/coordinator — a host wanting hard enforcement
  must check these fields itself (matches the spec's explicit "Rate Limiting (logical only)").
- **`durationMs` is always `0`.** Because every strategy is a synchronous, pure transformation,
  `averageUpdateTimeMs`/`averageValidationTimeMs`/`averageRefreshTimeMs` will always read `0`
  unless a host wraps strategy execution with its own real timing.
- **Cron support has no local-timezone/DST semantics** and gives up (throwing) beyond a ~139-day
  search horizon — acceptable for an in-memory, host-driven-tick package with no real timers, but
  worth flagging for a future revision that might need calendar-aware scheduling.
- **No maximum-cardinality guard on the registry's `Map`-backed buckets.** A host that never calls
  `removeJob`/lets sessions/reports accumulate indefinitely will grow those maps unboundedly — this
  package has no built-in retention/eviction policy (unlike, e.g., `knowledge-analytics`'s
  `historyRetentionLimit`).
