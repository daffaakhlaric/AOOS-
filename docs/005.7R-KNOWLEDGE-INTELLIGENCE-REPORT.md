## Architecture Overview

`@aos/knowledge-intelligence` is a fully standalone, in-memory Enterprise Knowledge Intelligence engine. Like its three immediately-prior siblings (005.7O `knowledge-graph`, 005.7P `knowledge-analytics`, 005.7Q `knowledge-auto-update`), it imports **zero** other `@aos/*` packages at runtime. It defines its own:

- `KnowledgeIntelligenceException` exception base (mirrors `AosError`'s shape — `code`/`message`/`cause`/`context` — without extending `@aos/errors`).
- `IKnowledgeIntelligenceEventPublisher` local event-publishing contract, with an `InMemoryEventPublisher` default implementation and a `NoOpEventPublisher` alternative (no `@aos/event-bus` dependency).
- `IKnowledgeIntelligenceModule` minimal structural `IModule` equivalent (`id`/`start`/`stop`) so hosts that duck-type against `@aos/runtime-kernel`'s `IModule` can integrate `KnowledgeIntelligenceEngine` without a compile-time dependency.

Every time-dependent computation (freshness, staleness) is driven by an injectable `IClock`, defaulting to `SystemClock` (real wall-clock) only at the outermost composition boundary (`KnowledgeIntelligenceEngine`'s constructor); all domain logic elsewhere receives the clock via constructor injection and never calls `Date.now()` directly. Tests use `ManualClock` exclusively, so the entire suite is deterministic and reproducible with zero flakiness.

The package follows Domain-Driven Design + Clean Architecture layering:

```
types/ utils/ contracts/ errors/ events/       <- foundation (no internal deps)
value-objects/ entities/                        <- immutable domain model
similarity/ scoring/ classification/ gap/ analysis/   <- domain services (Strategy/Specification)
recommendation/                                  <- builds on analysis + scoring + similarity
intelligence/                                    <- composes analysis + scoring + recommendation
builders/ factories/ registry/                   <- construction + storage
pipeline/                                        <- orchestrates everything (Pipeline pattern)
services/                                        <- thin cross-cutting orchestration helpers
```

`KnowledgeIntelligenceEngine` (in `src/intelligence/`) is the single intended integration surface: it wires every engine/analyzer together, exposes `runIntelligence()` (executes the full 11-stage pipeline), `classify()`/`classifyAll()`, `suggestTags()`/`suggestTagsFromSimilarItems()`, `takeSnapshot()`, and read access to the underlying registry/configuration.

### Determinism design

No external AI model, no external embedding provider, no networking, no filesystem, no database. Every "intelligence" capability is computed from real, classical, explainable algorithms over caller-supplied structured input (a `KnowledgeItemSnapshot`):

- **Similarity**: Jaccard index over tag sets (primary), cosine similarity over optional numeric feature vectors (secondary, when both items supply one of equal length).
- **Classification**: a genuine Specification-pattern rules engine — `ISpecification<T>` predicates with `And`/`Or`/`Not` combinators, evaluated in priority order — not a trained model.
- **Scoring**: one shared `KnowledgeScoreComputer` (normalization + weighted aggregation + threshold evaluation) reused by Quality/Health/Freshness/Risk/Priority/Readiness/Coverage.
- **Gap/Orphan detection**: plain set-difference over a caller-supplied taxonomy table and adjacency-list connectivity checks — no graph is owned by this package.
- **Relationship discovery**: similarity-threshold and shared-tag-count based inference.

This is documented in depth in the package README under "Why classical deterministic algorithms instead of AI".

### 26 Intelligence Capabilities

All implemented: Knowledge Health/Freshness/Coverage/Completeness/Readiness/Quality/Risk/Priority Score; Duplicate Detection; Near-Duplicate Detection; Semantic (Jaccard/cosine) Similarity; Relationship Discovery; Gap Detection; Coverage Analysis; Staleness Detection; Orphan Knowledge Detection; Conflict Detection (via caller-supplied `conflictsWith`); Knowledge Classification; Auto Category Suggestion; Auto Tag Suggestion; Knowledge/Improvement/Merge/Archive/Update/Split/Consolidation Recommendation.

### 11-stage Analysis Pipeline

`KnowledgeIntelligencePipeline` runs, in strict sequence: `CollectKnowledgeStage` → `AnalyzeStructureStage` → `AnalyzeRelationshipsStage` → `AnalyzeSimilarityStage` → `AnalyzeCoverageStage` → `AnalyzeQualityStage` → `AnalyzeFreshnessStage` → `AnalyzeRisksStage` → `GenerateRecommendationsStage` → `GenerateIntelligenceReportStage` → `PublishEventsStage`. Each stage delegates to real, injected domain services (no stubs); a failure in any stage is wrapped in `PipelineStageFailureException` and the pipeline halts.

### 14 Report types

Modeled via one flexible entity, `KnowledgeIntelligenceReport`, parameterized by the `ReportType` enum (`KnowledgeIntelligence`, `Health`, `Coverage`, `Gap`, `Recommendation`, `Similarity`, `Classification`, `Relationship`, `Freshness`, `Quality`, `Priority`, `Readiness`, `Risk`, `ExecutiveSummary`) with a `sections: Record<string, unknown>` payload assembled per-type by `KnowledgeIntelligenceReportBuilder`. `KnowledgeHealthReport` and `KnowledgeGapReport` remain dedicated, strongly-typed entities because the spec names them explicitly as Core Components with a fixed shape.

### 14 Events

All implemented as `KnowledgeIntelligenceEventType` enum members, dotted (`knowledge_intelligence.<name>`), published through `IKnowledgeIntelligenceEventPublisher`: `IntelligenceStarted`, `IntelligenceCompleted`, `IntelligenceFailed`, `KnowledgeAnalyzed`, `InsightGenerated`, `RecommendationGenerated`, `GapDetected`, `DuplicateDetected`, `SimilarityDetected`, `RelationshipDiscovered`, `HealthCalculated`, `ScoreCalculated`, `ClassificationCompleted`, `ReportGenerated`.

## Design Decisions

1. **Folder-structure interpretation (judgment call).** The spec's raw listing runs `src/{19 folders}`, `tests/`, `README.md`, `docs/005.7R-...REPORT.md` as if all nested under `src/` — informal, not literal. Resolved identically to the three immediately-prior standalone siblings: package root has `src/` (19 subfolders), a top-level `test/` folder (singular, not `tests/`), a package-local `README.md`, and the Engineering Report lives in the **monorepo root's** `docs/` folder (`docs/005.7R-KNOWLEDGE-INTELLIGENCE-REPORT.md`), not `packages/knowledge-intelligence/docs/`.
2. **One flexible report entity for 14 report types**, per above — avoids 14 near-duplicate entity classes while keeping `KnowledgeHealthReport`/`KnowledgeGapReport` strongly typed since they are individually spec'd.
3. **Shared `KnowledgeScoreComputer`** (`scoring/knowledge-score-computer.ts`, wrapping `utils/scoring-math.ts`'s `normalizeToScore`/`weightedAverage`/`evaluateThreshold`) is the single implementation of the normalize → weighted-aggregate → threshold-evaluate pipeline, reused by every scoring engine instead of 8 separate reimplementations.
4. **Health bands**: Healthy ≥ 80, At Risk 50–79, Critical < 50. **Risk bands**: Critical ≥ 80, High ≥ 60, Moderate ≥ 30, Low < 30. Both are lower-bound-inclusive and fully configurable via `KnowledgeIntelligenceConfiguration.healthBands`/`riskBands`.
5. **Similarity thresholds**: Duplicate ≥ 0.95, Near-Duplicate ≥ 0.70, Related ≥ 0.50, else Distinct — validated at `KnowledgeIntelligenceConfiguration` construction time to be strictly decreasing (`duplicate > nearDuplicate > related`).
6. **Freshness decay is linear**: `score = clamp(100 * (1 - age / freshnessMaxAgeMs), 0, 100)`, default `freshnessMaxAgeMs` = 90 days.
7. **Registry buckets**: reports, snapshots, recommendations, insights — the four id-addressable artifact kinds a host needs to look back up after a run. Findings/scores are transient `PipelineContext` data, intentionally not separately registered (they are embedded inside `KnowledgeHealthReport`/`KnowledgeIntelligenceReport.sections` instead).
8. **Recommendation rules are independent, not mutually exclusive** — a single item can receive multiple recommendation types in one run. Merge/Consolidation are evaluated per-pair (from the similarity matrix); Archive/Update/Split/Improvement are evaluated per-item.
9. **Classification confidence** = `1 / matchedRuleCount`; the returned `category` is the first matching rule in registration order (extra caller-registered rules are evaluated before the 4 built-ins).
10. **Coverage is corpus-level, not item-level** — `KnowledgeHealthEngine.score()` accepts an optional per-call `coverageScore` parameter (default 100) rather than deriving a per-item coverage signal, since "coverage" fundamentally describes how well a taxonomy is covered across the whole corpus.
11. **`average([])` (empty-signal-list) convention** = 100, mirroring `KnowledgeHealthEngine.averageOverall([])`'s "an empty corpus has nothing wrong with it" convention, applied consistently in `GenerateRecommendationsStage`'s internal `average()` helper.
12. **`takeSnapshot()`/error-message extraction** use a couple of narrowly-scoped `/* v8 ignore next */`-annotated defensive branches (documented inline) for conditions that are provably unreachable given the pipeline's guaranteed sequential execution (e.g. `context.healthReport` is always populated after a successful `runIntelligence()` call) — kept as defense-in-depth rather than deleted, so future refactors that break the invariant fail loudly instead of silently.

## Known Technical Debt

- **O(n²) pairwise stages.** `AnalyzeSimilarityStage` and `AnalyzeRelationshipsStage` (and `KnowledgeRecommendationEngine`'s Merge/Consolidation pass) compare every item pair; this is fine for the corpus sizes a single intelligence run is expected to handle but will not scale to tens of thousands of items without a pre-filtering/bucketing strategy (out of scope for 005.7R).
- **No persistence layer.** `KnowledgeIntelligenceRegistry` is purely in-memory by design (spec requirement); a host needing durable reports/snapshots must persist them itself.
- **Cosine similarity is opt-in and unused by classification/duplicate-detection.** Only Jaccard drives `SimilarityClassification`; cosine is computed and reported alongside for callers that supply vectors, but no built-in capability currently switches its threshold logic to cosine. This was a deliberate scope decision (the spec's primary signal is tag/keyword-set based) but is worth revisiting if 005.7S introduces vector-heavy inputs.
- **Recommendation rule set is fixed.** The 6 recommendation types are generated by hardcoded thresholds (`LOW_USAGE_VIEW_COUNT`, `SPLIT_CONTENT_LENGTH`, `LOW_QUALITY_THRESHOLD`) rather than being part of `KnowledgeIntelligenceConfiguration`; a future task could promote these to configurable fields alongside the existing weight/threshold configuration.
