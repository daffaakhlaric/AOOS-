# Engineering Task 005.7I — Enterprise Knowledge Policy — Closing Report

## Summary

Delivered `@aos/knowledge-policy`, the layer responsible for defining, validating,
evaluating, and enforcing (at the metadata level only) every policy governing Knowledge
Assets inside AOS: policy lifecycle, policy rules, policy evaluation, policy resolution,
policy assignment, policy scope, policy conditions, policy actions, policy metadata,
policy registry, policy statistics, and policy audit metadata **only**. The package
implements no retrieval, no runtime, no synchronization, no versioning, no provider, no
embedding, no vector search, no AI, no LLM, no workflow runtime, no agent runtime, no
memory runtime, no business execution, no permission execution, and no access
enforcement — every algorithmic capability is deferred to one of the 10 interface-only
Extension Points.

This phase picked up from a prior partial run that had already verified/fixed the full
`src/` tree against the prompt (domain, contracts, errors, context, token, session,
state-machine, lifecycle, registry, resolver, validator, pipeline, middleware, factory,
events, metrics, health, monitoring, statistics, manager, policy façade, bootstrap,
config, `src/index.ts` barrel — all clean via `npx tsc -b` and `npx eslint`) but had
written zero `.spec.ts` test files. This phase wrote the entire test suite from scratch,
plus both documentation deliverables.

**403 tests passing** in `packages/knowledge-policy/test/` (target was 400+). Coverage:
**100% statements / 100% branches / 100% functions / 100% lines** — exceeding the
95/90/95/95 threshold on every dimension. Full workspace-wide verification
(`pnpm -w lint`, `pnpm -w build`, `pnpm -w typecheck`, `pnpm -w test`,
`pnpm -w format:check`) passed clean — 49/49 (lint/typecheck/test) and 27/27 (build)

## Architecture

```
KnowledgePolicy (policy/) — the public façade, composition root
  owns StateMachine + Pipeline + Middleware + Manager + Resolver + Permission
        │
        ▼
KnowledgePolicyPipeline (pipeline/) — 8 fixed stages
  Validation → Policy Resolution → Scope Resolution → Assignment Resolution →
  Metrics → Lifecycle → Audit → Logging
        │
        ▼
KnowledgePolicyStateMachine — the only code allowed to mutate KnowledgePolicyInstance.state
        │
        ▼
KnowledgePolicyResolver — resolve Policy/Rule/Scope/Assignment/Evaluation
        │
        ▼
KnowledgePolicyRegistry (7 generic buckets) + KnowledgePolicyManager (token-keyed ledger)
        │
        ▼
KnowledgePolicyMiddleware — policy.use() extensibility, separate from the Pipeline
        │
        ▼
contracts/ — 10 interface-only extension points, zero implementations
```

`KnowledgePolicy` is the single façade named in the prompt's Public API list (unlike
`@aos/knowledge-versioning`, whose prompt named both `KnowledgeVersioning` and
`KnowledgeVersion`). To avoid a same-name collision at the package barrel, the read-only
per-policy domain view returned by every operation is exported as `KnowledgePolicyRecord`
instead. `KnowledgePolicyManager` is a distinct, mid-level class — composing `registry` +
`session` + `statistics` + a private token-keyed execution ledger — mirroring
`@aos/knowledge-versioning`'s `KnowledgeVersioning`/`KnowledgeVersionManager` split, and
`@aos/knowledge-provider`'s equivalent pattern before it.

## Domain Model

`KnowledgePolicy`, `KnowledgePolicyRule`, `KnowledgePolicyScope`,
`KnowledgePolicyCondition`, `KnowledgePolicyAction`, `KnowledgePolicyAssignment`,
`KnowledgePolicyEvaluation`, `KnowledgePolicyMetadata`, `KnowledgePolicyConfiguration`,
`KnowledgePolicyPermission`, `KnowledgePolicyAudit` — the exact 11 aggregates named by the
prompt. `KnowledgePolicyRecord` (the concrete, read-only view class implementing the
`IKnowledgePolicy` contract) and `KnowledgePolicy` (the façade) are deliberately separate
names — see "Architecture" above.

## Policy Types

`KnowledgePolicyType` covers the exact 10 types named by the prompt: Access,
Classification, Retention, Lifecycle, Version, Synchronization, Visibility, Sharing,
Compliance, Custom.

## Rule Engine

`KnowledgePolicyRuleType` covers the exact 5 types named by the prompt: Allow, Deny,
Require, Optional, Conditional. Each `KnowledgePolicyRule` carries ordered lists of
condition ids and action ids, resolved only through the interface-only
`IKnowledgeConditionResolver`/`IKnowledgeActionResolver` Extension Points — this package
never itself evaluates a condition expression or executes an action. The one piece of
real, built-in rule evaluation is inside `KnowledgePolicy.evaluatePolicy()`: every
**enabled** rule with `ruleType: "deny"` produces a violation and forces the evaluation
result to `FAIL`; Allow/Require/Optional/Conditional rule types are recorded on the
policy but not evaluated in this phase (a judgment call — the prompt requires "Policy
Evaluation" as a domain concern to be modeled, not a full rule-engine execution semantics
to be implemented, which would cross into "business execution", explicitly excluded).

## Lifecycle

9 states, in the prompt's own order: Draft, Created, Validated, Active, Suspended,
Deprecated, Archived, Restored, Destroyed. Only `Destroyed` is hard-terminal (verified by
a dedicated test asserting every non-terminal state has a `Destroyed` edge). The
transition table connecting all 9 states — not specified edge-by-edge in the prompt — was
designed as: `Draft -> Created -> Validated -> Active` is the mainline authoring path;
`Active` fans out to `Suspended`/`Deprecated`/`Archived`/`Destroyed`;
`Suspended`/`Deprecated`/`Archived` can all `Restore`; a `Restored` policy may
re-`Activate` or `Archive`. `KnowledgePolicyLifecycle` is a read-only, query-only
companion (`states()`/`transitionsFrom()`/`isTerminal()`/`isSettled()`) to the imperative
`KnowledgePolicyStateMachine`, which is the only code in this package allowed to change
`KnowledgePolicyInstance.state`, appending one immutable history entry per legal
transition and stamping `activatedAt`/`destroyedAt` on the corresponding transitions.

## State Machine

`KnowledgePolicyStateMachine.transition()` throws `IllegalPolicyTransitionException` for
any edge not present in `KNOWLEDGE_POLICY_STATE_TRANSITIONS`, and is the sole point of
mutation for `KnowledgePolicyInstance.state` across the whole package — the Pipeline's
Lifecycle stage (stage 6) is its only caller. A dedicated parity test
(`test/state-machine/state-machine-extra.spec.ts`) walks every `(from, to)` pair across
all 9 states and asserts `canTransition()` agrees exactly with the domain transition
table, closing the possibility of the two ever silently drifting apart.

## Registry

One generic `KnowledgePolicyRegistry` class covers the exact 7 required buckets — Policy,
Rule, Scope, Assignment, Evaluation, Statistics, Session — as a
`Map<Bucket, Map<string, Identified>>`. Never scanned: every read is a direct Map lookup
by id through `KnowledgePolicyResolver`; `list()`/`count()` exist only for Metrics/Health
sampling. A bucket-isolation matrix test confirms all 7 buckets are independent (an
entry registered under one id in one bucket never collides with the same id in another
bucket).

## Resolver

`KnowledgePolicyResolver` implements the exact 5 dimensions named by the prompt: Policy,
Rule, Scope, Assignment, Evaluation — each with a throwing `resolveX()` (raising
`PolicyNotFoundException`) and a non-throwing `tryResolveX()`.

## Validation

A strict 10-stage validator, in the prompt's own order: Identity, Metadata, Scope, Rules,
Conditions, Assignment, Policy Type, Configuration, Dependency, Integrity. Every stage
runs and its issues are aggregated — no short-circuiting within the Validator itself
(verified directly by a test that supplies two independently-failing fields and asserts
both issues surface). The Integrity stage additionally re-checks lifecycle-transition
legality against the same `KNOWLEDGE_POLICY_STATE_TRANSITIONS` table the State Machine
enforces, so an illegal transition is caught in Validation (Pipeline stage 1) before the
Pipeline's Lifecycle stage (stage 6) ever calls the State Machine — a second,
independent check on the same invariant, matching the "belt and suspenders" layering
`@aos/knowledge-versioning`'s Validator/Pipeline established for its own Lifecycle stage.

## Pipeline

Exactly 8 fixed stages, per the prompt:

1. **Validation** — the real 10-stage `KnowledgePolicyValidator` → throws
   `PolicyValidationException` and records a failed Validation-Count sample.
2. **Policy Resolution** — no-op (see below).
3. **Scope Resolution** — no-op (see below).
4. **Assignment Resolution** — no-op (see below).
5. **Metrics** — records a Policy-Count sample.
6. **Lifecycle** — drives the State Machine to `targetState` (skipped when no
   `targetState` is supplied, or when it already equals the current state).
7. **Audit** — appends a `KnowledgePolicyAuditEntry` (fromState/toState/reason).
8. **Logging** — appends a `KnowledgePolicyLogEntry`.

Tracing (stamping a `KnowledgePolicyTrace` with an incrementing `runCount`) also runs
whenever `context.correlationId` is present — every context this package constructs
always has one.

A judgment call: stages 2–4 (Policy/Scope/Assignment Resolution) are named explicitly by
the prompt's fixed 8-stage list, but this package never dereferences a Policy/Scope/
Assignment id it doesn't already hold — every entity the Pipeline operates on arrives
fully materialized on the `KnowledgePolicyExecution` passed in (this package registers
Policies directly rather than loading them from an external store). Those three stages
are therefore present as explicit, source-commented pipeline positions — preserving the
exact 8-stage count and order the prompt requires — rather than as dead work performing
a resolution this package has no need to perform. `KnowledgePolicyResolver` remains a
fully real, independently tested component (`test/resolver/resolver.spec.ts`) available
for a caller that does need id-based resolution outside the Pipeline.

## Metrics

The exact 7 fields named by the prompt: Policy Count, Active Policy Count, Assignment
Count, Evaluation Count, Validation Count, Archive Count, Restore Count — plus an
internal `validationFailureCount` used only to derive domain Health, never exposed as an
8th "named" metric (matching the `validationFailureCount` precedent in
`@aos/knowledge-versioning`).

## Monitoring

`KnowledgePolicyMonitoring.sample()` — exact name `KnowledgePolicyMonitoring`, per the
prompt's Public API list — combines a Metrics snapshot and a Health report into one
`KnowledgePolicyDashboard`, deriving domain health from the
`validationCount`/`validationFailureCount` ratio (healthy at 0% failures, warning below
10%, degraded below 50%, unavailable at or above 50%, unknown with zero samples).

## Statistics

`KnowledgePolicyStatistics` maintains its own private
`Map<KnowledgePolicyType, KnowledgePolicyStatisticsSnapshot>` (createdCount/
activatedCount/lastActivityAt) — separate from the Registry's `STATISTICS` bucket, which
exists for callers registering their own externally computed statistics providers, per
the pattern already established by `@aos/knowledge-versioning`/`@aos/knowledge-provider`.

## Known Limitations

- **All 10 named extension-point contracts have zero implementations** — by design. No
  real compliance check, no real condition/action resolution, no real conflict
  resolution, and no real durable storage exists anywhere in this package;
  `IKnowledgePolicyEvaluator`/`IKnowledgePolicyProvider`/`IKnowledgeComplianceProvider`/
  `IKnowledgeConditionResolver`/`IKnowledgeActionResolver`/`IKnowledgeScopeResolver`/
  `IKnowledgePolicyStorage`/`IKnowledgePolicyPublisher`/`IKnowledgePolicyAuditProvider`/
  `IKnowledgePolicyConflictResolver` are invoked only when a caller supplies one via
  `KnowledgePolicyConfig` — this package never does so itself.
- **`evaluatePolicy()` only checks enabled Deny rules** — see "Rule Engine" above; real
  condition-driven Allow/Require/Optional/Conditional evaluation is deferred to
  `IKnowledgePolicyEvaluator`.
- **`KnowledgePolicyResolver` ships zero registered Policies** — a caller must
  `createPolicy()` at least once before any `resolve*()` call can return results.
- **`KnowledgePolicySession` is a separate access-window ledger from the Policy
  Lifecycle State Machine** — the two are not automatically kept in sync by this
  package.
- **`KnowledgePolicyPermission` is metadata-driven only** — "deny always wins,
  permissive by default when no grant matches" is enforced consistently on every gated
  Policy Operation, but this is explicitly not the "Access Enforcement" or "Permission
  Execution" the prompt excludes: no real identity/authentication integration exists.
- **`assignPolicy()`/`unassignPolicy()` do not validate `targetType`/`targetId` against
  any external inventory** — an assignment can be created against a `targetId` that
  doesn't correspond to any real Knowledge Base entity; this package has no visibility
  into that inventory by design (see Dependency Rules).

## Non-obvious design/judgment calls made this phase

1. Pipeline stages 2–4 (Policy/Scope/Assignment Resolution) are structural no-ops — see
   "Pipeline" above — rather than invented resolution logic against a store this package
   doesn't own.
2. `evaluatePolicy()`'s built-in evaluation only inspects enabled Deny rules — the
   minimal real behavior that stays inside "Policy Evaluation... no business execution".
3. The Lifecycle transition table's exact edges (fan-out from `Active`, universal
   `Restore` from `Suspended`/`Deprecated`/`Archived`, `Restored` re-fanning to
   `Active`/`Archived`) were designed from the prompt's state list and the "Illegal
   transitions MUST throw" requirement, since the prompt names states but not edges.
4. Test fixtures (`test/helpers/*.ts`, written in the prior phase) default
   `policyId`/`tenantId`/`workspaceId` to the same values across
   `metadataFixture()`/`contextFixture()`/`configurationFixture()`, so a bare
   `createInput()` in the façade tests passes full Identity/Scope/Configuration
   validation without per-test boilerplate — deviating fields are overridden explicitly
   per test.
5. `test/contracts/contracts.spec.ts` exercises every one of the 10 Extension Point
   interfaces (plus the 4 future-readiness contracts) with a minimal inline fake
   implementation — these interfaces have no runtime code of their own (excluded from
   coverage via `i-*.ts` in `vitest.config.ts`), so this is a compile-time-shape/contract
   test, not a coverage-driving test; it exists to prove every declared contract is
   actually satisfiable by a real implementation with the exact declared signature.
6. Two tests originally written against slightly-wrong assumptions about the Health
   status boundary (`failureRatio < 0.1` for "warning", not `<=`) and about
   Pipeline's no-transition path (targeting the current `DRAFT` state, which the
   Integrity validator correctly rejects since `DRAFT -> DRAFT` isn't a listed
   transition) were corrected during the test-writing pass rather than weakening the
   source `src/` logic to fit an incorrect test expectation.
