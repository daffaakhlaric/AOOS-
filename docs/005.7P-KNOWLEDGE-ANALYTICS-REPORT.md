# 005.7P — Enterprise Knowledge Analytics — Engineering Report

Status: **Complete**. Package: `packages/knowledge-analytics` (`@aos/knowledge-analytics`).

## Architecture Overview

`@aos/knowledge-analytics` is a standalone, pure in-memory analytics/reporting engine over metrics
data supplied by callers. It does not read from a database, does not make network calls, does not
persist to the filesystem, and — per the 005.7P constraint (identical to 005.7O
`@aos/knowledge-graph`) — imports **zero** other `@aos/*` packages at runtime.

The package follows Domain Driven Design / Clean Architecture layering:

- **`value-objects/`** — `KnowledgeMetricSample` (one recorded data point: name, value, timestamp,
  tags), `KnowledgeMetricDefinition` (a metric's static shape: id, category, unit, description),
  `KnowledgeAnalyticsConfiguration` (percentile thresholds, dashboard cadence metadata, trend
  bucket size, history retention limit). All frozen at construction; "updates" return new
  instances.
- **`entities/`** — `KnowledgeAnalyticsSummary`, an identity-bearing rollup of this package's own
  operational footprint.
- **`reports/`** — `KnowledgeAnalyticsReport` and `KnowledgeDashboardSnapshot`, the two
  identity-bearing report/snapshot aggregates.
- **`analytics/`** — the 11 domain-specific analytics services, each recording caller-supplied
  events and computing derived statistics from them via a shared `BaseKnowledgeAnalyticsService`
  (per-metric sample storage, registry publish, tag aggregation) and `KnowledgeMetricCalculator`
  (the actual math).
- **`metrics/`** — `KnowledgeMetricCalculator` (average/sum/min/max/rate/percentile, all real
  computations) and `KnowledgeMetricRegistry` (id-keyed `Map` registry of metric
  definitions/current values).
- **`builders/`** — `KnowledgeAnalyticsReportBuilder`, a genuine Builder-pattern class.
- **`registry/`** — `KnowledgeReportRegistry`, an id-keyed store of generated reports.
- **`factories/`** — `KnowledgeMetricSampleFactory`, `KnowledgeDashboardSnapshotFactory`,
  `KnowledgeAnalyticsReportFactory`, `KnowledgeAnalyticsConfigurationFactory`.
- **`pipeline/`** — `KnowledgeAnalyticsPipeline` plus its 6 stage classes, implementing the exact
  flow from the specification.
- **`services/`** — `KnowledgeAnalyticsEngine` (top-level facade/orchestrator implementing
  `IKnowledgeAnalyticsModule`) and `KnowledgeAnalyticsStatistics` (internal operational counters).
- **`events/`** — `KnowledgeAnalyticsEventType` (6 dotted event names), `InMemoryEventPublisher`,
  `NoOpEventPublisher`.
- **`errors/`** — `KnowledgeAnalyticsException` base + 5 concrete subclasses
  (`MetricNotFoundException`, `InvalidReportTypeException`, `InvalidSampleException`,
  `PipelineStageFailureException`, `ReportNotFoundException`).
- **`contracts/`** — `IKnowledgeAnalyticsEventPublisher`, `IKnowledgeAnalyticsModule`,
  `IExternalMetricsSink` (optional, never required).
- **`types/` / `utils/`** — `KnowledgeMetricName` (30 values), `KnowledgeMetricCategory` (11
  values), `KnowledgeReportType` (10 values), `KnowledgeMetricUnit` (8 values), plus pure helpers
  (`calculatePercentile`, `calculateAverage`/`Sum`/`Min`/`Max`/`Rate`, `bucketByInterval`,
  `calculateTrendSlope`, `calculatePeriodOverPeriodDelta`, `Clock`/`createFixedClock`/
  `createSteppingClock`, `generateId`).

### 10 report types — modeling approach

One flexible `KnowledgeAnalyticsReport` entity parameterized by `KnowledgeReportType`, assembled by
`KnowledgeAnalyticsReportBuilder`:

- **8 single-domain types** (Usage, Performance, Graph, Quality, Embedding, Trend, Cost,
  Recommendation) each require their one matching section (supplied via the corresponding
  `.withX(...)` builder method) and `.build()` throws `InvalidReportTypeException` if that section
  was never supplied — so each of these 8 reports' content is genuinely different, sourced from a
  single analytics service's current state.
- **2 composite types** (Summary, DashboardSnapshot) include every section supplied to the builder
  so far, with none individually required.

The pipeline's "Generate Reports" stage (4) produces 9 reports per run: the Summary plus all 8
single-domain types. `DashboardSnapshot` — the 10th type — is instead produced by the pipeline's
dedicated stage 5 ("Generate Dashboard Snapshot") as its own `KnowledgeDashboardSnapshot` entity
(built from the numeric KPI map via `KnowledgeDashboardSnapshotFactory`), matching the
specification's explicit separation of stages 4 and 5. `KnowledgeReportType.DashboardSnapshot`
remains available through the builder too, for a host that wants an all-sections "report" view of
the same moment.

### Percentile / rate correctness testing approach

- **Percentile**: linear interpolation between closest ranks
  (`index = p/100 * (n-1)`, then interpolate between `sorted[floor(index)]` and
  `sorted[ceil(index)]`) — the same method NumPy's default `percentile()` and Excel's
  `PERCENTILE.INC` use. Hand-verified against a 1..100 fixture (`test/helpers/fixtures.ts`):
  P50 = 50.5, P95 = 95.05, P99 = 99.01, independently computed by hand and cross-checked at the
  `calculatePercentile` unit level, the `KnowledgeMetricCalculator` level, each relevant analytics
  service (`KnowledgeQueryAnalytics`, `KnowledgePerformanceAnalytics`,
  `KnowledgeEmbeddingAnalytics`), and end-to-end through `KnowledgeAnalyticsEngine.runPipeline()`.
  A second, smaller 5-item fixture (`[10,20,30,40,50]` → P95 = 48, P99 = 49.6) is used for
  additional hand-verified assertions with simpler arithmetic.
- **Rate**: exact known hit/miss and success/failure splits (e.g. 80/20, 7/3, 9/1, 37/13) recorded
  through `KnowledgeSearchAnalytics`/`KnowledgeQualityAnalytics`/`KnowledgeRetrievalAnalytics` and
  asserted to equal the exact expected fraction, plus the invariant `hitRate + missRate === 1` and
  `successRate + failureRate === 1` over the same recorded population.
- **Trend**: a 5-point, 1000ms-bucketed dataset (`[10,20,30,40,50]` at
  `t=0,500,1000,1500,2000`, producing 3 buckets averaging `15, 35, 50`) is hand-verified via OLS to
  slope exactly `17.5` and period-over-period delta exactly `15/35`, tested at the pure-function
  level (`src/utils/time-bucket.ts`), the `KnowledgeTrendAnalytics` level, and end-to-end through
  the engine.

## Design Decisions

See the README's "Design Decisions" section for the full numbered list (10 items) — reproduced
here for completeness, plus process-level judgment calls specific to this report:

1. Single flexible `KnowledgeAnalyticsReport` entity + `KnowledgeReportType` enum, not 10 distinct
   report classes.
2. `KnowledgeDashboardSnapshot` is its own entity/factory, matching the pipeline's stage 4/5 split.
3. Percentile method: linear interpolation between closest ranks (documented, hand-verified).
4. Trend computation: OLS slope + period-over-period delta over time-bucketed history.
5. Rate of 0/0 defined as exactly `0`, never `NaN`/`Infinity`.
6. `KnowledgeMetricCategory` (11, "which service owns this") kept distinct from `KnowledgeMetricUnit`
   (8, "what physical quantity").
7. `KnowledgeAnalyticsStatistics` (operational counters) kept distinct from domain `Metrics`
   (computed analytics values) — same split as every completed sibling package.
8. `KnowledgeQualityAnalytics` owns Success/Failure Rate (reassigned from a naive Search-adjacent
   reading of the spec) since these read as generic outcome indicators, not search-specific ones;
   `KnowledgeSearchAnalytics` scoped to Search Count/Hit Rate/Miss Rate.
9. `KnowledgePerformanceAnalytics` owns Retrieval Time and generalizes it via
   `recordOperation(name, durationMs)`, since the spec places Retrieval Time separately from
   Retrieval Count/Cache Hit/Cache Miss (owned by `KnowledgeRetrievalAnalytics`).
10. `dashboardRefreshCadenceMs` on `KnowledgeAnalyticsConfiguration` is advisory metadata only — no
    real timer/scheduler exists in this in-memory, standalone package.

### Additional non-obvious judgment calls

11. **Folder structure interpretation.** The specification's raw folder listing runs
    `src/{contracts,...,utils}` then `tests/` then `README.md` then
    `docs/005.7P-KNOWLEDGE-ANALYTICS-REPORT.md` all seemingly nested under `src/` — read literally,
    this would put tests and docs inside `src/`. Per the task's explicit instruction, this was
    treated as an informal flattened listing of the package's real top-level contents, not literal
    nesting, matching the convention every completed sibling package (most recently
    `@aos/knowledge-graph`) actually uses: package root has `src/` (with exactly the listed
    subfolders), a **top-level `test/`** folder (singular — matching every sibling's convention,
    not the spec's plural "tests/"), a package-local `README.md`, and the Engineering Report at the
    **monorepo root**'s `docs/005.7P-KNOWLEDGE-ANALYTICS-REPORT.md` (this file) rather than
    `packages/knowledge-analytics/docs/...`.
12. **`KnowledgeMetricRegistry` located under `metrics/`, not `registry/`.** The specification
    lists both a `metrics/` and a `registry/` folder without specifying which houses
    `KnowledgeMetricRegistry`. It was placed under `metrics/` alongside `KnowledgeMetricCalculator`
    (the two are used together constantly — every analytics service records into both), with
    `registry/` reserved for the report-lookup registry (`KnowledgeReportRegistry`), which the
    prompt implies but does not name explicitly ("any other id-keyed lookup registries needed").
13. **`KnowledgeMetricUnit` placed in `types/common.ts` rather than `value-objects/`.** It is a
    pure enum with no runtime behavior of its own (a classification tag attached to
    `KnowledgeMetricDefinition`), so it lives with the other pure type definitions
    (`KnowledgeMetricName`, `KnowledgeMetricCategory`, `KnowledgeReportType`) rather than being
    promoted to its own value-object file.
14. **`BaseKnowledgeAnalyticsService` is an internal abstract class**, not one of the 21 named
    components, introduced to avoid reimplementing per-metric sample storage, registry
    publishing, and tag aggregation 11 times. Every one of the 11 analytics services extends it;
    its own dedicated spec files (`base-knowledge-analytics-service.spec.ts` and its `-more`
    companion) verify its behavior directly, in addition to being exercised indirectly through
    every analytics-service spec file.
15. **`KnowledgeAnalyticsEngine.runPipeline()` regenerates all 9 domain-and-summary reports on
    every call**, rather than accepting a subset-selection parameter. This keeps the pipeline's
    "Generate Reports" stage simple and matches the specification's flow diagram (no conditional
    branching implied), at the cost of always producing every report type even if a host only
    wants one — a host that wants a single report type outside a full pipeline run can use
    `KnowledgeAnalyticsReportBuilder` directly instead.
16. **Test doubling via `createSteppingClock`/`createQueueClock` in specs that exercise the
    engine.** Because `KnowledgeAnalyticsEngine` pre-registers every metric, every `recordX(...)`
    call ticks the injected clock twice (once for the sample's own timestamp, once for the
    registry's `updatedAt` when `publish()` syncs it). Tests that need exact, hand-verified
    timestamps through the _engine_ (rather than through a bare analytics service, which has no
    registry and therefore only ticks the clock once per call) use a small local queue-clock
    helper (`test/integration/cost-and-trend-correctness.spec.ts`) rather than a naive fixed-step
    clock, to control sample timestamps precisely regardless of how many extra ticks `publish()`
    consumes in between. This is a deliberate, documented test-authoring pattern, not a production
    bug — `publish()`'s extra clock read is intentional (the registry's `updatedAt` should reflect
    the actual moment of publication).

## Testing Strategy

- **87 spec files**, **731 tests**, zero skipped, zero flaky (no reliance on real wall-clock
  timing anywhere — every test that needs "time" uses `createFixedClock`, `createSteppingClock`,
  or a local queue clock; no `setTimeout`/`sleep`/timing races).
- **Fixtures first** (`test/helpers/fixtures.ts`): hand-verified statistical fixtures — a 1..100
  array with pre-computed sum/average/P50/P95/P99, a 5-item latency array with pre-computed
  P95/P99, an 80/20 hit/miss boolean sequence — used across dozens of spec files so every
  percentile/rate assertion traces back to one independently-verified source of truth.
- **Module-by-module unit coverage**: every one of the 21 core components, every error class,
  every event-publisher implementation, every utility function, every factory, and every pipeline
  stage has its own dedicated `.spec.ts`, typically paired with a `-more.spec.ts` companion
  covering edge cases (empty inputs, boundary percentiles, zero denominators, history-retention
  eviction, tie-breaking, etc.).
- **Integration coverage** (`test/integration/`): 8 files driving real, multi-service scenarios
  through `KnowledgeAnalyticsEngine` — full pipeline runs, report-content differentiation across
  all 9 generated report types, the exact 30-metric catalog distribution (parametrized via
  `it.each`), KPI-map shape correctness (numeric vs. non-numeric metrics), dashboard-snapshot
  point-in-time correctness, statistics/event correctness across multiple runs, and explicit error
  paths.
- **Parametrized (`it.each`) tests** are used deliberately for exhaustive-but-uniform assertions —
  e.g. every one of the 30 metric names is checked for registry presence and category correctness,
  every one of the 9 generated reports is checked for registry round-tripping, every one of the 11
  analytics services is checked for uniform `sampleCount()`/`reset()`/`summary()` behavior — which
  both maximizes genuine coverage and keeps the test suite honest about uniform contracts across
  parallel components.
- **No stale-template mistake (005.7L lesson).** Every spec file in this package was written fresh
  against this package's actual public API; none were copied from `@aos/knowledge-graph` or any
  other sibling's test suite. The one true bug this testing strategy caught during authoring — a
  trend-correctness integration test computing the wrong expected slope because
  `KnowledgeAnalyticsEngine`'s default `trendBucketSizeMs` (1 hour) didn't match the test's
  intended 1-second buckets, and separately because `publish()`'s extra clock tick doubled the
  effective step size of a naive stepping clock — was root-caused and fixed by inspecting the
  actual runtime behavior (a debug script printing real bucket boundaries) rather than adjusting
  the assertion to match incorrect output.

## Known Technical Debt

- **No conditional report generation.** `runPipeline()` always builds all 9 domain+summary reports
  every run; a host that only cares about one report type still pays the cost of building all of
  them. Acceptable at current scale (in-memory, synchronous, no I/O), but would need addressing if
  a future host runs the pipeline at very high frequency with very large recorded-sample volumes.
- **Trend bucket anchoring is per-series-first-sample, not wall-clock-aligned.** Two independently
  started trend series will not share bucket boundaries even if fed the same wall-clock-timestamped
  data. A future revision could accept an explicit epoch anchor in
  `KnowledgeAnalyticsConfiguration` for cross-series alignment.
- **`KnowledgeMetricUnit`/`KnowledgeMetricCategory` are not currently used to drive any
  unit-conversion or category-filtered query API** — they are descriptive metadata only. A future
  package could add `KnowledgeMetricRegistry.listByCategory(category)` or similar.
- **No maximum-cardinality guard on tag-based aggregation** (`aggregateByTag`,
  `knowledgeUsageByKnowledge`, `providerUsageByProvider`, cost-by-provider breakdowns). A caller
  recording millions of distinct `knowledgeId`/`providerId` tag values would grow those breakdown
  maps unboundedly; `historyRetentionLimit` bounds sample count per metric name but not distinct
  tag-value cardinality.
