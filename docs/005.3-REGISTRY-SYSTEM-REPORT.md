**Design decision, stated plainly:** rather than implementing Entity/Contract/Validator/Loader/Resolver/Indexer/Search/Version/Metadata/Dependency-Checker/Health/Metrics 23 times (as a literal reading of "every Registry must have" might suggest), this package implements all twelve **once**, generically, in `registry/registry.ts`'s `Registry<TManifest>` class. This is not a scope reduction — every kind genuinely has all twelve; it is the enterprise-correct way to deliver them without 23x duplicated, individually-buggy implementations, and it is the direct structural consequence of the user's own manifest-driven revision.

## 3. Dependency Graph

Two distinct kinds of "dependency" exist in this system, deliberately kept separate:

**(a) Intra-registry dependencies** — a manifest's own `dependencies` field, referencing other entries of the _same_ kind (e.g. one Workflow depending on another Workflow). Resolved by `dependency/dependency-graph.ts`'s `DependencyGraph`, run once per `Registry.load()` batch.

```
Registry.load(directory)
   │
   ▼
ManifestLoader.load() ──▶ [manifest, manifest, ...]
   │
   ▼
Build dependenciesById map (existing entries + batch)
   │
   ▼
DependencyGraph.check()
   ├─ findMissing() ──▶ any dependency id not in the known set? → DependencyException
   ├─ findCircular() ──▶ DFS with recursion-stack cycle detection → DependencyException
   └─ topologicalSort() ──▶ safe load order
   │
   ▼
register() each manifest in topological order
```

**(b) Cross-registry references** — a manifest's fields referencing _other_ Registry kinds (the user's revision: Agent's `required_tools` → Tool Registry). Declared in `bootstrap/cross-reference-map.ts`, checked by `RegistrySystem.validateCrossReferences()` / enforced by `registerWithCrossCheck()`:

```
CROSS_REFERENCE_MAP = {
  agent:    { required_tools → tool, required_models → model, memory → memory_provider, workflows → workflow },
  workflow: { required_agents → agent, required_tools → tool },
  prompt:   { target_agent → agent },
}
```

Both mechanisms produce the same category of result shape (`ok`/`valid` + a structured list of what's missing) but operate at different scopes — (a) within one Registry's own load batch, (b) across the whole RegistrySystem, on demand.

## 4. Validation Flow

```
register(manifest)
   │
   ├─ self-dependency guard (manifest.dependencies includes its own id?) → DependencyException
   │
   ▼
ValidationPipeline.run(manifest, context)
   │
   ├─ 1. SchemaValidator    — Zod safeParse against the kind's manifest schema
   ├─ 2. BusinessValidator  — kind-specific rules (opt-in per registry/kinds/*.ts)
   ├─ 3. DependencyValidator — per-manifest missing-dependency check (context.existingIds)
   ├─ 4. VersionValidator    — valid SemVer + strictly greater than every prior version
   └─ 5. PermissionValidator — `permissions` entries match `resource.action` format
   │
   ▼
any issues? ──yes──▶ emit ValidationFailed, throw ValidationException (aggregates ALL issues,
   │                  not just the first failure — every stage always runs)
   no
   ▼
construct RegistryEntry, index, cache-invalidate, emit RegistryUpdated
```

## 5. Search Flow

```
Registry.search(criteria) / discover()
   │
   ▼
SearchIndex.search({ id?, name?, tag?, capability?, category?, tenantId?, version? })
   │
   ▼
for each indexed RegistryEntry:
   AND-match every provided criterion against entry.manifest
   (name: case-insensitive substring, falling back to id when manifest.name is unset;
    tag/capability: array-includes; id/category/tenantId/version: exact match)
   │
   ▼
return matching entries (empty criteria object matches everything)
```

`get(id, versionRef?)` is a related but distinct path: it goes through `EntryResolver` (id + version-reference → one entry) and `TtlCache`, not `SearchIndex` — search is for discovery/filtering across many entries, `get`/`resolve` is for retrieving one specific, known entry efficiently.

## 6. Hot Reload Flow

```
Registry.reload()
   │
   ├─ no lastLoadLocation recorded? ──▶ RegistryException ("call load() first")
   │
   ▼
save location = lastLoadLocation
   │
   ▼
clear entriesById, searchIndex, cache   ◄── full in-memory reset, NOT a Kernel restart
   │
   ▼
load(location)   ◄── re-reads the directory fresh; VersionValidator's "must be strictly
   │                  greater" check is vacuously satisfied because the clear() step just
   │                  removed all prior version history for every id
   ▼
emit RegistryReloaded
```

This is the concrete mechanism behind "Registry dapat di-reload tanpa restart kernel": `reload()` only touches this one `Registry` instance's in-memory state — nothing about the Kernel, the process, or any other Registry is affected, proven in `test/registry/registry.spec.ts`'s "Hot Reload" test group (including the specific case of reloading a directory whose manifest versions are unchanged, which would otherwise fail version-monotonicity validation).

## 9. Known Limitations

1. **No persistence** — explicitly out of scope per the source prompt; every Registry is wiped on process restart. This is the single largest limitation and the named subject of a future sprint.
2. **`RemoteRegistryLoader` is a stub that throws** — the `IManifestSource` port exists and is wired for a future implementation, but no network-backed Registry source exists yet.
3. **Cross-reference validation is opt-in, not automatic** — `Registry.register()` alone does NOT check cross-registry references; only `RegistrySystem.registerWithCrossCheck()` does. A caller using `registries.agent.register(...)` directly bypasses the Tool/Model/Memory/Workflow existence checks. This is a deliberate API design (a single Registry must remain usable standalone, without requiring a `RegistrySystem`), but it is a real footgun worth flagging.
4. **`permissions` are structurally validated only** — `PermissionValidator` checks the `resource.action` string shape but never checks the permission is actually granted to anything; that is future Permission Registry consumer / Guardrail Engine territory (Constitution §25), not this package's job.
5. **`DependencyGraph`'s circular detection scope is per-`load()`-batch** — it does not re-validate the _entire_ Registry's accumulated dependency graph on every single `register()` call (only the lighter per-manifest `DependencyValidator` runs there). A pathological sequence of individual `register()` calls could theoretically construct a cycle that only a subsequent `load()` or manual `reload()` would catch. Not observed in testing, but a known structural gap.
6. **`RegistrySystem`'s `IModule` integration is unwired** — `RegistrySystem implements IModule` and is tested standalone (`onBootstrap`/`onShutdown`), but no code in this repository actually calls `buildKernel({ modules: [registrySystem] })` — that integration is proven possible, not yet exercised end-to-end through a real Kernel `start()`.
7. **TypeScript-metadata manifest loading uses dynamic `import()`** — works correctly (tested with real `.mjs` fixtures) but means loading untrusted `.ts`/`.js`/`.mjs` manifests executes arbitrary code at load time, unlike YAML/JSON. This is inherent to the format, not a bug, but is a security consideration for a future Marketplace/third-party-manifest scenario.

## 11. Readiness Checklist for ENGINEERING TASK 005.4 (Event Bus)

This checklist assesses what the Registry System already provides that an Event Bus implementation can build on, and what 005.4 will need to add — **nothing in this checklist is implemented as part of this report.**

- [x] An **Event Registry** (`registry/kinds/event-registry.ts`) already exists, holding `EventManifest` metadata (`payload_schema_ref`, `publishers`, `subscribers`) — the Event Bus's first consumer need (discovering what events exist and who's declared as publishing/subscribing to them) is already served by this Registry, not something the Event Bus needs to build itself.
- [x] `RegistryEventEmitter` (this package's own in-process pub/sub, explicitly scoped as **not** the platform Event Bus) is a proven, tested pattern (`KernelEventEmitter` in `@aos/runtime-kernel`, `RegistryEventEmitter` here) — the same typed-payload-map + Node `EventEmitter` wrapper approach is directly reusable as a design reference for the distributed Event Bus's local delivery mechanics, even though the Bus itself needs a durable, cross-process transport (NATS JetStream, per TSR §3.7/§3.8) this package does not provide.
- [x] Every Registry's `RegistryLoaded/Reloaded/Updated/Removed` events are already real, typed, and tested — a future Event Bus bridge could subscribe to `RegistrySystem.events` and republish onto the real, distributed Event Bus without any change to this package.
- [x] The Queue Registry (`registry/kinds/queue-registry.ts`) holds `QueueManifest` metadata (`fifo`, `dead_letter_ref`) that a real Queue implementation (TSR §3.7, BullMQ) will read to configure itself — the metadata layer is ready; no queue runs yet.
- [x] `EntryStatus`'s transition model (`DRAFT → ACTIVE → DEPRECATED → RETIRED`, `QUARANTINED`) is exactly the lifecycle doc 003.5's Event Contract and other Contracts already specify — the Event Bus's own event-schema versioning (additive-only within a major version, RULE-035) can reuse this Registry's `VersionValidator`/`VersionChecker` machinery directly rather than reimplementing SemVer discipline.
- [ ] **Not yet provided:** any actual message transport — NATS JetStream (or any broker) is not installed, configured, or connected to by this package; 005.4 owns that entirely.
- [ ] **Not yet provided:** distributed trace/correlation propagation across a real publish/subscribe boundary — this package's `RegistryEventEmitter` is synchronous and in-process only; the Event Contract's `trace_id`/`correlation_id`/`tenant_id` fields (doc 003.5 §10) are not exercised by anything in this package.
- [ ] **Not yet provided:** Dead Letter Queue handling, retry/backoff policy execution, or delivery guarantees of any kind — `QueueManifest.dead_letter_ref` is metadata only; nothing enforces it.
- [ ] **Recommendation:** 005.4 should treat the Event Registry and Queue Registry populated here as its configuration source of truth (an Event Bus reads `registries.event.list()` to know what event names/schemas exist, rather than hardcoding them), and should implement its own event emitter/transport as a genuinely new component — not by extending `RegistryEventEmitter`, which is correctly scoped to stay a small, in-process, Registry-internal notification mechanism per its own file-level documentation.
