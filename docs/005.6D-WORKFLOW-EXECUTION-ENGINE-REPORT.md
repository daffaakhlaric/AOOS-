# ENGINEERING TASK 005.6D — Enterprise Workflow Execution Engine — Closing Report

Package: `packages/workflow-execution` (`@aos/workflow-execution`)
Source prompt archived at: `docs/PROMPT-005.6D-WORKFLOW-EXECUTION-ENGINE.md`

Scope actually implemented: the `WorkflowExecutionEngine` that orchestrates one Workflow
Execution end-to-end by driving `@aos/workflow-runtime` (Workflow Instance lifecycle,
005.6B) and `@aos/node-runtime` (Node Instance lifecycle, 005.6C) together, walking a
Workflow Definition's graph Node-by-Node — Execution Token/Context/Session/Cursor/Graph/
State Machine/Result/History/Metadata/Statistics, a Transition Engine (7 outcomes), Retry
(4 strategies), Timeout (4 scopes, config only), Cancellation, 12 named Execution Events, a
6-stage extensible Middleware pipeline, Metrics/Health/Monitoring, and a 5-stage Execution
Validation pipeline. **No Agent/Capability/Tool/Connector/Knowledge/Memory Runtime,
Planner, Reasoner, Reflection, Simulation Runtime, AI Gateway, or Model Router** was
implemented, imported, or stubbed anywhere in this package — Capability execution is
defined as `ICapabilityExecutor`, an interface only (implementation belongs to 005.9).
Checkpoint (`ICheckpointStore`) and Compensation (`ICompensationManager`) are likewise
interface-only, per the source prompt.

## 1. Architecture

```
executeWorkflow(input)
        │
        ▼
workflowRuntime.createInstance() ──▶ WorkflowDefinition + WorkflowInstance (@aos/workflow-runtime)
        │
        ▼
createExecutionToken() + createExecutionContext() + buildExecutionGraph() + createExecutionCursor()
        │
        ▼
runOperation("initialize") → runOperation("start")     (this package's OWN ExecutionState machine)
workflowRuntime.initialize() → workflowRuntime.start()  (the WorkflowInstance's OWN state machine)
publish WORKFLOW_STARTED
        │
        ▼
runGraph()  ── frontier-based Node-by-Node walk ──────────────────────────┐
  for each Node in the current frontier:                                  │
    executeNodeWithRetry(nodeId) → executeNodeOnce(nodeId)                │
      nodeRuntime.createFromDefinition() → .initialize() → .start()       │
      (CAPABILITY Node → executeCapabilityNode() → ICapabilityExecutor,   │
       if configured — else a business failure, never a crash)           │
      nodeRuntime.complete() / .fail()                                    │
    transitionEngine.resolve(outcome) ──▶ next Node id(s) / loop-back      │
────────────────────────────────────────────────────────────────────────────┘
        │
        ▼
runOperation("complete" | "fail") → workflowRuntime.complete()/.fail()
publish WORKFLOW_COMPLETED | WORKFLOW_FAILED
        │
        ▼
ExecutionResult { success, nodesVisited, error?, completedAt }
```

`WorkflowExecutionEngine` (`engine/workflow-execution-engine.ts`) is the composition root
and this package's **entire public API**, per the prompt's "Export ONLY
WorkflowExecutionEngine, ExecutionToken, ExecutionContext, ExecutionResult, ExecutionState,
Interfaces. Hide all internal services." `src/index.ts` exports `WorkflowExecutionEngine`,
its Kernel Module wrapper `WorkflowExecutionSystem`, and only the data-contract surface
(types/enums/errors/factory functions/interfaces) required to actually call
`WorkflowExecutionEngine`'s methods and interpret their results — every concrete internal
service (`ExecutionValidationPipeline` and its 5 validators, all 6 Middleware classes,
`ExecutionStateMachine`, `TransitionEngine`, `RetryCoordinator`,
`ExecutionMetricsCollector`, `ExecutionHealth`, `ExecutionMonitor`,
`ExecutionCoordinator`) stays unexported. This tension — and why it's an unavoidable
minimum rather than a loophole — is documented directly in `src/index.ts`'s own comment,
mirroring the precedent set in 005.6B/005.6C.

The Engine tracks **three intentionally-parallel state-tracking layers** for one Workflow
Execution: this package's own `ExecutionSession`/`ExecutionState` machine, the underlying
`@aos/workflow-runtime` `WorkflowInstance`'s own state machine (addressed via an internal
`workflowRuntimeTokens: Map<workflowExecutionId, string>`, since `@aos/workflow-runtime`'s
own `ExecutionToken` is a different, opaque string type), and each `@aos/node-runtime`
`NodeInstance`'s own state machine (addressed by `NodeExecution.instance.id`). None of
these duplicate the others' internal logic — the Engine only ever calls into their public
APIs (`workflowRuntime.initialize()/.start()/.pause()/.resume()/.cancel()/.complete()/
.fail()`, `nodeRuntime.createFromDefinition()/.initialize()/.start()/.complete()/.fail()`).

## 3. Execution Flow

Workflow Start → Load Definition (`workflowRuntime.createInstance()`) → Create Token
(`createExecutionToken()`) → Create Context (`createExecutionContext()`) → Resolve Graph
(`buildExecutionGraph()`) → Resolve First Node (`graph.startNodeId`) → Validate Node
(`ValidationMiddleware` running `ExecutionValidationPipeline` over the built graph) →
Execute Node (`nodeRuntime.start()`/`.complete()`/`.fail()`, or `ICapabilityExecutor` for a
CAPABILITY Node) → Wait Result → Resolve Transition (`TransitionEngine.resolve()`) → Next
Node → Workflow Complete (`workflowRuntime.complete()`/`.fail()`).

**10 Execution Modes** (`context/execution-mode.ts`): Sequential, Parallel, Conditional,
Loop, Wait, Event Driven, Scheduled, Manual Approval, Compensation, Retry. Only Sequential
(the default), Parallel (fan-out via `PARALLEL`/`MERGE`-kind Transitions), and Loop
(synthetic `LOOP`-kind edges, bounded by `config.maxLoopIterations`) drive any actual
structural difference in `runGraph()` today — the remaining 7 are declared and threaded
through `ExecutionContext.mode` but have no dedicated runtime behavior yet (see Known
Limitations).

**Transition Engine** resolves 7 outcomes (`transition/transition-outcome.ts`): `success`,
`failure`, `timeout`, `cancelled`, `retry`, `manual`. A `failure`/`timeout` outcome with no
matching Transition kind is a normal **business failure** — `TransitionEngine.resolve()`
returns an empty `nextNodeIds` array rather than throwing, and `runGraph()` turns that into
`ExecutionResult{success:false}`. A `success`/`manual` outcome reaching a non-End Node with
no outgoing structural edge is a genuine Workflow Definition defect and does throw
`TransitionResolutionException` — the business-vs-system-failure distinction is applied
consistently throughout.

## 7. Performance Notes

- `runGraph()`'s frontier walk is bounded by
  `maxSteps = graph.nodeIds.length * maxLoopIterations * 4 + 10`, throwing
  `WorkflowExecutionException` if exceeded — a deliberate circuit breaker against a
  Workflow Definition whose cycle detection was somehow bypassed upstream.
- No Retry delay is ever actually awaited (`computeDelayMs()` is called but its result is
  never passed to a `setTimeout`/sleep) — `executeNodeWithRetry()`'s loop is fully
  synchronous, keeping test execution fast and deterministic at the cost of not honoring
  real backoff timing in production today (see Known Limitations).
- "Parallel" fan-out Nodes execute sequentially within one `frontier` round rather than
  concurrently — `Promise.all()` was deliberately not used so that Node execution order
  stays deterministic for the Cursor's `visitedNodes`/`executionPath` bookkeeping; a future
  revision introducing real concurrency will need to redesign Cursor mutation to be
  concurrency-safe.

## 8. Technical Debt

- **"Expose ONLY WorkflowExecutionEngine..." required the same judgment call documented in
  005.6C.** A strictly literal reading would export nothing else, but TypeScript consumers
  need types for the Engine's method parameters/return values, error classes to catch, the
  event enum to subscribe on, and the Middleware interface to write a custom stage for
  `.use()`. `src/index.ts` documents this tension inline.
- **The dual-token design (`ExecutionToken` vs. `@aos/workflow-runtime`'s own
  `ExecutionToken` string) is necessary but adds a bookkeeping map
  (`workflowRuntimeTokens`) that must stay in sync with the Coordinator** — if a future
  revision ever needs to persist/restore Sessions, this map needs to be persisted
  alongside them.
- **No polling for cancellation/pause between Node steps** — see Known Limitations below;
  this is the most significant orchestration gap relative to a fully-hardened Execution
  Engine.
- **`ExecutionMode` values `Conditional`/`Wait`/`Event Driven`/`Scheduled`/`Manual
Approval`/`Compensation`/`Retry` are declared but have no dedicated `runGraph()`
  behavior** beyond what naturally falls out of Transition-kind resolution (e.g. `manual`
  outcome) — a future revision may need per-mode branches in `runGraph()` itself.

## 9. Known Limitations

- **No Expression Evaluator exists in any AOS package to date** — `CONDITION`-kind
  Transitions and `Manual` (Manual Approval) outcomes are both resolved
  structurally/unconditionally, consistent with the same limitation noted in 005.6A/B/C.
- **A Loop Node backed by a real `@aos/node-runtime` Node Instance cannot execute
  end-to-end today** — `@aos/node-runtime`'s built-in `LOOP` manifest requires a
  `config.condition` string (`z.string().min(1)`), but `@aos/node-runtime`'s own
  `derive-config-from-definition-node.ts` (not modifiable in this Engineering Task) yields
  an empty config for Loop Nodes, since a WDL Loop Node's `loopCondition` is a structured
  `Expression` object with no string equivalent. `executeWorkflow()` surfaces this as a
  thrown `NodeValidationException` originating from `@aos/node-runtime`. This package's own
  `ExecutionGraph`/`TransitionEngine`/`ExecutionCursor` loop-iteration logic is fully
  implemented and unit-tested independent of this cross-package gap.
- **Cancelling an Execution mid-flight does not stop the in-flight Node step, and can
  desynchronize the underlying `WorkflowInstance`'s state** — `executeWorkflow()` does not
  poll for cancellation between Node steps. If `cancel()` is called while a Node is
  running, the Node still runs to completion, and since the underlying
  `@aos/workflow-runtime` `WorkflowInstance` was genuinely transitioned to `CANCELLED`, the
  Engine's own later `workflowRuntime.complete()` call on it fails with an
  `IllegalTransitionException` from that package — a real, observable inconsistency
  surfaced as a thrown error, not silently swallowed. `pause()`/`resume()`/`timeout()` do
  not have this specific interaction since they don't leave the underlying
  `WorkflowInstance` in a state incompatible with eventual completion.
- **"Parallel" Execution Mode is simulated, not concurrent** — see Performance Notes.
- **No real Retry delay is ever awaited** — see Performance Notes.
- **Checkpoint/Compensation remain interface-only** — `ICheckpointStore` and
  `ICompensationManager` have zero implementations; no Session is ever persisted or
  restored, and nothing drives a Session from `FAILED` to `COMPENSATING` automatically.
- **Idle/Execution-level Timeout enforcement does not exist** — `ExecutionTimeouts`
  (`workflowTimeoutMs`/`nodeTimeoutMs`/`executionTimeoutMs`/`idleTimeoutMs`) is validated
  by `TimeoutValidator` if configured, but nothing in `runGraph()` actually measures
  elapsed time against these values and calls `engine.timeout()` — a caller must invoke
  `timeout()` explicitly today.
