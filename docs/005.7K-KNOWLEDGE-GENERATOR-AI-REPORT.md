# Engineering Task 005.7K — Enterprise Knowledge Generator AI — Closing Report

## Summary

Delivered `@aos/knowledge-generator`, the layer responsible for orchestrating
AI-assisted generation of enterprise knowledge assets: knowledge generation, generation
sessions, generation jobs, generation requests, generation results (metadata only),
generation metadata, prompt references, context references, output metadata, generation
policies, generation statistics, generation audit **only**. The package implements no
embeddings, no vector search, no quality scoring, no validation-as-a-service, no
recommendation, and — critically — no LLM provider logic of any kind: it never calls the
OpenAI SDK, Claude SDK, Gemini SDK, Ollama SDK, or any provider SDK; it never constructs a
real prompt string; it never implements inference. Every real generation action is
delegated through `IKnowledgeGenerationProvider`/`IKnowledgePromptProvider`/
`IKnowledgeContextProvider` interfaces this package never implements.

Built from scratch this phase: the entire `src/` tree (23 folders, 74 source files), the
entire `test/` tree (28 spec files + 3 fixture helpers), and both documentation
deliverables.

## Architecture

```
KnowledgeGenerator (generator/) — the public façade, composition root
  owns StateMachine + Pipeline + Middleware + Manager + Resolver + Factory + providers map
        │
        ▼
KnowledgeGeneratorPipeline (pipeline/) — 10 fixed stages
  Validation → Context Resolution → Prompt Resolution → Policy Resolution →
  Provider Resolution → Metadata → Metrics → Lifecycle → Audit → Logging
        │
        ▼
KnowledgeGeneratorStateMachine — the only code allowed to mutate KnowledgeGeneration.state
        │
        ▼
KnowledgeGeneratorResolver — resolve Generation/Prompt/Context/Policy/Session
        │
        ▼
KnowledgeGeneratorRegistry (8 generic buckets) + KnowledgeGeneratorManager
                                                  (token-keyed ledger)
        │
        ▼
KnowledgeGeneratorMiddleware — generator.use() extensibility, separate from the Pipeline
        │
        ▼
contracts/ — 12 interface-only extension points + 3 future-readiness contracts,
             zero implementations, zero real generation logic anywhere in this package
```

`KnowledgeGenerator` is the single façade named in the prompt's Public API list. To avoid
a same-name collision at the package barrel, the read-only per-generation domain view
returned by every operation is exported as `KnowledgeGenerationRecord` instead —
mirroring the `KnowledgeMarketplace`/`KnowledgeMarketplaceRecord` split established by
`@aos/knowledge-marketplace`. `KnowledgeGeneratorManager` is a distinct, mid-level class —
composing `registry` + `session` + `statistics` + a private token-keyed execution
ledger — mirroring `@aos/knowledge-marketplace`'s equivalent split before it.

## Domain Model

`KnowledgeGeneration`, `KnowledgeGenerationJob`, `KnowledgeGenerationSession`,
`KnowledgeGenerationRequest`, `KnowledgeGenerationResult`, `KnowledgeGenerationContext`,
`KnowledgeGenerationPromptReference`, `KnowledgeGenerationMetadata`,
`KnowledgeGenerationConfiguration`, `KnowledgeGenerationPolicy`, `KnowledgeGenerationAudit`,
`KnowledgeGenerationStatistics` — the exact 12 aggregates named by the prompt, each backed
by a Zod schema (`domain/knowledge-generation-*.ts`).

**Result-vs-content modeling (judgment call):** `KnowledgeGenerationResult` models
metadata ABOUT a result — `{ resultId, generationId, providerId, providerType,
completedAt, contentLocation?, summary?, outputMetadata }` — never the generated content
itself, per the prompt's explicit direction ("Generation Results" is scoped as metadata
in "Scope", never as generated artifacts). `contentLocation` is a pointer string (e.g. a
storage key a caller-supplied `IKnowledgeGenerationStorage` would resolve); this package
never reads or writes the underlying content.

**Prompt-vs-text modeling (judgment call):** `KnowledgeGenerationPromptReference` is
`{ promptId, promptVersion, namespace, description? }` — a pointer into a prompt owned by
`@aos/prompt-runtime`, never the prompt text. The "AI Scope Boundary" section explicitly
forbids "create prompts", so the Pipeline's Prompt Resolution stage only ever resolves
and attaches this reference — it never dereferences it into text.

**Context-vs-Generator-Context naming (judgment call):** the prompt's own "Public API"
list names `KnowledgeGeneratorContext` while its "Domain Model" list names
`KnowledgeGenerationContext` — two genuinely distinct concepts. This report keeps that
distinction explicit: `KnowledgeGeneratorContext` (`context/`) is the caller-scoped
operational context every Generation Operation runs under (token, tenantId,
correlationId, ...); `KnowledgeGenerationContext` (`domain/`) is a registered grounding
reference (e.g. a knowledge-engine namespace/collection id) a Request may point at.

## Generation Flow

`createGeneration()` (→ Draft) → `queue()` (→ Queued) → `prepare()` (→ Preparing, resolves
Context/Prompt/Policy/Provider through the 10-stage Pipeline, `requireProvider: true`) →
`start()` (→ Generating, invokes a registered `IKnowledgeGenerationProvider.generate()`
if one is registered, `requireProvider: true`) → `review()` (→ Reviewing) → `complete()`
(→ Completed, records/finalizes the `KnowledgeGenerationResult` and a real average
duration metric) — or `fail()`/`cancel()` at any earlier point, then `archive()` →
`destroy()`. Every operation is one atomic Pipeline call: validate → drive State Machine
→ record metadata → update statistics → publish the matching event → return the updated
`KnowledgeGenerationRecord`.

## Provider Abstraction

Providers are never resolved from the Registry — there is no Provider Registry bucket in
the spec's 8-bucket list. They live in a private
`Map<KnowledgeGenerationProviderType, IKnowledgeGenerationProvider>` on the façade,
populated via `KnowledgeGeneratorConfig.providers` at construction or
`registerProvider()`/`hasProvider()` afterward. The Pipeline's Provider Resolution stage
(Stage 5) only checks availability by Provider Type; it never invokes the Provider.
`start()` is the sole call site in the entire package that ever calls
`provider.generate(request)`, and only when one is actually registered for the Request's
declared `providerType` — absent one, `start()` still transitions the Generation to
`Generating` without recording a `KnowledgeGenerationResult`, and a caller supplies the
result explicitly via `complete({ token, result })` instead.

## Prompt Resolution

`KnowledgeGeneratorResolver.resolvePrompt()`/`tryResolvePrompt()` is a direct `PROMPT`
Registry bucket lookup by `promptId` — never a collection scan. The Pipeline's Prompt
Resolution stage (Stage 3) resolves and attaches the reference and records Prompt Usage
metrics; an unresolvable declared reference throws `GenerationPromptException`. The
12-stage Validator's Stage 5 (Prompt) independently checks the same resolvability flag
before the Pipeline stage ever runs, so a malformed Request fails fast at Stage 1
(Validation) rather than partway through the Pipeline — see "Validation" below for how
this affects test design for Stages 2-5's own exception paths.

## Context Resolution

`KnowledgeGeneratorResolver.resolveContext()`/`tryResolveContext()` is a direct `CONTEXT`
Registry bucket lookup by `contextId`. The Pipeline's Context Resolution stage (Stage 2)
resolves and attaches the `KnowledgeGenerationContext` reference and records Context Usage
metrics; an unresolvable declared reference throws `GenerationContextException`. No
embeddings, no vector search, no retrieval — metadata presence only, matching "No
embeddings. No vector search." in the prompt's "Scope" section.

## Lifecycle

10 states, in the prompt's own order: Draft, Queued, Preparing, Generating, Reviewing,
Completed, Cancelled, Failed, Archived, Destroyed. Only `Destroyed` is hard-terminal.

**Transition-table design (judgment call — the prompt lists the 10 states but not the
edges between them):**

```
Draft      -> Queued, Cancelled, Destroyed
Queued     -> Preparing, Cancelled, Failed, Destroyed
Preparing  -> Generating, Cancelled, Failed, Destroyed
Generating -> Reviewing, Cancelled, Failed, Destroyed
Reviewing  -> Completed, Cancelled, Failed, Destroyed
Completed  -> Archived, Destroyed
Cancelled  -> Archived, Destroyed
Failed     -> Archived, Destroyed
Archived   -> Destroyed
Destroyed  -> (none — terminal)
```

`Draft -> Queued -> Preparing -> Generating -> Reviewing -> Completed` is the mainline
path; every non-settled state can additionally be `Cancelled` or `Destroyed` directly;
`Queued`/`Preparing`/`Generating`/`Reviewing` can fail into `Failed`; `Completed`/
`Cancelled`/`Failed` all fan into `Archived`; every state (including `Archived`) has an
edge into the hard-terminal `Destroyed`. A dedicated test proves every one of the 10
states is reachable from `Draft` via BFS over this table (both at the raw
`KNOWLEDGE_GENERATION_STATE_TRANSITIONS` level and again through the façade's actual
operations), and a full 10×10 legality matrix test (100 assertions:
26 legal edges + 64 illegal non-edges + 10 self-transition rejections) locks the table
down.

The façade adds a `review()` operation (`Generating -> Reviewing`) — not explicitly named
in the prompt's operation list but required to reach `Reviewing` before `complete()`
(`Reviewing -> Completed`) can run, since `Generating -> Completed` is intentionally NOT
a direct edge (Reviewing is meant as a real checkpoint, not a pass-through state). This
mirrors how `@aos/knowledge-marketplace` added setup helpers beyond its own named
Marketplace Operations list.

`KnowledgeGeneratorLifecycle` (`states()`/`transitionsFrom()`/`isTerminal()`/
`isSettled()`) is a read-only, query-only companion to the imperative
`KnowledgeGeneratorStateMachine`, which is the only code allowed to change
`KnowledgeGeneration.state` — every legal transition appends one immutable history entry
and stamps `startedAt` (entering Generating) / `completedAt` (entering Completed).
`KnowledgeGeneratorStateMachine.transition()` throws
`IllegalGenerationTransitionException` for any edge not present in the table.

## Resolver

`KnowledgeGeneratorResolver` — a single class implementing the exact 5 dimensions named
by the prompt (Generation Resolver, Prompt Resolver, Context Resolver, Policy Resolver,
Session Resolver) as 5 method pairs, matching the sibling-package convention of
implementing multiple named "Resolvers" as one class with per-domain resolve methods —

## Validation

A strict 12-stage validator, in the prompt's own order: Identity, Metadata, Request,
Context, Prompt, Policy, Provider, Configuration, Lifecycle, Dependency, Integrity, Audit.
Every stage runs and its issues are aggregated — no short-circuiting within the
Validator, matching every prior AOS Knowledge package's convention. The Dependency stage
(10) enforces real cross-field rules: every non-`Custom` Generation Mode requires a
declared Prompt Reference; a resolved Policy with `requireApproval` requires a
Configuration record. The Integrity stage (11) cross-checks `tenantId` consistency
between Context and Metadata, and `providerType` consistency between Request and a
resolved Configuration.

**Validator "Audit" stage (12) vs. Pipeline "Audit" stage (9) — documented distinction,
mirroring 005.7F's Configuration-stage/Validator-stage overlap:** the Validator's Audit
stage is a **pre-flight** field check — it confirms `request.requestedBy` (the audit
actor) and `request.createdAt` are present/well-formed BEFORE an operation runs. The
Pipeline's Audit stage is a **post-flight** side effect — it APPENDS the actual
`KnowledgeGenerationAudit` entry (with `fromState`/`toState`/`occurredAt`, registered into
the `AUDIT` Registry bucket) AFTER the operation completes. The two never duplicate each
other's work; both are required for the "12 Validator stages" / "10 Pipeline stages"
counts to be exact per the spec.

**Testing implication:** because the Validator's Context/Prompt/Policy/Provider stages
(4/5/6/7) independently check the same resolvability facts the Pipeline's Context/Prompt/
Policy/Provider Resolution stages (2/3/4/5) compute, a malformed Request normally fails
fast at Pipeline Stage 1 (Validation) before ever reaching Stages 2-5's own resolution
code. `test/pipeline/pipeline.spec.ts` isolates Stages 2-5's own exception paths
(`GenerationContextException`/`GenerationPromptException`/`GenerationPolicyException`/
`GenerationProviderException`) using a permissive stub Validator, so both layers'
independent logic are separately covered.

## Pipeline

Exactly 10 fixed stages, per the prompt: Validation, Context Resolution, Prompt
Resolution, Policy Resolution, Provider Resolution, Metadata, Metrics, Lifecycle, Audit,
Logging — implemented in `pipeline/knowledge-generator-pipeline.ts`, see "Validation"
above for Stage 1 and "Lifecycle" above for Stage 8. Provider availability is only
required in the Validator/Pipeline when the calling Generation Operation flags
`requireProvider: true` (`prepare()`/`start()`); earlier operations (`createGeneration()`/
`queue()`/`cancel()`/`fail()`/...) never require a Provider to be registered.

`KnowledgeGeneratorStatistics` maintains its own private

## Known Limitations

- **All 12 named extension-point contracts have zero implementations** — by design. No
  real inference, embeddings, vector search, memory, or workflow execution exists
  anywhere in this package; they are invoked only when a caller supplies one via
  `KnowledgeGeneratorConfig`/`registerProvider()` — this package never does so itself.
- **`review()` is a bare Lifecycle transition** — unlike `@aos/knowledge-marketplace`'s
  `review()` (which records an approve/reject decision as a reason string), this
  package's `review()` records no decision payload; a caller wanting richer review
  metadata attaches it to `KnowledgeGenerationMetadata` before calling `review()`.
- **`KnowledgeGeneratorResolver` ships zero registered Prompts/Contexts/Policies** — a
  caller must `registerPrompt()`/`registerContext()`/`registerPolicy()` at least once
  before any `resolve*()` call for that dimension can succeed.
- **`KnowledgeGeneratorSession` is a separate access-window ledger from the Generation
  Lifecycle State Machine** — the two are not automatically kept in sync; closing a
  Session does not cancel or otherwise affect the underlying Generation's state.
- **No cost tracking, no streaming, no caching wired by default** —
  `IKnowledgeGenerationCostProvider`/`IKnowledgeGenerationStreamingProvider`/
  `IKnowledgeGenerationCache` exist purely as extension points.
- **`destroy()` is idempotent, not error-on-repeat** — calling `destroy()` a second time
  on an already-`Destroyed` Generation is treated as a Lifecycle no-op (since
  `targetState === currentState` skips the State Machine stage) rather than throwing,
  matching the same-target-state convention every other Generation Operation follows.

## Technical Debt

- The 12-stage Validator and the 10-stage Pipeline independently compute the same
  Context/Prompt/Policy/Provider resolvability facts (see "Testing implication" above) —
  functionally correct and matches the sibling-package convention, but is duplicated
  work on every Pipeline run. A future optimization could thread the Validator's
  precomputed facts into the Pipeline's resolution stages instead of resolving twice.
- `KnowledgeGenerationConfiguration` has no dedicated Registry bucket or Resolver
  dimension (the 8-bucket/5-resolver spec has no slot for it) — Configuration records
  live only inline on the execution envelope, attached via `complete()`/future facade
  extension rather than through `registerConfiguration()`. A future phase wanting
  Configuration reuse across Generations would need to add a bucket, which is an
  additive, non-breaking change.
- `KnowledgeGenerationJob` scheduling is metadata-only (`createJob`/`completeJob`/
  `failJob`) — there is no real queueing/execution timing, matching
  `IKnowledgeGenerationScheduler`'s extension-point-only status.

## Non-obvious design/judgment calls (full list)

1. **Dependency-name mapping** — the prompt's "Allowed Dependencies" names
   `@aos/kernel`/`@aos/shared`/`@aos/events`/`@aos/knowledge-engine`/
   `@aos/knowledge-policy`/`@aos/knowledge-versioning`/`@aos/prompt-runtime`. The real
   workspace packages are `@aos/runtime-kernel` (not `@aos/kernel`) and `@aos/common`
   (not `@aos/shared`) and `@aos/event-bus` (not `@aos/events`) — the same mapping every
   prior sibling package used. `@aos/prompt-runtime` does **not** exist as a workspace
   package (`ls packages/` confirms no `prompt-runtime` directory) — it is NOT declared
   as a dependency in `package.json`, per the task's explicit instruction to omit
   non-existent packages. `@aos/knowledge-engine`/`@aos/knowledge-policy`/
   `@aos/knowledge-versioning` all exist but, like every sibling package, this package
   imports zero concrete classes from any of them at runtime — interface-references-only
   in spirit, matching how the actual `package.json` `dependencies` list only ends up
   containing `@aos/common`, `@aos/errors`, `@aos/event-bus`, `@aos/runtime-kernel`, and
   `zod`.
2. **Event-name mapping** — `GenerationCreated`/`GenerationQueued`/`GenerationStarted`/
   `GenerationCompleted`/`GenerationFailed`/`GenerationCancelled`/`GenerationArchived`/
   `GenerationDestroyed` map onto dotted event-bus type strings
   `knowledge.generation.created`/`.queued`/`.started`/`.completed`/`.failed`/
   `.cancelled`/`.archived`/`.destroyed`, matching the `knowledge.marketplace.*` pattern
   `@aos/knowledge-marketplace` established.
3. **Result-vs-content modeling** — see "Domain Model" above.
4. **Lifecycle transition-table design** — see "Lifecycle" above, including the addition
   of a `review()` facade operation not explicitly named in the prompt's operation list.
5. **Resolver shape** — one `KnowledgeGeneratorResolver` class with 5 method-pairs rather
   than 5 separate classes, matching every prior sibling package's convention for
   multi-named "Resolvers".
6. **Future Readiness interpretation** — exactly 3 additional single-method interfaces
   (`IKnowledgeQualityEngineGenerator`, `IKnowledgeValidatorAiGenerator`,
   `IEmbeddingManagerGenerator`) for 005.7L/005.7M/005.7N respectively, mirroring how
   `@aos/knowledge-marketplace` added exactly 3 for its own Future Readiness section — no
   speculative stub modules/folders beyond these 3 interfaces.
7. **Token prefix chosen** — `kgen_` (Knowledge GENerator), confirmed collision-free
   against every existing prefix in the codebase (`ptok_`, `stok_`, `ksrc_`, `kver_`,
   `kpol_`, `kmkt_` — verified via `packages/knowledge-marketplace/src/token/`, the most
   recently completed sibling).
8. **Validator "Audit" stage vs. Pipeline "Audit" stage distinction** — see "Validation"
   above; documented explicitly to avoid the two being mistaken for duplicated scope,
   mirroring 005.7F's Configuration-stage/Validator-stage overlap precedent.
9. **Provider Resolution's conditional strictness** — Provider availability is only
   validated/enforced when the calling Generation Operation flags `requireProvider: true`
   (`prepare()`/`start()`); every earlier operation (`createGeneration()`/`queue()`/
   `cancel()`/`fail()`/`archive()`/`destroy()`) never requires a Provider to be
   registered, since a Generation can legitimately be drafted, queued, or even
   cancelled/failed before any Provider Type decision needs to be resolvable. This is a
   judgment call not explicit in the prompt, made to keep early lifecycle operations
   independent of provider-registration order in typical caller code.
10. **`KnowledgeGenerationConfiguration` has no Registry bucket/Resolver dimension** —
    the prompt's 8-bucket/5-resolver lists have no slot for Configuration; it is modeled
    as an inline field on the execution envelope instead (see "Technical Debt" above).
11. **Session domain-record keying** — `KnowledgeGenerationSession` Registry entries are
    keyed by the owning Generation's `token` (not a freestanding `sessionId`) so
    `openSession()`/`closeSession()`/`cancelSession()`/`expireSession()`/
    `renewSession()` remain O(1) Map lookups without a secondary token→sessionId index —
    a judgment call trading a slightly unconventional `id` field (equal to the
    Generation's token rather than the Session's own `sessionId`) for guaranteed
    "never scan collections" compliance.
