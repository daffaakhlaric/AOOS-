# ENGINEERING TASK 005.7E — Enterprise Knowledge Synchronization — Closing Report

Package: `packages/knowledge-synchronization` (`@aos/knowledge-synchronization`)
Source prompt archived at: `docs/PROMPT-005.7E-KNOWLEDGE-SYNCHRONIZATION.md`

Scope actually implemented: the vendor-neutral Enterprise Synchronization Orchestrator
bridging the Enterprise Knowledge Platform to external knowledge sources — a 13-state
Synchronization Lifecycle, a 10-stage Pipeline (Validation → Policy → Permission →
Provider Resolution → Connection Validation → Change Detection → Synchronization →
Commit → Metrics → Events), a token/id-addressed Registry (8 buckets), a Manager
orchestrating Registry + Session + Statistics + Scheduler, a Provider Resolver
("resolve providers only, no provider implementation"), a Policy engine combining real
Policy evaluation with dispatch-only Conflict Resolution, an in-memory Scheduler job
ledger (Cron/Interval/One Time/Manual Trigger/Event Trigger), a Koa-style Middleware
Pipeline (`sync.use()`), a 10-event `KnowledgeSynchronizationEvents` publisher, Metrics/
Health/Monitoring, 12 interface-only extension points, and the
`KnowledgeSynchronization`/`KnowledgeSynchronizer` public façade (plus its
`KnowledgeSynchronizationSystem` Kernel Module wrapper). **No OAuth, no API clients, no
Connector SDK, no LLM, no AI, no retrieval, no indexing, and no memory** was implemented,
imported, or stubbed anywhere in this package — it only orchestrates the synchronization
job lifecycle over `@aos/knowledge-engine`/`@aos/knowledge-indexing`/
`@aos/knowledge-retrieval` (read-only references, never written to), dispatching to
caller-supplied Provider/Conflict Resolver/Change Detector implementations.

## 2. Synchronization Flow

A caller obtains a `KnowledgeSynchronization` instance (constructed from a real
`KnowledgeEngine` + `KnowledgeIndexing` + `KnowledgeRetrieval` trio), registers at least
one `IKnowledgeSynchronizationProvider`, then calls
`synchronization.synchronize(job, context, conflictStrategy?)`:

1. `KnowledgeSynchronizer.synchronize()` records `recordSynchronizationStarted()`,
   creates a `KnowledgeSynchronizationExecution` in the `Created` state, registers it in
   `KnowledgeSynchronizationManager`, and publishes `knowledge.sync.created`.
2. It transitions to `Queued` and publishes `knowledge.sync.started`, then calls
   `KnowledgeSynchronizationPipeline.run()` — one atomic call covering all 10 Pipeline
   stages.
3. On success, it rapidly transitions `Preparing` → `Connecting` → `Synchronizing` →
   `Validating` → `Committing` → `Completed` (6 history entries recording that those
   stages occurred inside the single Pipeline call), stamps `changes`/`changeCount`,
   records `recordSynchronizationCompleted()` and a Statistics entry, and publishes
   `knowledge.sync.completed`.
4. On failure, it transitions to `Failed`, records `recordSynchronizationFailed()`, and
   publishes `knowledge.sync.failed`. If an optional `IKnowledgeSynchronizationRetryStrategy`
   reports `shouldRetry(execution, error)`, it also transitions to `Retrying`
   (incrementing `instance.retryCount`), records `recordRetry()`, and publishes
   `knowledge.sync.retry`.

`synchronization.retry(token)` re-runs the Pipeline for a `Retrying` Execution, replaying
its stored Job/Context and transitioning `Preparing` → `Connecting` → `Synchronizing` →
`Validating` → `Committing` → `Completed` on success, or back through the same failure/
retry handling on error. `synchronization.cancel(token)`/`destroy(token)` transition to
`Cancelled`/`Destroyed` — `destroy()` additionally removes the Execution from the
Manager's ledger, since `Destroyed` is the package's one hard-terminal state.

## 3. Domain Model

- **`KnowledgeSynchronizationState`** (13 values): Created, Queued, Preparing,
  Connecting, Synchronizing, Validating, Committing, Completed, Failed, Cancelled,
  Retrying, Expired, Destroyed. Only `Destroyed` has zero outgoing transitions —
  Completed/Failed/Cancelled/Expired are "settled" (`KNOWLEDGE_SYNCHRONIZATION_SETTLED_STATES`)
  but can still transition to `Destroyed`, following the same "one hard-terminal Destroy
  step" precedent as `@aos/knowledge-runtime`/`@aos/knowledge-indexing` rather than
  `@aos/knowledge-retrieval`'s all-4-terminal model (which has no `Destroyed` state at
  all). `Queued` legally transitions to `Failed` directly — Validation runs as the first
  Pipeline stage while the Execution is still `Queued` (state transitions to `Preparing`
  only happen after the atomic Pipeline call succeeds), so a Validation failure must be
  representable from `Queued`.
- **`KnowledgeSynchronizationJobType`** (10 values): Manual/Scheduled/Incremental/Full/
  Version/Metadata/Permission/Policy/Relationship/Template Sync.
- **`KnowledgeSynchronizationMode`** (7 values): Manual, Scheduled, Incremental, Full,
  Real-Time, Webhook, Streaming — the last 3 are "interface only": no Pipeline/Scheduler
  logic in this package ever drives them end-to-end; a caller who registers a mode-aware
  Provider must implement that behavior itself.
- **`KnowledgeChangeType`** (12 values): Added, Updated, Deleted, Moved, Renamed,
  Metadata/Permission/Policy/Relationship/Version/Template Changed, Content Hash Changed.
- **`KnowledgeSynchronizationProviderType`** (9 values): Document, Storage, Repository,
  CMS, Database, API, File System, Knowledge Service, Future Provider.
- **`KnowledgeConflictResolutionStrategy`** (5 values): Last Write Wins, Version Based,
  Manual Approval, Merge, Custom — a tagging enum, not 5 separate interfaces.
- **`KnowledgeSynchronizationScheduleType`** (5 values): Cron, Interval, One Time, Manual
  Trigger, Event Trigger.
- **`KnowledgeSynchronizationJob`** (Zod schema): id, type, mode, providerId, sourceId,
  tenantId, workspaceId?, collection?, namespace?, createdAt.
- **`KnowledgeChangeRecord`** (Zod schema): id, changeType, assetId?, path?,
  previousPath?, contentHash?, detectedAt, metadata — "Only metadata detection. No
  content parsing." — never carries parsed file content.

## 4. Synchronization Context

`KnowledgeSynchronizationContext` (Zod schema) carries the exact prompt field list:
synchronizationId, token (ExecutionToken), tenantId, workspaceId?, organizationId?,
departmentId?, providerId, sourceId, sourceType, collection (KnowledgeCollection)?,
namespace?, version?, policy?, permission?, environment?, metadata, traceId?,
correlationId. `createKnowledgeSynchronizationContext()` generates `synchronizationId`/
`token`/`correlationId` when omitted. `KnowledgeSynchronizationToken` uses an `stok_`
prefix (distinct from `@aos/knowledge-retrieval`'s `rtok_`).

## 5. Pipeline

10 stages, in fixed order, run inside one atomic `KnowledgeSynchronizationPipeline.run()`
call:

1. **Validation** — `KnowledgeSynchronizationValidator` (12 stages, see §8); throws
   `SynchronizationValidationException`; publishes `knowledge.sync.validation.failed`.
2. **Policy** — `KnowledgeSynchronizationPolicy.evaluate(job)` against every enabled,
   scope-matching registered Policy's `allowedModes`/`deniedModes`; throws
   `SynchronizationPolicyViolationException` on any violation.
3. **Permission** — optional `ISynchronizationPermissionChecker`, permissive by default;
   throws `SynchronizationPermissionDeniedException` when it rejects.
4. **Provider Resolution** — `KnowledgeSynchronizationResolver.resolveProvider()`;
   throws `ProviderNotFoundException` when unregistered; publishes
   `knowledge.sync.provider.resolved`.
5. **Connection Validation** — calls the resolved Provider's optional
   `validateConnection()`; throws `ConnectionValidationException` when it reports
   failure; permissive (valid) when the Provider declares no such method.
6. **Change Detection** — `KnowledgeSynchronizationResolver.detectChanges()`, delegating
   to an optional injected `IKnowledgeSynchronizationChangeDetector` (permissive `[]`
   when unconfigured); records `recordSynchronizationMode()`.
7. **Synchronization (Conflict Resolution)** — `KnowledgeSynchronizationPolicy.resolveConflicts()`
   dispatches to a registered `IKnowledgeSynchronizationConflictResolver` when a
   `conflictStrategy` is requested; no-op pass-through otherwise; throws
   `ConflictResolutionNotSupportedException` when the requested strategy is
   unregistered.
8. **Commit** — calls an optional configured `IKnowledgeSynchronizationCommitter` with
   `{ job, context, changes }`; permissive no-op when unconfigured.
9. **Metrics** — `recordProviderUsage()`, `recordTenantUsage()`, and
   `recordWorkspaceUsage()` when `context.workspaceId` is set.
10. **Events** — lifecycle events (Started/Completed/Failed/Cancelled/Retry) are
    published by the outer `KnowledgeSynchronizer`, which owns the State Machine
    transitions they describe; the Pipeline itself already published the two
    stage-scoped events it can fully attribute (`VALIDATION_FAILED` in stage 1,
    `PROVIDER_RESOLVED` in stage 4).

## 6. Registry

One generic `KnowledgeSynchronizationRegistry` class covering all 8 buckets the source
prompt requires: Synchronization Job, Provider, Policy, Schedule, Session, Statistics,
Health, Lifecycle — `register()`/`replace()`/`get()`/`require()`/`remove()`/`list()`/
`count()`, throwing `DuplicateSynchronizationEntryException`/`SynchronizationNotFoundException`
as appropriate. Unlike `@aos/knowledge-retrieval`'s Registry (whose source prompt
explicitly omits "Statistics" from its bucket list), this prompt's own Registry section
explicitly lists Statistics/Health/Lifecycle as things to register — interpreted as
generic id-keyed extension-registration buckets (e.g. externally supplied Health
checkers or Lifecycle hooks a caller wants addressable by id), while
`KnowledgeSynchronizationStatistics` itself still owns its own private counter map for
this package's own internal per-Mode bookkeeping (documented in `statistics/`).

## 7. Scheduler

"Support Cron, Interval, One Time, Manual Trigger, Event Trigger (interface only)."
`KnowledgeSynchronizationScheduler` maintains an in-memory ledger of Schedule entries
(`id`, `scheduleType`, `jobId`, opaque `cronExpression`/`intervalMs`/`runAt` config,
`status: pending|triggered|cancelled`, timestamps) — `schedule()`/`trigger()`/`cancel()`/
`get()`/`require()`/`list(jobId?)`. It never computes actual next-run times or performs
the sync work it schedules — a caller reacts to a triggered Schedule by calling
`KnowledgeSynchronization.synchronize()`. Optionally delegates the "when to fire" concern
to an external `IKnowledgeSynchronizationScheduler` backend when one is configured; the
in-memory ledger is always kept regardless.

## 8. Validator

12 stages, run in fixed order by `KnowledgeSynchronizationValidator`, aggregating every
issue without short-circuiting: **Provider**/**Source** (blank check + Job/Context
mismatch), **Namespace** (blank check + mismatch when both set), **Policy**/
**Permission** (blank Context field when present), **Schedule** (a `SCHEDULED`-mode Job
must have `type` `SCHEDULED_SYNC`), **Metadata** (rejects reserved keys —
`__proto__`/`constructor`/`prototype`), **Relationship** (a `RELATIONSHIP_SYNC` Job needs
a `collection`), **Version** (a `VERSION_SYNC` Job needs a Context `version`),
**Tenant** (blank check + mismatch), **Workspace** (mismatch when both set),
**Execution Token** (structural `stok_` format check). Accepts optional caller-supplied
`extraStages`.

## 9. Provider Resolver

"Resolve providers only. No provider implementation." `KnowledgeSynchronizationResolver`
resolves a registered `IKnowledgeSynchronizationProvider` by id from the Registry's
`PROVIDER` bucket, throwing `ProviderNotFoundException` when nothing is registered. It
also owns Change Detection delegation (see §5, stage 6) — a second, distinct
responsibility bundled into the same Public API class since the source prompt names only
one `KnowledgeSynchronizationResolver`.

## 10. Policies & Conflict Resolution

`KnowledgeSynchronizationPolicy` combines two responsibilities under one Public API
class, per the source prompt's adjacent "Provider Resolver"/"Conflict Resolution"
sections and the single `KnowledgeSynchronizationPolicy` name:

- **Policy evaluation** — `evaluate(job)` checks every enabled Policy whose `scope`
  covers the Job's `tenantId`/`workspaceId` for `allowedModes`/`deniedModes` violations
  against `job.mode` — real, non-stub evaluation logic (not merely a permissive
  pass-through), mirroring `@aos/knowledge-engine`'s `KnowledgePolicyEngine.evaluate()`
  pattern but self-contained (not reusing that engine directly, since Synchronization
  Policies gate Jobs/Modes rather than `KnowledgeAsset`s).
- **Conflict Resolution** — "Create interface-only contracts ... No implementation."
  `resolveConflicts(changes, strategy?)` owns no resolution algorithm; dispatches to a
  registered `IKnowledgeSynchronizationConflictResolver` keyed by
  `KnowledgeConflictResolutionStrategy`, kept in a private map (not the Registry, whose
  8-bucket list has no "Conflict Resolver" entry) — mirrors
  `@aos/knowledge-retrieval`'s `KnowledgeRankingEngine` dispatch-only pattern exactly.

## 11. Change Detection

"Only metadata detection. No content parsing." `KnowledgeChangeRecord` never carries
parsed file content — only `assetId`/`path`/`previousPath`/`contentHash`/`metadata`
pointers a Provider's Change Detector populates. Detection is delegated entirely to an
optional injected `IKnowledgeSynchronizationChangeDetector`; this package supplies zero
detectors of its own.

## 12. Middleware Pipeline

"MIDDLEWARE PIPELINE: Validation → Permission → Policy → Tracing → Metrics → Lifecycle →
Logging → Custom Middleware. Support sync.use()." `KnowledgeSynchronizationMiddlewarePipeline`
is a Koa-style chain (`use()`/`run()`, `next()`-based dispatch, throws on double-`next()`
calls) a caller extends via `synchronization.use(middleware)`. It runs once per
`synchronize()` call, after the real `KnowledgeSynchronizationPipeline` has already
validated/gated/resolved/committed the Execution — the 7 named built-in slots are
pass-through extensibility hook points a caller's Custom Middleware can observe or
augment (e.g. attach a real `IKnowledgeSynchronizationTracer`/`IKnowledgeSynchronizationTelemetry`);
this package registers no real tracing/logging/telemetry behavior itself.

## 14. Health

5 statuses (Healthy/Warning/Degraded/Unavailable/Unknown). `KnowledgeSynchronizationHealth.check()`
derives Registry health from whether any of the 8 buckets has an entry (`unknown` when
empty, `healthy` otherwise), and Synchronization health from the live
`failedSynchronizations/synchronizationCount` ratio (`healthy` at 0, `warning` ≤ 0.2,
`degraded` ≤ 0.5, `unavailable` above). Overall status is the worst of the two.

## 18. Technical Debt

- `KnowledgeSynchronizationSession` and the Synchronization Lifecycle State Machine are
  two independent state ledgers over the same `KnowledgeSynchronizationToken` — a caller
  wanting session-scoped synchronization history must correlate them itself.
- `KnowledgeSynchronizer`'s post-pipeline state transitions (`PREPARING` → ... →
  `COMMITTING` → `COMPLETED`) are recorded in rapid succession after one atomic
  `KnowledgeSynchronizationPipeline.run()` call rather than being driven stage-by-stage
  from inside the Pipeline itself — accurate lifecycle bookkeeping, but not a mechanism a
  caller can hook mid-Pipeline (the Middleware Pipeline runs only after the entire
  `synchronize()` call resolves).
- `KnowledgeSynchronizationScheduler` never computes real Cron/Interval next-run times —
  a production deployment needs an external `IKnowledgeSynchronizationScheduler`
  implementation (or a 005.7F Provider) to actually drive scheduled Jobs on a wall clock.
- `ISynchronizationPermissionChecker` is permissive by default; a production deployment
  must supply a real checker before this package enforces any Permission gate for real
  tenant data.

## 19. Known Limitations

- All 12 Extension Point contracts (`contracts/`) have zero implementations — by design.
- `KnowledgeSynchronizationResolver` ships zero registered Providers; a caller must
  register at least one Provider before `KnowledgeSynchronization.synchronize()` can
  resolve anything.
- `knowledge.sync.metrics.updated`/`.health.changed` are declared in
  `KnowledgeSynchronizationEventType` but never published — no scheduled Metrics/
  Health-diffing sampler exists in this package (matching the same documented gap in
  `@aos/knowledge-retrieval`'s `knowledge.search.health.changed`).
- `KnowledgeSynchronizationPolicy`'s Policy evaluation only understands
  `allowedModes`/`deniedModes` rule fields — richer rule types (e.g. time-window or
  Provider-type restrictions) are not modeled and would require extending
  `KnowledgeSynchronizationPolicyRecord`.
