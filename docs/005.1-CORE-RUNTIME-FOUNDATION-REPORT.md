## 6. Architecture Summary

Every package obeys the same shape: `README.md` (purpose, contents, dependency graph, architecture note), `package.json` (workspace-scoped, explicit `dependencies` vs `devDependencies`), a `library.json`-derived `tsconfig.json` (strict mode, `NodeNext`, composite builds), a parallel `tsconfig.eslint.json` covering `test/` too, ESLint via the shared `@aos/eslint-config`, and Vitest via the shared `@aos/vitest-config` base.

The package boundaries mirror Constitution §3.11 (Hexagonal Architecture) exactly: `@aos/types` and `@aos/common` are the innermost, dependency-free layer; `@aos/errors`, `@aos/utils`, `@aos/logger`, `@aos/sdk` sit one layer out; `@aos/config` and `@aos/telemetry` are the outermost Foundation packages, closest to what a real Runtime service will eventually wire together. `@aos/sdk` is the one deliberate exception to "every package does real work" — it is intentionally type-only, existing solely to keep the Contract Specification's field shapes (`docs/003.5-CONTRACT-FIRST-DESIGN.md`) compile-time-checked ahead of any Registry Service existing to validate them at runtime.

The Docker Compose stack matches TSR §3's decisions exactly (PostgreSQL, Valkey, NATS JetStream, Temporal, MinIO, Qdrant) at Phase 1 "Simulation" scale per `docs/004A-COST-SCALING-STRATEGY.md` §2 — single-node, no HA, no managed services, deliberately.

## 7. Known Limitations (Foundation Phase — by design, not oversight)

1. **No Runtime exists.** `@aos/sdk`'s Contract types have nothing behind them yet — no Registry Service validates an `AgentContract` instance against `schemas/agent.schema.json` at runtime; that validation currently only exists as the hand-authored JSON Schema files from Engineering Task 003.5.
2. **No app exists under `apps/`.** `pnpm dev` and `pnpm exec playwright test` are wired but have nothing to run against.
3. **`@aos/telemetry` has no exporter attached.** `initTracing`/`initMetrics` register providers but ship spans/metrics nowhere — intentional, per the package's own Architecture Note (exporter choice is a deployment-time decision, not a Foundation-time one).
4. **`@aos/config`'s `baseConfigSchema` is intentionally minimal.** It has no knowledge of Postgres/NATS/Temporal connection shapes — those schemas belong to whichever future package actually connects to those systems.
5. **Husky's `prepare` script warns "`.git` can't be found"** because this directory is not yet a git repository (confirmed at session start) — harmless, but `git init` should happen before the pre-commit hook can actually fire.
6. **`docker-compose.yml` has no application container.** Only infrastructure dependencies are defined; there is nothing in `apps/` yet to containerize.
7. **Local Node version is 20.14.0, not the TSR/prompt-mandated Node 22 LTS.** `package.json` engines are set to `>=20.11.0` to reflect the actual verified environment; Docker images (once apps exist) should still target `node:22-alpine` per TSR §3.1, and CI (`ci.yml`) already pins Node 22 — this is a local-dev-environment gap, not a repository configuration gap.
8. **No secrets management is wired up.** `@aos/config`'s `env-loader` reads plain `.env` files; Vault/cloud Secrets Manager integration (TSR §3.22) is a Runtime-phase concern.

## 8. Recommendation for ENGINEERING TASK 005.2

This report recommends, but does **not** implement, the following scope for 005.2:

1. **First real app under `apps/`** — most likely the Core Runtime's Registry Service (doc 003.5 §13/§14), since every other runtime pillar (Event Bus, Tool Manager, Workflow Runtime, Agent Runtime) depends on Registry entries existing first, per the build order already established in `docs/003.5-CONTRACT-FIRST-DESIGN.md` §22 Dependency Graph.
2. **Wire `@aos/sdk`'s Contract types to real schema validation** — either generate them from `schemas/*.schema.json` directly (closing the "hand-maintained mirror" gap noted in `packages/sdk/README.md`) or add a runtime validation layer (e.g. `ajv`) that validates a parsed JSON payload against the schema and only then trusts it as the corresponding `@aos/sdk` type.
3. **Attach a real OpenTelemetry exporter** to `@aos/telemetry`, targeting the Phase 1 Grafana LGTM stack from `docs/004A-COST-SCALING-STRATEGY.md` §2 (add `otel-collector`, `grafana`, `prometheus`, `loki`, `tempo` services to `docker/docker-compose.yml` at that point — not before, per this report's own "don't over-build Phase 1" discipline).
4. **`git init` this repository** and configure branch protection referencing `.github/CODEOWNERS`, so Husky's pre-commit hook and the CI workflow actually activate.
5. **Extend `@aos/config`'s schema** with the first real infrastructure connection shapes (Postgres, NATS) only once the Registry Service (or whatever app lands first) actually needs to connect to them — not speculatively.
6. **Do not** add Workflow Runtime, Agent Runtime, Planner/Reasoner/Reflection, or any Dashboard code in 005.2 unless the Registry Service (or chosen first app) is complete and its own foundation is verified with the same install/lint/build/test/typecheck discipline used here — each runtime pillar should get its own scoped implementation task, mirroring how Foundation was scoped separately from Contract Specification (003.5) and Technology Selection (004).

**This recommendation is a scope proposal only — Engineering Task 005.2 itself is not implemented as part of this report.**
