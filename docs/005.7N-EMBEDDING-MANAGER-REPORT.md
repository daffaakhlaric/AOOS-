# 005.7N — Enterprise Embedding Manager — AI Delivery Report

## Summary

Built `packages/embedding-manager` (`@aos/embedding-manager`), the 14th package in the
identical AOS Knowledge-package architecture series, following `@aos/knowledge-validator`
(005.7M) as the closest structural precedent. The package orchestrates embedding
lifecycle, metadata, provider abstraction, model registry, embedding versioning,
embedding jobs, and cache metadata — and never generates an embedding, performs vector
search, or connects to a vector database. All real embedding work is delegated through
12 interface-only Extension Points this package never implements.

- **17** Public API classes (one fewer than every prior sibling — no "Knowledge" prefix
  means no second "...Manager" name is available; see "Architecture").
- **14** domain aggregates, **8** Providers (metadata), **9** Models (metadata),
  **9**-state Lifecycle, **8** Registry buckets, **5** Resolvers, exactly **12**-stage
  Validator, exactly **10**-stage Pipeline, Koa-style Middleware, **6** Factories,
  **11** Events, **8** Metrics, **12** Extension Points (+2 Future Readiness contracts).
- **703 tests** across 53 spec files.
- Coverage: **99.44%** statements / **98.65%** branches / **100%** functions /

- All 5 workspace-verification commands pass with zero regressions across the other 53

## Architecture

Identical shape to every completed AOS Knowledge package: contract-first,
metadata-driven, event-driven, vendor-neutral, strictly an orchestrator.
`EmbeddingManager` (the façade, `embedding/embedding-manager.ts`) composes Registry +
Resolver + Validator + Pipeline + Middleware + State Machine + Lifecycle + Session +
Events + Metrics/Health/Monitoring/Statistics + Factory — same collaborator set as
`KnowledgeValidator`.

### The manager/embedding naming-collision resolution (the single most important structural judgment call)

The spec's own "Package Structure" section lists both a `manager/` folder AND an
`embedding/` folder as siblings, mirroring the established `manager/` (low-level
composition: Registry+Session+Statistics+token-keyed ledger) + `<domain-name>/`
(public facade owning StateMachine+Pipeline+Middleware+Manager+Resolver) split from
`knowledge-validator`'s `manager/`+`validation/` and `knowledge-quality`'s
`manager/`+`quality/`. But this package's Public API list has ONLY `EmbeddingManager`
as the single top-level orchestrator name — there is no second "manager" name
available, unlike every prior sibling (`KnowledgeValidatorManager` vs
`KnowledgeValidator`, `KnowledgeQualityManager` vs `KnowledgeQualityAssessment`, etc.).

**Resolution**: the internal, NOT publicly re-exported composition class lives in
`manager/embedding-manager-ledger.ts` and is named `EmbeddingManagerLedger` —
internal-sounding, deliberately distinct from the Public API name. It is kept OUT of
`src/index.ts`'s curated exports. The actual Public API class literally named
`EmbeddingManager` lives in `embedding/embedding-manager.ts`, implements all the
Embedding Operations, and composes `EmbeddingManagerLedger` as one of its internal
collaborators alongside the StateMachine/Pipeline/Middleware/Resolver/Validator/Events.
This preserves the two-folder package structure the spec literally requires while
staying within the spec's literal 17-name Public API list.

## Domain Model

The 14 named aggregates map 1:1 onto dedicated `domain/*.ts` files. Two required a
documented rename to avoid a same-name collision with a Public API class:

- `EmbeddingSession` (the domain aggregate, "Domain Model" list) → exported as
  `EmbeddingSessionRecord` (`domain/embedding-session.ts`), since `EmbeddingSession`
  is ALSO the literal Public API class name (`session/embedding-session.ts`, the
  Open/Resume/Close/Cancel/Expire/Renew ledger) — same intentional split as
  `KnowledgeValidationSession` vs `KnowledgeValidatorSession` in 005.7M, but here the
  spec's own two lists literally use the identical string "EmbeddingSession" for both,
  so the domain-side rename is the resolution (documented in the file's own doc
  comment).
- `EmbeddingStatistics` (the domain aggregate) → the snapshot type is exported as
  `EmbeddingStatisticsSnapshot` (`domain/embedding-statistics-snapshot.ts`), since
  `EmbeddingStatistics` is the literal Public API class name
  (`statistics/embedding-statistics.ts`).

`EmbeddingRequest` deliberately carries only a `textReference`/`contentReference` (an
opaque pointer the caller resolves elsewhere) — never actual text content, per the "AI
Scope Boundary." `EmbeddingResultMetadata` carries `dimensionCount` and an opaque
`providerReportedMetadata` bag — never a vector. `EmbeddingCache` carries hit/miss
counters and a `cacheKeyReference` — never cached vector data.

## Embedding Flow

`createEmbedding()` → Draft → `queue()` → Queued → `prepare()` → Preparing →
`start()` → Embedding → `complete()`/`fail()` → Completed/Failed → `archive()` →
Archived → `destroy()` → Destroyed (terminal). `cancel()` is legal from every
non-terminal, non-settled state. Because the 10-stage Pipeline's Provider/Model/
Namespace/Configuration Resolution stages (2–5) run on **every** Pipeline invocation,
not only during `prepare()`, a declared Provider/Model must already be registered
before `createEmbedding()` itself succeeds — there is no "Draft with an unresolved
Provider" state in this design, unlike a design where Resolution is deferred entirely
to `prepare()`. This was verified directly by tests (`test/embedding/provider-model-matrix.spec.ts`,
`test/embedding/embedding-operations-extra.spec.ts`) that assert `createEmbedding()`
itself throws for an unregistered Provider/Namespace/Configuration.

`registerProvider()`/`registerModel()`/`registerVersion()` are setup plumbing OUTSIDE
the state-machine-driven Embedding Operations count — they publish
`ProviderRegistered`/`ModelRegistered`/`VersionCreated` respectively but never drive
`Embedding.state`, matching the "setup plumbing outside the main operation count"
pattern documented in `@aos/knowledge-marketplace`'s (005.7J) report.

## Lifecycle

Nine states in the prompt's own order: Draft, Queued, Preparing, Embedding, Completed,
Cancelled, Failed, Archived, Destroyed. Unlike `@aos/knowledge-validator` (005.7M),
which has TWO settled outcomes (Approved/Rejected) fanning out of a "Reviewing"
checkpoint, this package's spec has no separate reviewing step, so the transition
table is simpler:

```
Draft      -> Queued, Cancelled, Destroyed
Queued     -> Preparing, Cancelled, Destroyed
Preparing  -> Embedding, Failed, Cancelled, Destroyed
Embedding  -> Completed, Failed, Cancelled, Destroyed
Completed  -> Archived, Destroyed
Failed     -> Archived, Destroyed
Cancelled  -> Archived, Destroyed
Archived   -> Destroyed
Destroyed  -> (none — terminal)
```

`Preparing` and `Embedding` can both fail outright (`-> Failed`) since an externally
supplied `IEmbeddingProvider` can reject at either resolution or invocation time. Every
state is reachable from Draft (verified by a BFS-reachability test in
`test/state-machine/transition-table.spec.ts` and `test/lifecycle/lifecycle.spec.ts`);
`Destroyed` has no outgoing edges. `EmbeddingStateMachine` stamps `startedAt` on the
transition into `EmbeddingState.EMBEDDING` (careful: the enum value, spelled
identically to the `Embedding` domain-aggregate class and the package's own name —
every code comment disambiguates by writing `EmbeddingState.EMBEDDING`) and `settledAt`
on the transition into any of the 4 settled outcomes (Completed/Failed/Cancelled/
Archived).

## Registry

Eight buckets exactly as named: `EMBEDDING`, `PROVIDER`, `MODEL`, `VERSION`,
`NAMESPACE`, `SESSION`, `STATISTICS`, `AUDIT`. `JOB` and `CONFIGURATION` are NOT
Registry buckets, matching the documented-gap precedent from
`@aos/knowledge-validator`/`@aos/knowledge-generator`:

- **Jobs** live in a dedicated ledger on `EmbeddingManagerLedger` (`jobsById`),
  matching the Job-ledger convention every prior sibling used.
- **Configurations** live in a dedicated map on `EmbeddingResolver`
  (`configurationsById`), matching the Policy-map precedent on
  `KnowledgeValidatorResolver`. This resolution ALSO addresses a real design tension:
  `EmbeddingConfiguration.embeddingId` cannot be meaningfully cross-checked against
  "the current Embedding" at validation time, because Configuration is commonly
  registered as a reusable settings template (timeout/retries/batchSize) BEFORE the
  Embedding it will end up attached to even exists — see "Technical Debt" below.

Provider/Model records are keyed by a **deterministic, tenant-scoped composite id**
(`buildProviderRegistryId(tenantId, providerType)` /
`buildModelRegistryId(tenantId, modelName)`, both in
`domain/embedding-registry-keys.ts`) rather than a caller-chosen opaque id. This lets
the Pipeline's Provider/Model Resolution stages resolve "which registered
Provider/Model handles this Request" via a single `Map` lookup, built purely from the
Request's declared `providerType`/`modelName` tags — "Never scan collections" — without
requiring the Request to carry an opaque `providerId`/`modelId` the caller would
otherwise have to look up out-of-band first. `registerProvider()`/`registerModel()`
default a record's id to this composite key when the caller doesn't supply one
explicitly (verified by `test/embedding/embedding-manager.spec.ts` — "Provider
Operations"/"Model Operations").

## Providers

Eight metadata tags on `EmbeddingProviderType`: OpenAI, Voyage AI, Cohere, Jina AI,
Gemini, Ollama, FastEmbed, Custom Provider. Zero implementations ship in this package.

## Models

Nine metadata labels on `EmbeddingModelName`. The built-in
`EMBEDDING_MODEL_PROVIDER_CATALOG` (`domain/embedding-model-catalog.ts`) maps each to
its expected Provider:

| Model                    | Provider        | Rationale                                                  |
| ------------------------ | --------------- | ---------------------------------------------------------- |
| `text-embedding-3-small` | OpenAI          | OpenAI's own model naming.                                 |
| `text-embedding-3-large` | OpenAI          | OpenAI's own model naming.                                 |
| `voyage-large-2`         | Voyage AI       | Voyage's own model naming.                                 |
| `voyage-code-2`          | Voyage AI       | Voyage's own model naming.                                 |
| `jina-embeddings`        | Jina AI         | Jina's own model naming.                                   |
| `gemini-embedding`       | Gemini          | Google's own model naming.                                 |
| `nomic-embed`            | Ollama          | Nomic's embedding model ships as an Ollama-servable model. |
| `bge-large`              | FastEmbed       | BAAI's BGE family ships as a default FastEmbed model.      |
| `custom`                 | Custom Provider | The only model allowed under a caller-defined provider.    |

**`Cohere` has no catalog entry** — none of the 9 `EmbeddingModelName` labels are
Cohere's own `embed-*` naming. A documented gap: a Cohere-backed deployment is expected
to register under `EmbeddingModelName.CUSTOM` paired with
`EmbeddingProviderType.CUSTOM_PROVIDER` instead, same as any provider without a
first-class label. Verified explicitly by
`test/embedding/provider-model-matrix.spec.ts` — "Cohere has no catalog Model
(documented gap)".

## Validation

Exactly 12 stages: Identity, Metadata, Provider, Model, Namespace, Configuration,
Version, Lifecycle, Dependency, Statistics, Integrity, Audit — one file per stage plus
an aggregator (`validator/embedding-validator.ts`, class `EmbeddingValidator`), running
all 12 in fixed order without short-circuiting, with `extraStages` support.

### Validator-stage vs Pipeline-stage naming distinction

Stages 3–7 of the 12-stage Validator (Provider, Model, Namespace, Configuration,
Version) share names with Stages 2–5 of the 10-stage Pipeline (Provider Resolution,
Model Resolution, Namespace Resolution, Configuration Resolution) — deliberately, per
the spec's own naming. They are NOT the same work:

- The **Validator**'s stages are pure, pre-flight, structural checks on the fields
  ALREADY declared on the Request (and on whatever facts the Pipeline precomputed and
  handed in, e.g. an already-resolved Provider's `active` flag) — they never touch the
  Registry directly.
- The **Pipeline**'s stages perform the actual Registry lookups — resolving "does a
  Provider/Model/Namespace/Configuration matching this declaration actually exist" and
  throwing a dedicated exception (`EmbeddingProviderException`,
  `EmbeddingModelException`, `EmbeddingNamespaceException`,
  `EmbeddingConfigurationException`) when it does not.

Because the Pipeline always runs the full 12-stage Validator FIRST (Pipeline Stage 1),
an inactive resolved Provider is normally caught by the Validator's own
`ProviderValidator` stage before the Pipeline's own Stage 2 active-check is ever
reached — a documented, intentional defense-in-depth redundancy (see
`test/pipeline/pipeline.spec.ts` — "throws (via the pre-flight Validator) when the
resolved Provider is inactive" and the accompanying test that exercises the Pipeline's
OWN check directly via a stubbed always-valid Validator).

## Pipeline

Exactly 10 stages: Validation, Provider Resolution, Model Resolution, Namespace
Resolution, Configuration Resolution, Metadata, Metrics, Lifecycle, Audit, Logging.
Real substantive work at every stage — no stubs. Provider Resolution and Model
Resolution never invoke a Provider/Model; they only resolve which registered record
handles the Request and validate compatibility via the built-in catalog. This package
NEVER invokes `IEmbeddingProvider` from inside the Pipeline — that is exclusively a
facade-level concern (`EmbeddingManager.start()`).

## Metrics

Eight named counters, all real running computations (`metrics/embedding-metrics.ts`):
Embedding Count, Provider Count, Model Count, Version Count, Namespace Count, Average
Duration (a real running average), Cache Metadata Count, Provider Usage (a
per-`EmbeddingProviderType` tally, `Record<string, number>`). Plus internal
`checkCount`/`checkFailureCount` bookkeeping feeding Health/Monitoring.

## Monitoring

`EmbeddingMonitoring.sample()` combines a live Metrics snapshot with an
`EmbeddingHealth.check()` report (Registry occupancy across all 8 buckets + domain
failure-ratio derived from `checkCount`/`checkFailureCount`, 5 statuses:
healthy/warning/degraded/unavailable/unknown) into one `EmbeddingManagerDashboard`.

## Statistics

`EmbeddingStatistics` tracks `requestedCount`/`completedCount`/`failedCount`/
`cancelledCount`/`lastActivityAt` per `EmbeddingProviderType` — keyed by the Request's
declared Provider Type (mirroring `KnowledgeValidatorStatistics`'s per-Category
keying). A documented consequence, verified by
`test/embedding/embedding-operations-extra.spec.ts` — "multi-tenant isolation": since
Statistics is keyed by Provider Type only (not tenant), two different tenants using the
same Provider Type share the same counter bucket. This mirrors the precedent set by
every prior sibling's Statistics keying and is an acceptable simplification for a
package that is itself a metadata orchestrator, not a billing/reporting system.

## Technical Debt

1. **Configuration has no dedicated Registry bucket.** The spec's 8 named buckets do
   not include `CONFIGURATION`. Resolved by tracking Configuration records in a
   resolver-local map (`EmbeddingResolver.configurationsById`), matching the Policy
   precedent on `KnowledgeValidatorResolver`. A consequence: `ConfigurationValidator`
   (Validator Stage 6) deliberately does NOT cross-check
   `EmbeddingConfiguration.embeddingId` against the current Embedding's id, because
   Configuration is commonly registered as a reusable template before the Embedding it
   attaches to even exists. A future phase that needs a dedicated Configuration
   Registry bucket (e.g. to support listing/removing Configurations independently of
   the Resolver) would need a spec amendment adding an explicit `CONFIGURATION` bucket
   name.
2. **Cohere has no catalog Model.** None of the 9 `EmbeddingModelName` labels use
   Cohere's own naming convention. A Cohere deployment must register under
   `custom`/`Custom Provider`. A future phase could add Cohere-specific model labels
   (e.g. `embed-english-v3`) if the spec's 9-model list is ever extended.
3. **Statistics keyed by Provider Type only, not by tenant.** Acceptable for a
   metadata-orchestration package; a future phase needing tenant-scoped billing/
   reporting would need a composite key (mirroring `buildProviderRegistryId`'s
   `tenantId::type` pattern).
4. **`IEmbeddingCacheProvider`/`IEmbeddingCompressionProvider`/
   `IEmbeddingEncryptionProvider` are pure interfaces with no built-in default.** This
   is intentional per the "AI Scope Boundary," not a gap — but it means a caller must
   supply ALL of these before any real caching/compression/encryption behavior exists;
   this package provides zero default behavior for any of them.

## Known Limitations

- This package never validates that a caller-supplied `dimensionCount` in
  `EmbeddingResultMetadata` actually matches the resolved Model's declared
  `dimensions` field — that cross-check is left to the caller's own
  `IEmbeddingProvider`/`IEmbeddingModelProvider` implementation, since this package
  never inspects the actual vector.
- `EmbeddingCache` metadata (hit/miss counters, cache-key references) is a pure
  read/write surface with no built-in eviction policy or TTL — entirely the concern
  of a caller-supplied `IEmbeddingCacheProvider`.
- No default `IEmbeddingScheduler` is provided — `EmbeddingJob` records are inert
  metadata until a caller-supplied scheduler acts on them.

## Non-obvious design/judgment calls (full list)

1. **Dependency mapping.** Spec names `@aos/kernel`, `@aos/shared`, `@aos/events`,
   `@aos/knowledge-engine`, `@aos/knowledge-validator`. Real workspace packages are
   `@aos/runtime-kernel`, `@aos/common`, `@aos/errors`, `@aos/event-bus` — same mapping
   every prior sibling used (verified against `packages/knowledge-validator/package.json`).
   `@aos/knowledge-engine`/`@aos/knowledge-validator` are not imported at runtime at
   all — this package references neither concretely, matching every prior sibling's
   "interface-references-only, never a concrete runtime dependency" precedent for its
   "Knowledge" allowed-dependency section.
2. **Event namespace: `embedding.*`, not `knowledge.embedding.*`.** Since this
   package drops the "Knowledge" prefix entirely from its own naming
   (`@aos/embedding-manager`, classes `Embedding*`), `embedding.*` is the more
   internally consistent choice, and was used throughout
   (`events/embedding-manager-event-type.ts`).
3. **The manager/embedding folder-vs-facade naming resolution** — see "Architecture"
   above; the single most important structural judgment call in this package.
4. **Provider/Model built-in catalog design** — see "Models" above; documented mapping
   with Cohere as the one documented gap.
5. **Missing Configuration Registry bucket resolution** — see "Registry"/"Technical
   Debt" above; resolver-local map, no `embeddingId` cross-check.
6. **Lifecycle transition table design** — 9-state, no separate Reviewing checkpoint
   (unlike 005.7M), `Preparing` and `Embedding` can both fail outright. Fully
   BFS-reachability-verified.
7. **Resolver shape** — one `EmbeddingResolver` class with 5 named resolve-method
   pairs (Embedding/Provider/Model/Namespace/Version) plus a 6th, EXTRA
   Configuration pair backed by a resolver-local map, matching
   `KnowledgeValidatorResolver`'s Policy precedent exactly.
8. **Future Readiness interpretation.** Satisfied via exactly 2 additional small
   single-method interfaces (`IKnowledgeGraphEmbeddingProvider`,
   `IKnowledgeRecommendationEmbeddingProvider`, both in `contracts/`), each
   documented as a seam for 005.7O/005.7P respectively. No speculative stub
   modules/folders were added.
9. **Token prefix `embt_`** (EMBedding manager TOken) — collision-free with every
   existing AOS token prefix (`ptok_`, `stok_`, `ksrc_`, `kver_`, `kpol_`, `kmkt_`,
   `kgen_`, `kqua_`, `kval_`), confirmed by grepping
   `packages/knowledge-validator/src/token/knowledge-validator-token.ts` for the last
   entry in that list before choosing a new one.
10. **Validator-stage vs Pipeline-stage naming distinction** — see "Validation"
    above; documented in every affected stage's own doc comment.
11. **`EmbeddingState.EMBEDDING` vs `Embedding` the domain class.** Every code comment
    and this report consistently write `EmbeddingState.EMBEDDING` when referring to the
    enum value, never bare "Embedding" in that context, to keep the two unambiguous.
12. **Domain aggregate renames to avoid Public API collisions** — `EmbeddingSession`
    (domain) → `EmbeddingSessionRecord`; `EmbeddingStatistics` (domain) →
    `EmbeddingStatisticsSnapshot`. Both documented in their own file's doc comment.
13. **`registerProvider()`/`registerModel()`/`registerVersion()` publish events but
    are NOT part of the Embedding Operations state-machine count.** Matches the
    "setup plumbing outside the main operation count" pattern from
    `@aos/knowledge-marketplace` (005.7J).
14. **`Cohere` end-to-end matrix test exclusion.** The provider/model end-to-end test
    matrix (`test/embedding/provider-model-matrix.spec.ts`) explicitly excludes Cohere
    from its "one compatible Model per Provider" sweep and instead asserts the
    documented-gap behavior directly, rather than silently mis-mapping Cohere to an
    incompatible Model.

## Readiness Checklist for 005.7O (Knowledge Graph)

- `IKnowledgeGraphEmbeddingProvider` (`contracts/i-knowledge-graph-embedding-provider.ts`)
  is the prepared seam: `linkEmbeddingToNode(resultMetadata, nodeId)`. A future
  `@aos/knowledge-graph` package can implement this to consume `EmbeddingResultMetadata`
  when linking graph nodes to embedding results, without this package ever needing to
  know about graph structure.
- `EmbeddingResultMetadata` (dimension count, provider-reported metadata, timing) is
  the stable, already-shipped data shape 005.7O will consume — it will never change
  shape to accommodate graph-specific needs; any graph-specific data belongs on the
  graph side.
- `EmbeddingNamespace` and `EmbeddingVersion` are already registrable/resolvable
  independently of any specific Embedding, so a graph package can reference them by id
  without needing new contracts.
- `EmbeddingManagerConfig.knowledgeGraphProvider` is the config slot already wired
  through to `EmbeddingManager`'s constructor — 005.7O only needs to supply a real
  implementation, no changes to this package are required.
- No implementation of graph traversal, node linking, or graph storage exists in this
  package, per the strict scope boundary — 005.7O owns all of that.
