# Engineering Task 005.7M — Enterprise Knowledge Validator AI — Closing Report

## Summary

Delivered `@aos/knowledge-validator`, the layer responsible for orchestrating
enterprise validation of knowledge assets before they are accepted into the Knowledge
Platform: validation requests, validation sessions, validation jobs, validation rules,
validation decisions, validation reports, validation metadata, validation

(005.7L, immediate prior sibling) with the domain vocabulary shifted from "quality

## Architecture

Identical shape to every completed AOS Knowledge package. `src/` is organized into 24
modules: `domain/`, `contracts/`, `errors/`, `context/`, `token/`, `session/`,
`state-machine/`, `lifecycle/`, `registry/`, `resolver/`, `validator/` (12 stages),
`pipeline/` (10 stages), `middleware/`, `factory/`, `events/`, `metrics/`, `health/`,
`monitoring/`, `statistics/`, `manager/`, `validation/` (the façade folder — literally
named `validation/`, distinct from the `validator/` folder that holds the internal
12-stage Validator, per the spec's own Package Structure listing), `bootstrap/`,
`config/`, and root `index.ts`. `KnowledgeValidator` is a pure orchestrator: it never
holds validated content, never runs inference, and never computes a decision — it only
moves metadata through a strict state machine and delegates every substantive judgment
to caller-supplied provider interfaces.

### Decision vs. Report vs. Finding vs. ResultMetadata modeling

Four related-but-distinct concepts, deliberately kept separate:

- **`KnowledgeValidationDecision`** — records WHICH of the 6
  `KnowledgeValidationDecisionValue` values (`Approved`, `Conditionally Approved`,
  `Requires Review`, `Requires Revision`, `Rejected`, `Expired`) a reviewer or
  `IKnowledgeValidationDecisionProvider` reported for the _whole_ Validation, plus who
  reported it and an optional confidence. Exactly one (at most) per Validation,
  recorded by `approve()`/`reject()`.
- **`KnowledgeValidationFinding`** — one individual issue/observation, tagged with a
  `KnowledgeValidationCategory` and severity. Zero or many per Validation, recorded by
  `recordFinding()` or a provider's `validate()` result during `start()`.
- **`KnowledgeValidationResultMetadata`** — metadata ABOUT a validation outcome
  (confidence, outcome label, provider id) — never the validated content itself. Held
  on the execution envelope for a caller-supplied provider to attach structured
  outcome metadata beyond a single Decision, without this package ever interpreting
  it.
- **`KnowledgeValidationReport`** — the aggregate: built by `generateReport()` purely
  from whatever Findings + the Decision id have already been recorded. Never renders
  anything and never itself validates or decides.

## Validation Flow

`createValidation()` (→ Draft) → `queue()` (→ Queued) → `prepare()` (→ Preparing,
resolves Rule/Policy/Configuration/Decision) → `start()` (→ Validating, optionally
invokes `provider.validate()`) → `review()` (→ Reviewing) → `approve()` / `reject()`
(→ Approved / Rejected, records the caller-supplied Decision) → `archive()` (→
Archived) → `destroy()` (→ Destroyed). `recordFinding()` is legal while
Validating/Reviewing; `generateReport()` is legal at any point once at least the
Validation exists. `cancel()` is legal from every non-settled state.

## Decision Lifecycle

Ten states in the prompt's own order: `Draft, Queued, Preparing, Validating,
Reviewing, Approved, Rejected, Cancelled, Archived, Destroyed`. `Destroyed` is the
sole hard-terminal state (no outgoing edges).

**This is the first sibling package whose Lifecycle has two independent settled
outcomes.** Every prior AOS Knowledge package (`@aos/knowledge-generator`,
`@aos/knowledge-quality`, ...) has exactly one "success" terminal-adjacent state
(typically `Completed`). Here, `Reviewing` fans out into BOTH `Approved` and
`Rejected` — two mutually exclusive, independently reachable, non-terminal-but-settled
outcomes. The transition table (`domain/knowledge-validation-state.ts`) was designed
as follows:

- Mainline: `Draft → Queued → Preparing → Validating → Reviewing`.
- `Reviewing → {Approved, Rejected, Cancelled, Destroyed}` — the only state with 2
  settled-outcome edges.
- Every non-terminal, non-settled state (`Draft` through `Reviewing`) can also be
  `Cancelled` or `Destroyed` directly.
- `Approved`, `Rejected`, and `Cancelled` all fan into `Archived`.
- Every state (including `Archived`) has an edge into the hard-terminal `Destroyed`.

Verified via a BFS-reachability test (`test/state-machine/transition-table.spec.ts`):
every one of the 10 states is reachable from `Draft`; `Destroyed` has no outgoing
edges; `Approved` and `Rejected` are both independently confirmed reachable from
`Reviewing` via direct edge assertions. A second file
(`test/state-machine/state-machine-extra.spec.ts`) exhaustively parameterizes all 23
legal edges plus a curated set of illegal pairs through `canTransition()`.
`KnowledgeValidatorLifecycle.isSettled()` returns `true` for `Approved`, `Rejected`,
`Cancelled`, `Archived`, `Destroyed`; `isTerminal()` returns `true` only for
`Destroyed`. The State Machine stamps `settledAt` on the transition into EITHER
`Approved` or `Rejected` (a single shared timestamp field, since a Validation settles
exactly once regardless of which outcome it reaches).

## Registry

Eight buckets exactly as named in the prompt: `VALIDATION`, `SESSION`, `RULE`,
`DECISION`, `CONFIGURATION`, `STATISTICS`, `AUDIT`, `FINDING`. `JOB` and `POLICY` are
NOT Registry buckets — the spec's 8-bucket list has no slot for either — so
`KnowledgeValidationJob` records live in a dedicated `KnowledgeValidatorManager`
ledger Map, and `KnowledgeValidationPolicy` records live in a dedicated
`KnowledgeValidatorResolver` map, matching the `@aos/knowledge-quality` precedent for
this exact situation. Every read is a direct `Map` lookup by id, never a scan.

## Validation Rules

`KnowledgeValidationRule` is metadata only — a named check definition tagged with a
`KnowledgeValidationCategory` and a severity, "no executable rule logic." This package
NEVER evaluates a Rule itself; a caller-supplied `IKnowledgeValidationRuleProvider`
owns that. The Pipeline's Rule Resolution stage (Stage 2) only resolves declared Rule
ids against the RULE Registry bucket and records usage via `metrics.recordRuleUsage()`.

## Policy Integration

`KnowledgeValidationPolicy` is an allow/deny-style record (not one of the 12 named
aggregates, no dedicated Registry bucket — same judgment call as Rule/Job above)
tracked in a `KnowledgeValidatorResolver`-owned map, registered via
`validator.registerPolicy()`. `evaluateKnowledgeValidationPolicy()`
(`domain/knowledge-validation-policy.ts`) is a real evaluator, not a stub: an inactive
Policy denies everything; an empty `allowedCategories` list means "no restriction"
(permissive-by-omission, matching `@aos/knowledge-policy`'s evaluators); otherwise
both the Request's declared primary Category and every resolved Rule's Category must
appear in the allow-list, with each disallowed Category producing its own reason
string. A caller may override this built-in evaluator entirely with a richer,
externally-governed policy engine via the `IKnowledgeValidationPolicyProvider`
extension point — the built-in evaluator is the default, not a mandatory path.

## Pipeline

Exactly 10 stages (`pipeline/knowledge-validator-pipeline.ts`), run in this fixed
order for every Validation Operation:

1. **Validation** — runs the entire 12-stage `KnowledgeValidatorValidator` aggregator
   over precomputed resolution facts (rule resolvability, Policy, Configuration,
   Decision). A failure halts the Pipeline and throws `ValidationCheckException`.
2. **Rule Resolution** — resolves every declared Rule id against the RULE bucket;
   throws `ValidatorRuleException` on any miss (in practice pre-empted by Stage 1's
   own Rule check when Rules are declared — see "Verified-but-practically-unreachable
   exception paths" below).
3. **Policy Resolution** — resolves the declared Policy and evaluates allow/deny via
   `evaluateKnowledgeValidationPolicy()`; throws `ValidatorPolicyException` on
   non-resolution or denial.
4. **Configuration Resolution** — resolves/validates the declared Configuration
   against the CONFIGURATION bucket; throws `ValidatorConfigurationException` on
   non-resolution. **Unlike Rule/Policy, this stage's exception path IS genuinely
   reachable in normal operation** — the 12-stage Validator's own Configuration stage
   only checks the _fields_ of an already-resolved Configuration (timeout/retries/
   maxFindings ranges), never whether a declared `configurationId` resolves at all.
5. **Decision Resolution** — the stage unique to this package (no sibling has an
   equivalent). If a `KnowledgeValidationDecision` has already been recorded on the
   execution, OR is being recorded by the current operation (passed via
   `RunValidatorPipelineInput.decision`, as `approve()`/`reject()` do), this stage
   validates the Decision's `value` is one of the 6 legal enum values and records it
   into Metrics (`recordDecision(confidence)`). When no Decision is present, this
   stage is a documented no-op — same spirit as `@aos/knowledge-generator`'s
   "structural no-op" stages.
6. **Metadata** — stamps `metadata.updatedAt`.
7. **Metrics** — records the named `Validation Count` metric via
   `metrics.recordValidation()`.
8. **Lifecycle** — advances the State Machine to `targetState` when supplied and
   different from the current state.
9. **Audit** — appends one immutable `KnowledgeValidationAudit` entry to the AUDIT
   bucket.
10. **Logging** — appends one structured, in-memory log entry.

### The triple "Validation" naming distinction

Per the task instructions, this is documented explicitly and kept separated in code
comments in every relevant file:

1. **Pipeline Stage 1, "Validation"** — runs the whole 12-stage
   `KnowledgeValidatorValidator` aggregator over the current execution's resolved
   facts. This is an orchestration step, not a field-level check.
2. **The 12-stage Validator's own Stage 3, also named "Validation"**
   (`validator/validation-validator.ts`, class `ValidationValidator`) — checks that
   the validation **Request itself** (not the knowledge being validated) has
   well-formed required fields: `requestId`, `requestedBy`, `targetReference` not
   blank, and `category` must be one of the 9 enumerated `KnowledgeValidationCategory`
   values.
3. **The 12-stage aggregator class itself**, `KnowledgeValidatorValidator`
   (`validator/knowledge-validator-validator.ts`) — a top-level Public API export in
   its own right, name-adjacent to but structurally and behaviorally distinct from the
   `KnowledgeValidator` façade (`validation/knowledge-validator.ts`) that drives it.

### Verified-but-practically-unreachable exception paths

Because Pipeline Stage 1 always runs first and reuses the exact same
pre-computed resolution facts (`missingRuleIds`, resolved `policy`, resolved
`decision`) that Stages 2/3/5 later re-check, a missing Rule/Policy/Decision will
almost always already fail Stage 1 (`ValidationCheckException`) before Stages 2/3/5's
own dedicated exceptions (`ValidatorRuleException`/`ValidatorPolicyException`/
`ValidatorDecisionException`) can fire. This mirrors `@aos/knowledge-quality`'s
identical structural situation. The test suite (`test/pipeline/pipeline.spec.ts`)
covers both: the everyday path (Stage 1 catches it first) AND the dedicated Stage 2/
3/5 exception paths directly, via `vi.spyOn(KnowledgeValidatorValidator.prototype,
"validate")` to bypass Stage 1 for exactly those 4 tests — confirming the Pipeline's
own stage-level exceptions are correct dead-code-in-the-happy-path defenses, not
unreachable garbage. Configuration Resolution (Stage 4) has no such overlap and is
reachable in every test without mocking, since the Validator's Configuration stage
never checks resolvability, only field ranges.

## Metrics

Eight named counters (`KnowledgeValidatorMetrics`, all real running computations, no
stubs): `Validation Count`, `Approved Count`, `Rejected Count`, `Decision Count`,
`Rule Usage`, `Policy Usage`, `Average Duration`, `Average Confidence Metadata` (a
real running average computed from every recorded `Decision.confidence`, matching the
Average-Duration/Average-Confidence running-average precedent from
`@aos/knowledge-quality`). Plus internal bookkeeping fields
(`configurationUsageCount`, `findingCount`, `checkCount`/`checkFailureCount`) that
exist purely to feed Health/Monitoring without inflating the 8 named metrics —
`checkCount`/`checkFailureCount` specifically track the 12-stage Validator's per-run
pass/fail outcome, distinct from the named `validationCount` metric (which counts
every Pipeline run regardless of outcome), mirroring the
`assessmentCount`/`validationCount` split in `@aos/knowledge-quality`.

## Monitoring

`KnowledgeValidatorMonitoring.sample()` combines a live `KnowledgeValidatorMetrics`
snapshot with a `KnowledgeValidatorHealth.check()` report into one
`KnowledgeValidatorDashboard`. Health derives Registry health from bucket occupancy
(healthy once anything is registered, unknown when empty) and domain health from the
`checkCount`/`checkFailureCount` failure ratio across the same 5-status scale used by
every prior AOS Knowledge package (healthy/warning/degraded/unavailable/unknown, at
0%/<10%/<50%/≥50% failure-ratio boundaries).

## Statistics

`KnowledgeValidatorStatistics` tracks `requestedCount`/`approvedCount`/
`rejectedCount`/`lastActivityAt` **per `KnowledgeValidationCategory`** — keyed by the
Request's single primary declared Category, since a Validation always declares
exactly one Category on its Request even though its resolved Rules may span several
Categories. This mirrors `@aos/knowledge-quality` keying its own Statistics by
Assessment Mode (a Request-level singular classifier) rather than by the
potentially-plural Dimension. Category-level rollups across many Rules are left to a
caller aggregating over `KnowledgeValidationFinding` records directly, exactly as
Dimension-level rollups were left to callers in the quality-engine precedent.

## Technical Debt

- The Decision Resolution stage's "consistent with current lifecycle state" check
  (per the prompt's own phrasing) is implemented narrowly — it validates the
  Decision's `value` is one of the 6 legal enum values, but does not independently
  re-derive "was this Decision legitimately recordable from the current state" beyond
  what `approve()`/`reject()` already enforce via `APPROVAL_DECISION_VALUES`/
  `REJECTION_DECISION_VALUES` before the Pipeline even runs. A future revision could
  push that consistency check fully into the Pipeline stage itself rather than
  splitting it across the façade and the stage.
- `IKnowledgeValidationDecisionProvider` is declared as a full Extension Point and
  `KnowledgeValidator.hasDecisionProvider()` reports whether one is configured, but no
  façade method automatically invokes it — `approve()`/`reject()` always take an
  explicit `DecisionInput` from the caller instead. This is a deliberate scope
  decision (see judgment call #12 below), not an oversight, but it does mean the
  interface currently has no automatic invocation path inside this package.

## Known Limitations

- In-memory only, single-process — no persistence, no distributed locking, no
  multi-instance coordination. Matches every prior AOS Knowledge package; production
  deployments are expected to layer `IKnowledgeValidationStorage`/
  `IKnowledgeValidationPublisher` adapters externally.
- `KnowledgeValidatorStatistics` and `KnowledgeValidatorMetrics` reset on process
  restart; no snapshot persistence is implemented (nor was it in scope).
- The built-in `evaluateKnowledgeValidationPolicy()` evaluator is intentionally
  simple (active/inactive + allow-list only) — real-world policy engines with
  conditional rules, time windows, or cross-tenant delegation must be supplied via
  `IKnowledgeValidationPolicyProvider`.

## Non-obvious design/judgment calls (full list)

1. **Dependency-name mapping** — the prompt's "Allowed Dependencies" names
   `@aos/kernel`/`@aos/shared`/`@aos/events`/`@aos/knowledge-engine`/
   `@aos/knowledge-quality`/`@aos/knowledge-policy`. The real workspace packages are
   `@aos/runtime-kernel` (not `@aos/kernel`), `@aos/common` (not `@aos/shared`), and
   `@aos/event-bus` (not `@aos/events`) — the identical mapping every prior sibling
   package used. `@aos/knowledge-engine`/`@aos/knowledge-quality`/
   `@aos/knowledge-policy` all exist as real workspace packages but, like every
   sibling package, this package imports zero concrete classes from any of them at
   runtime — every cross-package reference is interface-only (via this package's own
   Extension Point contracts), never a live import.
2. **Event-name mapping** — `ValidationCreated`/`ValidationQueued`/
   `ValidationStarted`/`ValidationCompleted`/`ValidationApproved`/
   `ValidationRejected`/`ValidationCancelled`/`ValidationArchived`/
   `ValidationDestroyed`/`DecisionCreated`/`ReportGenerated` map onto dotted
   event-bus type strings under the `knowledge.validation.*` namespace (with Decision
   and Report events nested one level deeper: `knowledge.validation.decision.created`,
   `knowledge.validation.report.generated`), matching the `knowledge.quality.*` /
   `knowledge.generation.*` pattern established by sibling packages.
3. **The Completed-vs-Approved/Rejected dual-publish decision** — the spec lists
   `ValidationCompleted` AND separately `ValidationApproved`/`ValidationRejected` as
   3 distinct named events, even though they all fire off the identical
   Reviewing→settled transition. Interpreted as: `ValidationCompleted` fires
   generically whenever Reviewing settles (either direction), and
   `ValidationApproved`/`ValidationRejected` fire as the more specific event for the
   _same_ transition. `approve()` publishes `DecisionCreated`, then
   `ValidationCompleted`, then `ValidationApproved`, in that order (and symmetrically
   for `reject()`) — 3 events per settle operation, satisfying the spec's literal
   11-event list without inventing a state that doesn't exist.
4. **Approved/Rejected dual-terminal-ish-state Lifecycle design** — see "Decision
   Lifecycle" above for the full transition table and BFS-reachability verification.
5. **Decision-vs-Report-vs-Finding-vs-ResultMetadata modeling** — see "Domain Model"
   above.
6. **Resolver shape** — one `KnowledgeValidatorResolver` class with 5 method-group
   pairs (Validation, Rule, Policy, Configuration, Decision) rather than 5 separate
   classes, matching every prior sibling package's convention for multi-named
   "Resolvers." Verified method-pair naming (`resolveX`/`tryResolveX`, plus batch
   `resolveRules`/`tryResolveRules` for Rule) directly against
   `@aos/knowledge-quality`'s real resolver source before writing tests against it.
7. **Future Readiness interpretation** — 2 additional single-purpose interfaces:
   `IEmbeddingManagerValidator` for 005.7N (embed a settled Report — mirrors
   `IEmbeddingManagerQuality` from the quality-engine precedent) and
   `IKnowledgeGraphValidator` for 005.7O (link a settled Validation into a future
   knowledge graph — a new, genuinely-obviously-needed contract this package
   introduces since 005.7O did not yet exist as a named downstream phase in any prior
   sibling's Future Readiness section, but is explicitly named in this task's Future
   Readiness list). No implementation of either; both live only as interfaces in
   `contracts/` and optional config fields on `KnowledgeValidatorConfig`.
8. **Token prefix chosen** — `kval_` (Knowledge VALidator), confirmed collision-free
   against every existing prefix in the codebase (`ptok_`, `stok_`, `ksrc_`, `kver_`,
   `kpol_`, `kmkt_`, `kgen_`, `kqua_`, `ktok_`, `rtok_`).
9. **The triple "Validation" naming distinction** — see "Pipeline" above; documented
   explicitly in code comments in `pipeline/knowledge-validator-pipeline.ts`,
   `validator/validation-validator.ts`, and `validator/knowledge-validator-validator.ts`
   to avoid the three being mistaken for duplicated or redundant scope.
10. **Validator "Audit" stage vs. Pipeline "Audit" stage distinction** — Stage 12 of
    the 12-stage Validator (`AuditValidator`) is a pre-flight field check
    (`requestedBy` actor present, `createdAt` well-formed) run BEFORE an operation
    executes; the Pipeline's own Stage 9 "Audit" is the post-flight side effect that
    APPENDS the actual `KnowledgeValidationAudit` entry after the operation completes.
    Same distinction `@aos/knowledge-quality` documented for its own Validator-stage-
    vs-Pipeline-stage Audit overlap.
11. **Policy, Rule, and Job have no Registry bucket** — the spec's 8-bucket list has
    no slot for Policy or Job (Rule DOES get a bucket, since the spec explicitly names
    "Rule Registry"); Policy and Job are modeled as dedicated Maps instead (see
    "Registry" above) — a documented judgment call, contrasting with
    `KnowledgeValidationConfiguration`, which DOES get a bucket since the spec
    explicitly names "Configuration Registry."
12. **`decisionProvider` config field with no automatic invocation** — unlike
    `provider`, which `start()` automatically invokes when configured,
    `decisionProvider` (`IKnowledgeValidationDecisionProvider`) is declared as a
    config field and exposed via `hasDecisionProvider()`, but no façade method calls
    `decisionProvider.decide()` automatically. This is deliberate: `approve()`/
    `reject()` already require an explicit `DecisionInput` parameter per their own
    method signatures (the spec's Validation Operations description for
    `approve(token, decision)`/`reject(token, decision)` names `decision` as a direct
    parameter, not something the package resolves on the caller's behalf) — a caller
    wanting provider-driven decisions calls `decisionProvider.decide()` themselves
    and passes the result into `approve()`/`reject()`. Documented as Technical Debt
    above since a future revision could offer a convenience wrapper.
13. **Statistics keyed by Validation Category, not Rule Category** — see "Statistics"
    above; a single Validation always has exactly one Request-level Category but may
    resolve many Rules spanning several Categories, so Category is the natural
    per-record statistics key (mirrors `@aos/knowledge-quality`'s Mode-keying).
14. **`KnowledgeValidation.settledAt` as one shared field for both outcomes** — rather
    than separate `approvedAt`/`rejectedAt` fields, the domain schema uses a single
    `settledAt` timestamp stamped on the transition into either `Approved` or
    `Rejected` (which outcome occurred is always derivable from `state` itself, so a
    second timestamp field would be redundant).
