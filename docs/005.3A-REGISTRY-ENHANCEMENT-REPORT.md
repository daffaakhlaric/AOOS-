## 4. Dependency Graph Baru (New Dependency Graph)

`RegistryKindGraph` (`src/bootstrap/registry-kind-graph.ts`) reuses the already-tested
`DependencyGraph` engine at Registry-**kind** granularity instead of reimplementing cycle
detection:

```
AGENT           → CAPABILITY
AGENT_BLUEPRINT → CAPABILITY, TOOL
CAPABILITY      → TOOL
TOOL            → CONNECTOR
SOLUTION_PACK   → INDUSTRY, AGENT, WORKFLOW, TOOL, CAPABILITY
```

`Provider Registry` and `External System` from the source prompt's chain are not modeled —
neither is a Registry kind (nothing to register), so the chain is validated up to `CONNECTOR`.

Two capabilities beyond `DependencyGraph.check()`:

- **Duplicate ID** — `RegistryKindGraph.audit(system)` scans every Registry's entries and
  flags any id that appears under more than one Registry kind.
- **Invalid Version** — an opt-in `"id@range"` convention in cross-reference fields (e.g.
  `required_tools: ["kie@^2.0.0"]`) is checked against the target's actual registered
  version via the existing `VersionChecker`. Plain ids (no `@`) are untouched, so no
  existing manifest is affected.

`validateKindGraph()` currently returns `ok: true` (no cycles, no missing kinds) — verified
by test.

## 5. Capability Namespace

`src/contracts/capability-namespace.ts` — 21 fixed namespaces (`inventory`, `crm`,
`customer`, `sales`, `marketing`, `ads`, `social`, `calendar`, `communication`, `workflow`,
`reasoning`, `planning`, `analytics`, `memory`, `knowledge`, `permission`, `tool`,
`connector`, `dashboard`, `system`, `tenant`), no duplicates (asserted by test).

Enforced by `capabilityNamespaceRule`, a `BusinessRule` wired into `createCapabilityRegistry()`
only — every other Registry kind is unaffected:

- A Capability id's dot-prefix must be one of the 21 namespaces.
- A declared `namespace` field, if present, must match the id's own prefix.

**Compatibility note:** this rule is new validation logic applied to a Registry kind
(`CAPABILITY`) that previously had none beyond schema shape. It is a deliberate, in-scope
tightening requested explicitly by Enhancement 5 ("Namespace harus tervalidasi"). It does
not affect any other Registry kind's validation behavior.

## 7. Migration Report

No migration is required for existing manifests or call sites — every change is additive
and optional. Two adjustments were made, both confined to this package's own test suite
(not shipped runtime behavior):

1. `test/registry/kinds/all-kinds.spec.ts`'s pre-existing Capability fixture id
   `content_generation` was renamed to `marketing.generate_content` because the new,
   explicitly-requested namespace rule (Enhancement 5) rejects unqualified Capability ids.
   Any real Capability manifest registered before this enhancement that lacks a namespace
   prefix will now fail validation on (re-)registration — this is intentional per
   Enhancement 5's own text ("Namespace harus tervalidasi") and is the one place this
   enhancement tightens behavior for a specific Registry kind rather than staying purely
   additive. No other Registry kind is affected.
2. Any caller that wants Duplicate-ID / Invalid-Version / kind-level Cycle checking can
   opt in via `new RegistryKindGraph().audit(registrySystem)` — nothing calls this
   automatically, so no existing code path changes behavior.

## 9. Known Limitations

- **Capability execution is not implemented** — `ICapabilityResolver` is an interface only,
  per the explicit instruction to defer this to ENGINEERING TASK 005.8.
- **Connector Runtime is not implemented** — no HTTP/gRPC/WebSocket call is ever made; the
  enriched Connector manifest (authentication, rate limit, retry policy, etc.) is metadata
  only.
- **No Marketplace and no Installer** — Solution Pack is a manifest bundle; nothing
  installs, licenses-checks, or publishes it.
- **No AI Gateway** — Model Profile is a benchmark/pricing record; nothing routes a real
  request based on it.
- **`"id@range"` version pins are opt-in and undocumented outside this report** — no
  existing manifest uses this convention; `RegistryKindGraph.audit()` is the only consumer.
  A future task should decide whether to promote this into `CROSS_REFERENCE_MAP` itself or
  keep it as an audit-only convention.
- **Duplicate-ID detection is advisory, not enforced** — `RegistryKindGraph.audit()` reports
  cross-kind duplicate ids but nothing blocks registration when one occurs; the same id can
  validly exist in two different Registry kinds today (e.g. a Tool and a Workflow that
  happen to share an id) since ids are only required to be unique **within** a kind.
- **Event Bus was not implemented**, per the explicit instruction in both 005.3 and 005.3A.
