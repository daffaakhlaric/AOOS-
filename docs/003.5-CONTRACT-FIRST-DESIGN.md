## 1. Contract Philosophy

### 1.1 Why Contract-First

AOS is built by many independent producers over time — human engineers, AI coding agents (Claude Code/Fabel AI), code generators, and eventually tenant-facing configuration tools — all of whom must agree on _what a valid Agent, Tool, Workflow, or Event looks like_ before any of them writes a single line of implementation. A contract written after the fact merely documents accidents of implementation; a contract written first is a design decision that implementation is then held accountable to. Constitution RULE-005 through RULE-009 already declare that Agents/Tools must be plugins with explicit schemas — this document is where those schemas are actually specified.

### 1.2 Why Interface Matters More Than Implementation

Constitution §3.11 (Hexagonal Architecture) and §2.5 (Dependency Inversion) already establish that the codebase must depend on abstractions, not concretions. A Contract _is_ that abstraction, made concrete enough to validate against but abstract enough to outlive any one implementation language, LLM provider, or framework choice. An Agent implemented in TypeScript today and re-implemented in a different runtime in three years is _the same Agent_ if — and only if — it satisfies the same Contract. Implementation is disposable; the Contract is durable.

### 1.3 Why Runtime Must Follow Contract, Not the Reverse

If runtime behavior were allowed to define the contract implicitly (i.e., "the contract is whatever the code currently does"), every refactor would silently change the platform's guarantees — exactly the failure mode Constitution §1.9 ("no silent failure") and RULE-106 (no silent constitutional violation) exist to prevent. By fixing the Contract first, any runtime behavior that diverges from it is unambiguously a _bug_, not a _feature interpretation_.

### 1.4 Why Contract Enables Code Generation

Every Contract in this document is expressed as JSON Schema (machine-readable, tool-agnostic) plus a YAML mirror (human-editable, diff-friendly, matching Constitution RULE-019's "Registry as declarative YAML"). This dual form is deliberately code-generation-ready: SDK client stubs, Registry validation middleware, Dashboard form generation, and API request/response types can all be mechanically derived from these schemas in a later implementation phase, with the schema — not hand-written code — as the source of truth.

### 1.5 Relationship to Constitution, Architecture, and DDD

```
001 Constitution  ──"how code must behave"──▶  governs every Contract's invariants (RULE-### citations throughout)
002 Architecture  ──"what systems exist"────▶  each Contract corresponds 1:1 to an Architecture §-numbered pillar
003 DDD           ──"what the business is"──▶  each Contract's fields are the formal schema of a DDD Entity/Event/VO
003.5 Contract     ──"what is valid"────────▶  THIS document — the enforceable, machine-checkable layer between DDD's
                                                 conceptual model and the eventual Core Runtime implementation
```

A Contract that cannot be traced to a Constitution RULE, an Architecture section, and a DDD concept is out of scope for this document and must not be added without first amending the upstream document it would otherwise contradict.

## 20. Schema Methodology

Every Contract in §2–19 ships exactly six artifacts, following one uniform pattern so tooling (validators, codegen, CI) can treat all 18 Contracts identically:

| Artifact                   | Location                          | Purpose                                                                                                                        |
| -------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1. Markdown Specification  | `contracts/<name>.contract.md`    | Human-readable authority: field table, lifecycle, invariants, cross-contract relationships                                     |
| 2. YAML Schema             | `schemas/<name>.schema.yaml`      | Diff-friendly, human-editable machine schema (JSON Schema dialect, YAML-serialized)                                            |
| 3. JSON Schema             | `schemas/<name>.schema.json`      | Canonical machine-validated schema for runtime/CI tooling                                                                      |
| 4. Valid Payload Example   | `examples/<name>.valid.json`      | A complete, schema-conformant instance                                                                                         |
| 5. Invalid Payload Example | `examples/<name>.invalid.json`    | An instance annotated with its specific violations, one per applicable Validation Rule                                         |
| 6. Validation Rules        | `validation/<name>.validation.md` | Numbered, severity-tagged rules (`VAL-###`), each traceable to a Constitution RULE, Architecture section, or DDD Business Rule |

The YAML and JSON Schema files are semantically identical (the YAML is the JSON Schema dialect expressed in YAML syntax) — this is deliberate redundancy: YAML for human review/PR diffs, JSON for machine tooling, matching Constitution ADR-019's preference for declarative, dual-readable configuration.

## 23. Versioning Strategy

- **SemVer** — every Contract instance (`agent.schema.json` version _of the schema itself_, and every individual Agent/Tool/Workflow _instance's_ `version` field) follows `MAJOR.MINOR.PATCH`, per Constitution §21 / RULE-070.
- **Backward Compatibility** — MINOR and PATCH schema changes MUST be additive-only (new optional fields, widened enums); consumers of any Contract are tolerant readers (Constitution RULE-036 applied to Contracts generally, not just Events).
- **Migration Rules** — a MAJOR schema version bump requires: (a) both old and new schema versions published simultaneously in `schemas/`, distinguished by filename suffix (e.g., `agent.schema.v2.json`), (b) a migration note appended to the relevant `contracts/<name>.contract.md`, (c) a minimum 90-day dual-support window (Constitution RULE-071).
- **Deprecation Policy** — a Contract field marked deprecated MUST remain present and validated for at least one MAJOR version cycle before removal; deprecated fields are annotated `"deprecated": true` with a `"replacement"` pointer in the JSON Schema's `description`.
- **Contract-of-Contracts** — this master document (`003.5-CONTRACT-FIRST-DESIGN.md`) itself is versioned identically to the Constitution (doc 001 §21); amending the _set_ of Contracts (adding/removing a Contract type) is a MAJOR version event for this document.

## 25. Acceptance Criteria

A Core Runtime implementation (Volume 004 onward) is considered **Contract-Compliant** only if all of the following hold:

1. **Schema Gate** — every Agent/Tool/Workflow/Event/etc. instance is validated against its `schemas/<name>.schema.json` before being persisted to any Registry; a failing instance is rejected, never silently coerced.
2. **Validation Rule Enforcement** — every Blocking `VAL-###` rule is implemented as an automated check in the Registry publish pipeline (Constitution RULE-011–013); Warning rules surface in review tooling but do not hard-block.
3. **No Undocumented Fields** — runtime code MUST NOT read or write a field not present in the corresponding Contract's schema (`additionalProperties: false` is enforced, not advisory).
4. **Traceability** — every runtime component that claims to implement a Contract (e.g., "this is the Tool Manager") must be reviewable against that Contract's `contracts/<name>.contract.md` field-by-field before its first release.
5. **Example Parity** — the `examples/<name>.valid.json` file for every Contract MUST validate successfully against its schema in CI; the `.invalid.json` file MUST fail validation with exactly the violations listed in its `_violations` annotation — both wired as permanent regression tests.
6. **No Contract Bypass** — if an implementation detail cannot be expressed within an existing Contract, the correct action is to propose a Contract amendment (versioned per §23), never to implement outside the Contract "temporarily."
7. **Conflict Protocol Applies** — any perceived need to violate a Constitution RULE in service of a Contract requirement triggers the same Conflict Protocol as any other implementation work (Constitution §0.2).

Compliance against these criteria is a required gate before any Volume 004 Core Runtime component is declared implementation-complete.

## 26. Roadmap — ENGINEERING TASK 004: Technology Selection Record (TSR)

This Contract Specification defines _what must be true_, deliberately independent of _which technology_ makes it true. Before Core Runtime implementation begins, the following technology decisions must be recorded (not implemented) in a forthcoming `docs/004-TECHNOLOGY-SELECTION-RECORD.md`:

1. **Schema Validation Engine** — which JSON Schema validator library/runtime enforces `schemas/*.schema.json` at Registry publish time and at Agent/Tool/Workflow invocation time.
2. **Event Bus Product** — concrete choice among the categories shortlisted in Architecture §38 (e.g., Kafka-compatible vs. cloud-native pub/sub), evaluated against the Event Contract's `delay`, `dead_letter`, `priority`, and tenant-partitioning requirements.
3. **Queue Product** — concrete choice satisfying the Queue Contract's `visibility_timeout`, `throughput`, and per-tenant fairness requirements (Constitution RULE-019).
4. **Workflow Durable-Execution Engine** — build vs. adopt an existing durable execution framework capable of satisfying the Workflow Contract's `nodes`/`edges`/`compensation`/`state_machine` model with crash-resumability (RULE-029/030).
5. **Vector Database** — for Memory Contract's `SemanticMemory`/`VectorMemory` and Knowledge Contract's `Embedding`, evaluated on tenant-sharding capability and RAG retrieval latency.
6. **Primary OLTP Database** — must support the Row-Level-Security-first, database-per-tenant-escape-hatch model from DDD §25.
7. **Secrets Manager** — must satisfy Tool Contract's `authentication`/`authorization` field resolution at call time (Constitution RULE-060).
8. **Model Router Provider Abstraction** — SDK/library choice for multi-provider LLM access satisfying the Model Contract's `fallback`/`routing_policy` fields.
9. **Scheduler Engine** — cron/interval/calendar execution engine satisfying the Scheduler Contract's `misfire_policy` and tenant-timezone requirements.
10. **Observability Stack** — metrics, tracing, and logging backends satisfying the Analytics, Logging, and Health Contracts' field sets (e.g., OpenTelemetry-compatible tracing backend, Prometheus-compatible metrics store).
11. **CI/CD and Schema-Codegen Tooling** — which pipeline mechanically generates SDK types/Dashboard forms/API contracts from `schemas/*.schema.json`, and how `examples/*.json` are wired as permanent regression fixtures (§25 Acceptance Criteria #5).
12. **Simulation Sandbox Runtime** — isolation mechanism (container/process sandbox) that executes Simulation Contract scenarios against real Agent Runtime code paths without touching live external systems.

Each of these twelve decisions must be recorded in the TSR with **Context / Decision / Consequences / Alternatives Considered**, ADR-style, before any Core Runtime file listed in DDD §31 is implemented. **The TSR itself is not implemented as part of this document** — this section is the roadmap for that forthcoming, separate Engineering Task only.
