# 005.5 — Enterprise Scheduler: Closing Report

Source prompt: `docs/PROMPT-005.5-ENTERPRISE-SCHEDULER.md`. New package: `packages/scheduler`
(`@aos/scheduler`). "Scheduler bertanggung jawab menentukan KAPAN sebuah Job dijalankan...
Scheduler hanya menerbitkan Event" — this package decides timing and publishes
`scheduler.job.*` events onto `@aos/event-bus`; it never calls a Workflow/Agent/Tool
directly, and none of those Runtimes are implemented here.

`SchedulerSystem` (`bootstrap/`) wraps `Scheduler` as an `@aos/runtime-kernel` `IModule`,
mirroring `EventBusSystem` (`@aos/event-bus`) and `RegistrySystem` (`@aos/registry`) — not
yet wired into any actual Kernel bootstrap call, same readiness-not-integration posture as
those two packages.

## 3. Job Lifecycle

```
        create                              fire/tick               dispatchReady
pending ───────▶ waiting ───────────────▶ ready ───────────────▶ (external Runtime claims it)
                    │  ▲                    │
             pause  │  │ resume      start  │
                    ▼  │                    ▼
                 paused │                running
                    │   │                 │  │
             cancel │   └────completed────┘  │ complete/fail
                    ▼                         ▼
                cancelled              completed / failed
                                                │
                                       (no retryPolicyConfig)  (retryPolicyConfig set)
                                                │                        │
                                                ▼                        ▼
                                            expired                 retrying ──(timer)──▶ ready
                                                                        │
                                                              (attempts exhausted)
                                                                        ▼
                                                                    expired
```

Every arrow is a `JOB_STATE_TRANSITIONS`-checked transition (`contracts/job-state.ts`); an
invalid one raises `StateTransitionException` rather than silently succeeding.

## 4. Trigger Flow

| Trigger             | Fires when…                                                                                                                                                            |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TimeTrigger`       | Delegates to `TimerService.tick()` — every `Waiting`/`Retrying` job whose `nextFireAt` has elapsed                                                                     |
| `ManualTrigger`     | `scheduler.fireManual(jobId)` is called on a `ScheduleType.MANUAL` job in a Ready-eligible state                                                                       |
| `DependencyTrigger` | `scheduler.reportCompleted(jobId)` re-checks every job depending on `jobId`; readies any whose **every** `dependsOnJobIds` entry is now `Completed` (Chain Dependency) |
| `RetryTrigger`      | `scheduler.reportFailed(jobId, error)` computes the next retry delay from the Job's `IRetryPolicy` and moves it to `Retrying` with a new `nextFireAt`                  |

## 5. Queue Flow

`queue/` ships `MemoryQueue` (generic FIFO), `JobPriorityQueue` (5-bucket, drains Critical
→ Background), `ReadyQueue` (a named `JobPriorityQueue<string>`), and `DelayedQueue`/
`RetryQueue` (fireAt-ordered, `drainDue(asOf)`). All four are fully implemented and unit
tested standalone. `JobDispatcher.dispatch(jobId)` itself operates on one job id at a
time (Policy Pipeline → Distributed Lock), so nothing in the current `Scheduler` facade
routes through these queues yet — see Technical Debt §13.

## 6. Retry Flow

```
reportFailed(jobId, error)
  │
  ▼
transition Running → Failed, metrics.recordJobFailed(), publish FAILED
  │
  ├─ no retryPolicyConfig ──▶ expireJob() ──▶ transition → Expired, publish EXPIRED
  │
  └─ retryPolicyConfig set
       │
       ▼
     RetryTrigger.scheduleRetry(jobId, policy, error)
       attempt = (previous attempt ?? 0) + 1
       │
       ├─ attempt > maxAttempts ──▶ throws RetryExhaustedException ──▶ expireJob()
       │
       └─ attempt <= maxAttempts
            nextRetryAt = now + policy.nextDelayMs(attempt)
            transition → Retrying, retryMetadata = {attempt, maxAttempts, lastError, nextRetryAt}
            metrics.recordRetry(), publish RETRY
            (later, TimerService.tick() promotes it back to Ready once nextRetryAt elapses)
```

`ExponentialBackoffPolicy`/`LinearBackoffPolicy` mirror `@aos/event-bus`'s Retry module
exactly (same formulas, same cap semantics) — deliberately not shared as a common package
since the two domains' `IRetryPolicy`/`RetryMetadata` shapes, while structurally similar,
belong to different bounded contexts (Event delivery vs. Job execution).

## 7. Dependency Flow

- **Job Dependency**: a `ScheduleType.DEPENDENCY` schedule's `dependsOnJobIds` names one or
  more other jobs; the dependent stays `Waiting` (no `nextFireAt`) until `DependencyTrigger`
  observes every dependency reach `Completed`.
- **Chain Dependency**: `dependsOnJobIds` can itself include another Dependency job, so
  completions cascade — `DependencyTrigger.onJobCompleted()` is called for every completion,
  re-evaluating all of that job's own dependents.
- **Cycle Detection**: `validator/dependency-validator.ts` runs a DFS-with-recursion-stack
  cycle check (the same algorithm shape as `@aos/registry`'s `DependencyGraph`) over the
  merged existing-dependency graph plus the candidate job's own edges, before any job is
  ever created — a cycle is rejected at `createJob()` time, never at runtime.

```

```

All 12 namespace events from the source prompt are emitted: `created`, `updated`_,
`deleted`, `ready`, `started`, `completed`, `failed`, `retry`, `paused`, `resumed`,
`cancelled`, `expired`. (_`updated` is defined in `SchedulerJobEventType` and ready for a
future `updateJob()` method — `createJob`/`deleteJob`/pause/resume/cancel/fire/tick/report*
cover every mutation this Engineering Task's `Scheduler` API exposes; `updateJob()` itself
was judged out of scope to keep the surface area matched to what's testable end-to-end
here, see Known Limitations.)

## 9. Clock Architecture

`IClockProvider.now(): Date` is the single seam every time-dependent component reads
through — `SchedulePlanner`, `TimerService`, `ManualTrigger`, `DependencyTrigger`,
`RetryTrigger`, `InMemoryLockProvider`, `SchedulerHealth`, and `Scheduler` itself all take
a clock, never call `Date.now()`/`new Date()` directly. `SystemClock` is the real
wall-clock implementation; `MockClock` (`set()`/`advanceMs()`) is what every test in this
package uses to deterministically simulate time — including multi-day Cron searches that
would otherwise be flaky against the real clock. "Belum membuat Simulation Clock" — a
Simulation Clock (e.g. one that runs faster/slower than real time, or replays a captured
timeline) would implement the same `IClockProvider` interface without touching any
consumer.

## 10. Schedule Validation Flow

```
createJob(input)
  │
  ▼
ValidationPipeline.run(input, context)   // aggregates every issue, no short-circuit
  ├─ ScheduleValidator     — input.schedule satisfies one of the 8 scheduleSchema variants
  ├─ CronValidator         — (Cron only) expression parses via planner/cron-parser.ts
  ├─ TimezoneValidator     — schedule.timezone is a valid IANA name (Intl-checked)
  ├─ RetryValidator        — (if set) retryPolicyConfig.baseDelayMs <= maxDelayMs
  ├─ DependencyValidator   — (Dependency only) every dependsOnJobIds id exists + no cycle
  └─ TenantValidator       — (if allowedTenantIds configured) tenantId is authorized
  │
  ▼
any issues? ──yes──▶ throw ValidationException (job never created)
  │no
  ▼
SchedulePlanner.computeNextFireTime(...) → store.create(job) → publish CREATED
```

`validateBusinessHoursConfig()` (`validator/business-hours-validator.ts`) is a separate,
setup-time check (workStart < workEnd, lunch inside working hours, ≥1 work day) for a
`BusinessHoursConfig` object — not part of the per-job pipeline, since a Business Hours
policy is configured once, not per job.

## 11. Health Check

`SchedulerHealth.check()` derives 5 components from a live `SchedulerMetricsSnapshot` +
the `IClockProvider` itself:

| Component  | Degrades when…                                                    | Unhealthy when…                  |
| ---------- | ----------------------------------------------------------------- | -------------------------------- |
| Clock      | —                                                                 | `clock.now()` is an Invalid Date |
| Dispatcher | failure ratio (`jobsFailed / (jobsSucceeded + jobsFailed)`) ≥ 10% | ratio ≥ 50%                      |
| Queue      | `queueDepth` > 10,000                                             | —                                |
| Trigger    | stateless — always healthy independently                          | —                                |
| Scheduler  | the worst of the above 4                                          | the worst of the above 4         |

## 12. Metrics

`SchedulerMetricsCollector` tracks exactly the set requested: Job Created/Running/
Success/Failed (counters), Retry Count, Execution Delay (average ms between a Job's
planned `nextFireAt` and `reportStarted()`), Schedule Drift (average ms — recording hook
provided via `recordScheduleDrift()`; no caller in this Engineering Task computes a drift
value yet, see Known Limitations), Queue Depth (gauge), Scheduler Latency (average ms per
`tick()` call).

## 13. Technical Debt

- **Queue module is unwired.** `ReadyQueue`/`DelayedQueue`/`RetryQueue` are fully
  implemented and unit-tested, but `Scheduler.tick()`/`dispatchReady()` operate directly
  against `IScheduleStore` rather than routing Ready/Delayed/Retrying jobs through them.
  This mirrors `@aos/event-bus`'s own precedent (its `PriorityQueue`/`MemoryBuffer` are
  real, tested, and used only by `publishBatch()`) — the building blocks exist for a future
  high-throughput, queue-backed dispatch loop without a redesign.
- **`recordScheduleDrift()` has no caller.** The metric exists on the collector and is
  tested directly, but nothing in `Scheduler`/`TimerService` currently computes "how far a
  recurring schedule's actual fire time drifted from its ideal cadence" and calls it. A
  natural place to wire it in is `TimerService.tick()`, comparing consecutive `nextFireAt`
  values for the same job.
- **`SchedulerJobEventType.UPDATED` has no publisher.** `Scheduler` has no `updateJob()`
  method (only create/delete/pause/resume/cancel/fire/tick/report*), so the `updated` event
  name is defined but never emitted. Adding `updateJob()` is a small, additive follow-up.
- **Job/Chain Dependency completion re-check is O(dependents × dependencies) per
  completion**, with no caching across calls — acceptable at the job counts this package
  targets (in-memory, single-tenant-process scale) but would need indexing for very large
  dependency graphs.

## 14. Known Limitation

- **In-memory only.** `InMemoryScheduleStore` and `InMemoryLockProvider` are the only
  implementations of `IScheduleStore`/`ISchedulerLockProvider` — "Belum membuat
  PostgreSQL. Belum membuat Redis," per the source prompt. All state is lost on process
  restart.
- **`InMemoryLockProvider` only correctly serializes dispatch within a single Node
  process.** It satisfies the `ISchedulerLockProvider` contract so a future Redis Lock /
  PostgreSQL Advisory Lock / Kubernetes Lease can be swapped in "tanpa mengubah logika
  Scheduler," but today it does not prevent double-dispatch across multiple Scheduler
  instances.
- **`IHolidayProvider` has no real calendar.** `StaticHolidayProvider` is an explicit
  date-set only — "Belum implementasi negara. Belum implementasi API," per the source
  prompt.
- **Business Hours has no holiday awareness of its own** — `BusinessHoursPolicy` and
  `HolidayPolicy` are separate, composable policies in the `PolicyPipeline`, not merged
  into one "business day" concept.
- **`ISchedulerPolicy` ships two concrete policies** (Business Hours, Holiday); Maximum
  concurrent jobs per tenant, Blackout windows, Rate limiting, and Daily execution quota —
  named in the 005.5 addendum — are not implemented, only the interface + pipeline they'll
  plug into.
- **No Event Trigger schedule kind** — explicitly listed as future work in the source
  prompt ("Future: Event Trigger").
- **No MessagePack serializer** — `JsonSerializer` is the only `ISerializer`
  implementation, per the source prompt's explicit "Future: MessagePack."
- **Permission Interface and Audit Event (Security section) are not separately
  implemented** — every Job mutation already publishes a `scheduler.job.*` Domain Event
  (functioning as the audit trail), and Tenant Isolation is enforced via
  `TenantValidator`/`SchedulerConfig.allowedTenantIds`, but no dedicated
  `IPermissionValidator`-style port (the pattern `@aos/event-bus` established for its own
  Permission Validation) was added in this task — flagged for a future pass if per-action
  authorization beyond tenant scoping is needed.

## 15. Checklist — ENGINEERING TASK 005.6 (Workflow Runtime)

**Not implemented here, per explicit instruction ("Jangan mengimplementasikan Workflow
Runtime").** What 005.6 can build on:

- ✅ `scheduler.job.ready` is the exact signal a Workflow Runtime should subscribe to
  (via `@aos/event-bus`, namespace `scheduler.*`) to know when to start executing a Job's
  associated Workflow.
- ✅ `Scheduler.reportStarted()`/`reportCompleted()`/`reportFailed(jobId, error)` are the
  exact callback surface a Workflow Runtime should call back into once it picks a Ready Job
  up — already implemented, tested, and driving the Retry/Dependency/Expiry flows.
- ✅ `JobRecord.payload`/`metadata` are the generic, untyped carriers a Workflow Runtime can
  use to attach its own Workflow definition reference — no Scheduler contract change needed
  to add a new payload shape.
- ✅ `ISchedulerLockProvider`/`InMemoryLockProvider` are ready for a Workflow Runtime that
  also needs distributed coordination — same interface, same swap-without-refactor
  guarantee the Scheduler itself gets.
- ✅ `ScheduleType.DEPENDENCY` + `DependencyTrigger` already model "run Job B after Job A
  completes" — a Workflow Runtime can express step ordering by creating one Scheduler Job
  per Workflow step and letting Dependency scheduling sequence them, without the Workflow
  Runtime needing its own dependency graph.
- ⬜ 005.6 will need its own persistence for Workflow definitions/execution state — nothing
  in `@aos/scheduler` provides that, matching this package's own "no persistence" boundary.
- ⬜ 005.6 should decide whether Workflow step failures map to `Scheduler.reportFailed()`
  (reusing the existing Retry Policy machinery) or roll their own retry semantics at the
  Workflow level — either is possible without a Scheduler change.
