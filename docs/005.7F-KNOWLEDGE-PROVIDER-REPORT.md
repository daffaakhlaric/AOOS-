# Engineering Task 005.7F — Enterprise Knowledge Provider — Closing Report

## Summary

Delivered `@aos/knowledge-provider`, the vendor-neutral abstraction layer between the
Enterprise Knowledge Platform and every external knowledge source. Google Drive, Notion,
GitHub, Database, and SharePoint connectors — and every future connector — expose
knowledge to the platform exclusively through a Provider registered with this package.
Knowledge Engine, Knowledge Runtime, Knowledge Indexing, Knowledge Retrieval, and
Knowledge Synchronization never see a connector-specific type or SDK; they only ever see
`IKnowledgeProvider` and `ProviderMetadataRecord`. The package implements no OAuth, no
API clients, no connector SDKs, no database drivers, no synchronization, no retrieval, no
embedding, no memory, no LLM, and no provider-specific logic — only registration,
capability resolution, metadata, lifecycle, validation, and a metadata-only catalog of 28
built-in Provider definitions.

**300/300 tests passing.** Coverage: **100% statements / 99.3% branches / 100% functions
/ 100% lines** — exceeding the 95/90/95/95 threshold on every dimension. Full
workspace-wide verification (`pnpm -w lint/build/typecheck/test/format:check`) passed
clean across all 45 packages with zero regressions.

## Architecture

```
Google Drive / Notion / GitHub / Database / SharePoint Connectors
(each implements IKnowledgeProvider — none of this package's business)
        │
        ▼
KnowledgeProvider (provider/) — the public façade, composition root
        │
        ▼
KnowledgeProviderPipeline (pipeline/) — 9 fixed stages
  Validation → Capability Resolution → Configuration → Policy → Permission →
  Provider Resolution → Metadata → Metrics → Events
        │
        ▼
KnowledgeProviderResolver — resolve by Type/Category/Capability/Namespace/Source/
                             Priority/Metadata
        │
        ▼
KnowledgeProviderPolicy — real allowedCategories/deniedCategories evaluation
        │
        ▼
KnowledgeProviderManager
  ├── KnowledgeProviderRegistry   (8 generic buckets)
  ├── KnowledgeProviderSession    (Open/Resume/Close/Cancel/Expire/Renew)
  └── KnowledgeProviderStatistics (per-Category counters)
        │
        ▼
KnowledgeProviderMiddlewarePipeline — provider.use() extensibility, not auto-run
        │
        ▼
contracts/ — 14 interface-only extension points, zero implementations
definitions/ — 28 built-in Provider metadata catalog entries, zero implementations
```

`KnowledgeProvider.register()` drives the State Machine directly around one atomic
`KnowledgeProviderPipeline.run()` call — there is no separate registrar/verb class, since
the source prompt's 21-name Public API list carries no distinct name for one (unlike
005.7D's `KnowledgeRetriever` or 005.7E's `KnowledgeSynchronizer`). This is a deliberate
simplification, not an oversight.

## Provider Model

Every external system this package can ever represent is exactly one
`IKnowledgeProvider` (`contracts/i-knowledge-provider.ts`) — an `id`, a
`KnowledgeProviderCategory`, a declared capability list, and two optional lifecycle hooks
(`connect()`/`disconnect()`) this package never calls itself (that responsibility belongs
to whichever caller owns the real connection, e.g. a future 005.7G Knowledge Source
Manager). Alongside it, every Provider carries one `ProviderMetadataRecord` — the 18-field
Zod schema matching the prompt's field list exactly (ProviderId, ProviderName,
ProviderVersion, ProviderCategory, ProviderAuthor, ProviderDescription,
ProviderCapabilities, ProviderConfiguration, ProviderStatus, ProviderPriority,
ProviderPolicy, ProviderNamespace, ProviderIcon, ProviderTags, ProviderLabels,
ProviderDependencies, ProviderLicense, ProviderHomepage) — and one
`KnowledgeProviderContext` (16 fields: ExecutionToken, TenantId, WorkspaceId,
DepartmentId, Environment, ProviderId, ProviderType, ProviderVersion, SourceId,
SessionId, Namespace, Policy, Permission, Metadata, TraceId, CorrelationId).

`KnowledgeProviderCategory` covers the 13 required buckets — Document, Storage,
Repository, CMS, Database, API, CRM, ERP, Knowledge, Messaging, Filesystem, Cloud, Future
Provider — and `KnowledgeProviderCapabilityFlag` covers the 20 required flags, from
`SupportsRead` through `SupportsRelationship`.

## Registry

One generic `KnowledgeProviderRegistry` class covers all 8 required buckets — Provider,
Capability, Metadata, Category, Policy, Session, Health, Statistics — as a
`Map<Bucket, Map<string, Identified>>`. A notable deviation from every prior package in
this series: `get<T>`/`require<T>`/`list<T>` were loosened from `T extends Identified` to
an unconstrained `T`, because `ProviderMetadataRecord` (a Zod-inferred type) carries no
`.id` field, only `.providerId` — only the write methods (`register`/`replace`, which
structurally need `.id` to key the map) still require the constraint.
`KnowledgeProviderMetadata` bridges this with a private `withId()` helper that maps
`providerId → id` before storing a record.

The Registry's `STATISTICS` and `HEALTH` buckets are generic id-keyed slots for a caller
to register its own externally supplied statistics/health providers — they are distinct
from `KnowledgeProviderStatistics`'s own private internal per-Category counter map, which
this package owns and updates itself. Both satisfy the prompt's Registry requirements
without contradicting each other.

## Capability Resolution

`KnowledgeProviderCapabilities` is a small, read-only, queryable wrapper
(`has()`/`hasAll()`/`hasAny()`/`list()`/`size`) over a `ReadonlySet<CapabilityFlag>`. The
Pipeline's Capability Resolution stage (stage 2) builds one from a Provider's declared
`providerCapabilities` on every registration and records per-flag usage into
`KnowledgeProviderMetrics`; `KnowledgeProviderResolver.resolveByCapability()` reuses the
same class to filter the Registry's `PROVIDER` bucket.

## Metadata

`KnowledgeProviderMetadata` is a full CRUD-style class over the Registry's `METADATA`
bucket: `register()`, `get()`, `require()`, `update()` (rejects any attempt to change
`providerId` via `InvalidProviderMetadataException`), `list()`, `listByCategory()`,
`listByTag()`. This is distinct from `KnowledgeProviderCapabilities`, which only answers
capability-membership questions.

## Lifecycle

10 states: Registered, Validated, Configured, Connected, Ready, Synchronizing,
Disconnected, Disabled, Failed, Destroyed. Only `Destroyed` is hard-terminal
(`KNOWLEDGE_PROVIDER_TERMINAL_STATES = new Set([DESTROYED])`) — Disconnected, Disabled,
and Failed are "settled" (no longer actively progressing, tracked separately via
`KNOWLEDGE_PROVIDER_SETTLED_STATES` for health/metrics purposes) but can still transition
onward to Destroyed. This is the third package in the series to use this "single
hard-terminal state" FSM shape (following 005.7E, diverging from 005.7D's all-4-terminal
model). `KnowledgeProviderLifecycle` is a read-only, query-only companion
(`states()`/`transitionsFrom()`/`isTerminal()`/`isSettled()`) that exposes the transition
table without importing the domain module directly.

`KnowledgeProvider.register()` drives Registered → Validated → Configured → Connected →
Ready in rapid succession once the Pipeline call succeeds, publishing the `CONNECTED`
event mid-sequence and stamping `connectedAt`/`readyAt` timestamps.
`disable()`/`enable()`, `disconnect()`/`reconnect()`, and `destroy()` are explicit
imperative operations a caller invokes afterward, each publishing its matching event.

## Pipeline

9 fixed stages, no short-circuiting on non-fatal issues within a stage, but a hard throw
on the first stage that fails:

1. **Validation** — `KnowledgeProviderValidator` (8 sub-stages: ProviderId, ProviderName,
   ProviderVersion, Category, Capabilities, Configuration, Tenant, ExecutionToken) →
   throws `ProviderValidationException`.
2. **Capability Resolution** — builds `KnowledgeProviderCapabilities`, records per-flag
   usage.
3. **Configuration** — `KnowledgeProviderConfiguration.assertValid()` → throws
   `ProviderConfigurationException`.
4. **Policy** — `KnowledgeProviderPolicy.evaluate()` → throws
   `ProviderPolicyViolationException`.
5. **Permission** — optional caller-supplied `IProviderPermissionChecker` → throws
   `ProviderPermissionDeniedException`.
6. **Provider Resolution** — `KnowledgeProviderResolver.resolveById()` → throws
   `ProviderNotFoundException`.
7. **Metadata** — registers the metadata record, publishes `UPDATED`.
8. **Metrics** — records category/provider/tenant/workspace usage.
9. **Events** — Provider Lifecycle events (Registered/Connected/etc.) are published by
   the outer `KnowledgeProvider` façade, which owns the State Machine transitions they
   describe, not by the Pipeline itself.

One documented overlap: a secret-looking `providerConfiguration` is always caught by
stage 1's `ConfigurationValidator` sub-stage before the Pipeline can ever reach its own
standalone stage 3 — both layers enforce "no secrets" as defense-in-depth for different
callers (stage 1 for anyone going through the full Pipeline; the standalone
`KnowledgeProviderConfiguration.assertValid()` for any caller that invokes it directly).

## Metrics

`KnowledgeProviderMetrics` — providerCount, providerUsage, providerCategory,
capabilityUsage, workspaceUsage, tenantUsage, failureCount, healthCount,
registrationCount — the 9 required buckets, all backed by real in-memory counters
updated by the Pipeline and the façade, no stubs.

## Health

5 statuses — Healthy, Warning, Degraded, Unavailable, Unknown — matching the vocabulary
used across every package in this series. `KnowledgeProviderHealth.check()` derives
Registry health from whether anything is registered across all 8 buckets, and Provider
health from the live `failureCount / registrationCount` ratio.

## Monitoring

`KnowledgeProviderMonitor.sample()` returns one `KnowledgeProviderDashboard` combining a
Metrics snapshot and a Health report across the 7 required dashboards: Provider,
Capability, Health, Workspace, Tenant, Category, Usage.

## Technical Debt

- None accepted knowingly beyond the two uncovered defensive branches noted above.
- `KnowledgeProviderMiddlewarePipeline` is not auto-run by `register()` — a caller (or a
  future package) must invoke `provider.middleware.run()` explicitly around whatever
  operation it wants wrapped. This differs from 005.7E's `KnowledgeSynchronization`,
  which does auto-run its middleware inside `synchronize()`; the divergence was not an
  explicit design requirement of either prompt, and is documented here for future
  packages that build on both to be aware of the inconsistency.

## Known Limitations

- All 14 extension-point contracts (`IKnowledgeProvider`, `IKnowledgeProviderFactory`,
  `IKnowledgeProviderRegistry`, `IKnowledgeProviderResolver`, `IKnowledgeProviderAdapter`,
  `IKnowledgeProviderConfiguration`, `IKnowledgeProviderValidator`,
  `IKnowledgeProviderObserver`, `IKnowledgeProviderHook`, `IKnowledgeProviderCapability`,
  `IKnowledgeProviderHealth`, `IKnowledgeProviderTelemetry`, `IKnowledgeProviderMetrics`,
  `IKnowledgeProviderPolicy`) have zero implementations in this package — by design.
- The 28 `BUILT_IN_PROVIDER_DEFINITIONS` are metadata only (`id`/`name`/`category`/
  `defaultCapabilities`/`description`) — registering the matching `IKnowledgeProvider`
  connector for any one of them is entirely a future responsibility.
- `KnowledgeProviderSession` is a separate access-window ledger from the Provider
  Lifecycle State Machine — the two are not automatically kept in sync by this package.
- `knowledge.provider.metrics.updated` and `.health.changed` are declared event types but
  never published by anything in this package — no scheduled sampler exists here.
- `KnowledgeProviderResolver` starts with zero registered Providers; a caller must
  register at least one before any `resolveBy*()` call can return results.

## Readiness Checklist for 005.7G Knowledge Source Manager

This package intentionally stops at the Provider abstraction layer. The following are
explicitly **not implemented here** and are handed off as-is to 005.7G:

- [ ] Wiring real connector implementations (Google Drive, Notion, GitHub, Database,
      SharePoint, etc.) against the 28 `BUILT_IN_PROVIDER_DEFINITIONS` catalog entries.
- [ ] Calling `IKnowledgeProvider.connect()`/`.disconnect()` at the right point in a
      Source Manager's own lifecycle — this package defines the hooks but never invokes
      them.
- [ ] Any OAuth flow, credential storage, or API client construction for a concrete
      Provider — `KnowledgeProviderConfiguration` actively rejects configuration keys
      that look like secrets, so any real secret material must live entirely outside
      this package's data model.
- [ ] Driving `KnowledgeProviderMiddlewarePipeline.run()` around real Provider
      operations — the hook points exist (Validation/Permission/Policy/Tracing/Metrics/
      Lifecycle/Logging) but nothing in this package invokes them automatically.
- [ ] Emitting `knowledge.provider.metrics.updated`/`.health.changed` on a schedule — no
      sampler exists; a Source Manager (or a shared scheduler integration) would need to
      call `provider.monitorSnapshot()` periodically and publish the diff itself.
- [ ] Multi-Provider orchestration (e.g., routing a single logical knowledge source
      across several registered Providers, failover, load balancing) — this package
      resolves exactly one Provider per `providerId`/query, with no orchestration layer
      above it.

`@aos/knowledge-provider` exports everything the next phase needs to build on top of:
`KnowledgeProvider`, `KnowledgeProviderRegistry`, `KnowledgeProviderResolver`,
`KnowledgeProviderManager`, `KnowledgeProviderFactory`, the 14 extension-point contracts,
and the 28-entry built-in catalog — all contract-first, metadata-driven, event-driven,
modular, vendor-neutral, and strongly typed, per the source prompt's closing mandate.
