## Architecture

### Standalone / hexagonal / no-AOS-dependency design, and why

This package's most consequential architectural decision is the one the spec mandated:
`dependencies` in `package.json` is `{}`, and every `devDependency` is tooling
(`@aos/eslint-config`, `@aos/testing`, `@aos/tsconfig`, `@aos/vitest-config`) that never ships in
the built artifact. To make that possible without becoming an island unable to integrate with the
rest of AOS, three seams were built entirely inside this package:

1. **`KnowledgeGraphException`** (`errors/knowledge-graph-exception.ts`) — a self-contained base
   exception class mirroring `@aos/errors`' `AosError` in shape (`code`, `message`, `cause`,
   `context`) without extending it.
2. **`IKnowledgeGraphEventPublisher`** (`contracts/`) — a one-method local port
   (`publish(eventType, payload)`) instead of importing `@aos/event-bus`'s `IPublisher`.
   `InMemoryEventPublisher` (listener registry + inspectable history) is the default; a host
   application wanting the real AOS event bus writes a trivial adapter.
3. **`IKnowledgeGraphModule`** (`contracts/`) — a structural equivalent of
   `@aos/runtime-kernel`'s `IModule` (`id` + `start()` + `stop()`). `KnowledgeGraphSystem`
   implements it directly; any kernel that duck-types against that shape can host it with zero
   compile-time dependency.

The payoff: this package can be adopted first (before any kernel/event-bus wiring exists) or
survive last (if everything else is stripped out), because relationship data is more durable
than any particular runtime's plumbing.

### Layered structure

```
application/  KnowledgeGraph facade — composition root, the one class most consumers touch
     │  composes
manager/      5 Managers, each owning one slice of the ~35 Graph Operations
     │  every mutating op runs through
pipeline/     GraphOperationPipeline — 7 fixed stages, wrapped by middleware/
     │  operates on
graph/        GraphEngine — the real adjacency-indexed in-memory graph data structure
     │  algorithms consume GraphEngine via
traversal/ analytics/ reasoning/   pure algorithm modules (BFS/DFS/shortest-path/
                                    cycle-detection/connected-components/dependency-reasoning)
     │  state lives in
registry/     6 id-keyed Registry buckets (no scan-based lookups)
     │  built by
factory/      GraphFactory, GraphSnapshotFactory, KnowledgeNodeFactory, KnowledgeEdgeFactory
     │  wired at

```

`domain/`, `contracts/`, `errors/`, `events/`, `metrics/`, `monitoring/`, `statistics/`,
`configuration/`, `infrastructure/`, `edges/`, `nodes/`, `relationships/`, `queries/`, and

## Domain Model — the 12 Graph Domain aggregates

`KnowledgeNode`, `KnowledgeEdge`, `KnowledgeGraph`, `GraphRelationship`, `GraphTraversal`,
`GraphPath`, `GraphCluster`, `GraphSnapshot`, `GraphVersion`, `GraphStatistics`, `GraphMetrics`,
`GraphConfiguration` — all real interfaces in `src/domain/`, each backing at least one runtime
module (factory, algorithm, or manager) that constructs or consumes it; none are unused stubs.

`KnowledgeGraph` itself is a mutable aggregate (`Map<string, KnowledgeNode>` +
`Map<string, KnowledgeEdge>`) wrapped by `GraphEngine`, which is the _only_ place adjacency
bookkeeping (`Map<nodeId, Set<edgeId>>` outgoing/incoming indexes) lives — every algorithm module
consumes `GraphEngine`'s O(1) adjacency accessors rather than re-deriving them.

## Node/Edge Type catalogue

- **18 Node Types**: `Knowledge, Document, Chunk, Embedding, Memory, Prompt, Agent, Workflow,
Capability, Tool, Connector, Organization, Department, Role, Employee, BusinessProcess,
SolutionPack, Custom`.
- **20 Edge Types**: `DependsOn, Uses, Calls, References, Generates, Consumes, Owns, Contains,
Extends, Implements, RelatedTo, ChildOf, ParentOf, DuplicateOf, DerivedFrom, VersionOf,
BelongsTo, AssignedTo, ManagedBy, Custom`.

Both enums ship a type guard (`isKnowledgeNodeType`/`isKnowledgeEdgeType`) and `Custom` requires
`customTypeLabel` (enforced by the factories, not just documented).

Four edge-type semantic families drive real pipeline behavior (`edges/edge-type-semantics.ts`):

- `HIERARCHICAL_EDGE_TYPES` (`DependsOn, ChildOf, ParentOf, Contains`) — the DAG-shaped family the
  Cycle Detection stage guards.
- `DEPENDENCY_EDGE_TYPES` (`DependsOn, Uses, Calls, References`) — the family `ReasoningManager`
  walks for dependency/dependent/impact analysis.
- `INVERSE_EDGE_TYPE_PAIRS` (`ChildOf ↔ ParentOf`) — Relationship Validation rejects an edge that
  contradicts an existing inverse edge between the same node pair.
- `SINGLE_TARGET_EDGE_TYPES` (`VersionOf, DuplicateOf, DerivedFrom`) — Relationship Validation
  rejects a second outgoing edge of these types from the same source node.

## Graph Operations

Create/Delete/Clone/Snapshot/Restore/Merge Graph · Create/Update/Delete/Move/Copy/Find(Node,
Nodes) · Create/Update/Delete/Find(Edge, Edges) · Connect/Disconnect/RelationshipExists ·
Breadth First Search/Depth First Search/Shortest Path/Find Neighbors/Find Ancestors/Find
Descendants/Sub Graph · Find Dependencies/Find Dependents/Impact Analysis · Cycle
Detection/Connected Components/Graph Validation/Graph Statistics — all ~35 operations from the
spec are implemented, catalogued as `GraphOperationType` (`pipeline/graph-operation-type.ts`),
and reachable from a Manager.

## The 7-stage Pipeline

Every mutating Graph Operation runs through exactly one `GraphOperationPipeline.execute()` call
composing 7 independently-testable stage functions:

1. **Validation** (`validation-stage.ts`) — runs the operation-specific `descriptor.validate()`
   callback (throws `GraphValidationException` on bad input) plus a generic check that any
   proposed edge names a real `KnowledgeEdgeType`.
2. **Authorization** (`authorization-stage.ts`) — delegates to the resolved configuration's
   `IGraphAuthorizationChecker`; throws `GraphAuthorizationException` on denial. Defaults to
   `PermissiveAuthorizationChecker` (allow-all) since this package has no identity model of its
   own.
3. **Relationship Validation** (`relationship-validation-stage.ts`) — enforces the inverse-pair
   and single-target-cardinality rules described above; throws `RelationshipValidationException`.
   Tolerant when `strictRelationshipValidation` is `false`.
4. **Cycle Detection** (`cycle-detection-stage.ts`) — for a proposed edge whose type is in the
   resolved `cycleCheckedEdgeTypes` (default: `HIERARCHICAL_EDGE_TYPES`), runs a real BFS
   reachability check (`wouldCreateCycle`, in `analytics/cycle-detection.ts`) asking "can the
   target already reach the source?" and throws `CycleDetectedException` if so — this genuinely
   runs _before_ the edge is committed, verified by
   `test/pipeline/graph-operation-pipeline.spec.ts`'s
   `"rejects a cycle-introducing edge before Execution, and accepts a valid one"` test and by
   `test/manager/hierarchical-edge-cycle-guard.spec.ts`'s per-hierarchical-type coverage.
5. **Execution** (`execution-stage.ts`) — calls `descriptor.execute()`, the real operation.
6. **Metrics** (`metrics-stage.ts`) — calls `descriptor.recordMetrics?.(output)`.
7. **Events** (`events-stage.ts`) — calls `descriptor.emitEvents?.(output)`.

`GraphOperationPipeline` (`pipeline/graph-operation-pipeline.ts`) composes the 7 stages and wraps
the whole run in caller-supplied `PipelineMiddleware`s (`middleware/`) using a classic onion
composition (`reduceRight`) — `LoggingMiddleware` records a success/failure entry per call,
`TimingMiddleware` records per-operation duration samples for `KnowledgeGraphMonitor`.

## Registry — 6 buckets, id-keyed, no scan-based lookups

`GraphRegistry`, `NodeRegistry`, `EdgeRegistry`, `RelationshipRegistry`, `SnapshotRegistry`,
`ConfigurationRegistry` — each backed by a generic `RegistryBucket<T>` (a single `Map`, so
`register`/`get`/`has`/`remove` are O(1)). `NodeRegistry`/`EdgeRegistry` are **global** (keyed by
node/edge id across every graph, carrying `{ graphId, node|edge }`) so a caller can resolve "which
graph is node X in" without scanning `GraphRegistry`'s contents — `KnowledgeGraphManager` keeps
them in sync on every node/edge mutation, including cascade deletes from Delete Node / Move Node.
(Graph algorithms in `traversal/`/`analytics/`/`reasoning/` do scan a _single graph's_ internal
adjacency structure — that is expected traversal behavior, not a Registry-lookup violation.)

## Manager — distribution of the ~35 Graph Operations across the 5 Managers

- **`KnowledgeGraphManager`** — Create/Delete/Clone/Snapshot/Restore/Merge Graph; Node CRUD
  (Create/Update/Delete/Move/Copy/Find Node/Find Nodes); Edge CRUD (Create/Update/Delete/Find
  Edge/Find Edges); Sub Graph extraction (implemented here since it registers a brand-new graph,
  the same lifecycle concern as Clone/Merge — exposed to callers via `TraversalManager.subGraph`,
  which delegates rather than duplicating the registration logic).
- **`RelationshipManager`** — Connect, Disconnect, Relationship Exists, plus
  `listRelationshipsForNode`/`listRelationshipsByType`. `connect`/`disconnect` delegate to
  `KnowledgeGraphManager.createEdge`/`deleteEdge` so they run through the identical 7-stage
  pipeline (including Relationship Validation and Cycle Detection) rather than re-implementing
  edge mutation a second time.
- **`TraversalManager`** — Breadth First Search, Depth First Search, Shortest Path, Find
  Neighbors, Find Ancestors, Find Descendants, Sub Graph. Every traversal call records its
  duration into `KnowledgeGraphMonitor` and bumps the Traversal Count metric.
- **`AnalyticsManager`** — Cycle Detection, Connected Components, Average Degree, Graph
  Validation, Graph Statistics. Refreshes the `averageDegree`/`connectedComponents`/`cycleCount`
  metrics gauges on every call so `GraphMetrics` snapshots stay current without a background
  poller.
- **`ReasoningManager`** — Find Dependencies, Find Dependents, Impact Analysis, all defined over
  `DEPENDENCY_EDGE_TYPES`.

All 5 share one `GraphSystemContext` (`manager/graph-system-context.ts`) — the composition-root
bundle of every registry, factory, the pipeline, the event publisher, the metrics collector, and
the monitor — built once by `KnowledgeGraph` (the facade) or `createGraphSystemContext` directly
for manual wiring.

## Traversal algorithms implemented

- **BFS** (`breadth-first-search.ts`) — queue-based, `O(V + E)` on the reachable subgraph, visits
  in shallowest-first order, supports `edgeTypes` filter and `maxDepth` bound.
- **DFS** (`depth-first-search.ts`) — iterative with an explicit stack (no recursion-depth risk on
  large graphs), same `O(V + E)`, same filter/bound support.
- **Shortest Path** (`shortest-path.ts`) — unweighted BFS with predecessor tracking, `O(V + E)`.
  Edge weights are intentionally ignored: this domain's meaningful notion of "distance" is fewest
  hops, and unweighted BFS is simpler and always-correct for that; Dijkstra was considered and
  rejected as unnecessary complexity for a relationship graph, not because it's harder to
  implement.
- **Find Neighbors** (`find-neighbors.ts`) — direct (depth-1) neighbors, deduplicated, with
  `outgoing`/`incoming`/`both` direction and edge-type filter.
- **Find Ancestors / Find Descendants** (`find-ancestors-descendants.ts`) — BFS flood-fill over
  the incoming/outgoing direction respectively, `O(V + E)`.
- **Cycle Detection** (`analytics/cycle-detection.ts`) — DFS with recursion-stack coloring
  (white/gray/black), reports every back-edge-closed cycle as the recursion-stack slice, `O(V +
E)`. `wouldCreateCycle` is the pipeline-facing reachability check (plain BFS from the proposed
  target, asking whether it can reach the proposed source).
- **Connected Components** (`analytics/connected-components.ts`) — union-find with path
  compression, treating edges as undirected (the standard "weak connectivity" definition for a
  directed graph), `O((V + E) · α(V))`.
- **Graph Merge** (`graph/graph-merge.ts`) — real union of two graphs' nodes/edges with a
  documented conflict-resolution rule (`"keep-target"` default / `"keep-source"` /
  `"merge-metadata"` shallow-merge), idempotent on re-merge (functional-key deduplication for
  edges: `type:source:target`).
- **Clone / Snapshot / Restore** — `GraphEngine.clone()` and `GraphSnapshotFactory` both use
  `utils/deep-clone.ts` (a hand-rolled recursive structural clone covering plain objects, arrays,
  `Map`, `Set`, and primitives) so a snapshot or clone can never be retroactively corrupted by
  later mutation of the live graph.

## Metrics (8) and Monitoring (5)

**Metrics** (`KnowledgeGraphMetricsCollector`): Graph Count, Node Count, Edge Count, Relationship
Count, Traversal Count, Average Degree, Connected Components, Cycle Count. Counters are cumulative
process-lifetime counts (with floor-at-zero decrements); the last three are gauges refreshed by
`AnalyticsManager`/`TraversalManager` calls.

**Monitoring** (`KnowledgeGraphMonitor`): Health (every registered graph passes structural
validation — no dangling edges, no self-loops), Performance (average traversal duration across
every recorded sample), Traversal Time (alias for the same figure), Memory Usage (`process
.memoryUsage().heapUsed`, `0` in environments without `process`), Graph Size (node/edge count for
a specific graph).

## Statistics

`GraphStatisticsService` (`statistics/`) is a thin service boundary in front of
`analytics/graph-statistics-calculator.ts`'s `calculateGraphStatistics`, kept as its own folder
(per the spec's package structure) so statistics _exposure_ concerns stay separate from the raw
_algorithms_ in `analytics/`.

## Technical Debt

- **Merge conflict testing requires bypassing `NodeRegistry`.** `NodeRegistry`/`EdgeRegistry`
  enforce id uniqueness _globally_ (not per-graph), which is the right invariant for O(1)
  cross-graph lookup — but it means two nodes with the same id can never coexist in two different
  graphs _if both were created via `KnowledgeGraphManager.createNode`_. The conflict scenario
  `mergeGraph`'s `"keep-target"/"keep-source"/"merge-metadata"` resolution exists to handle can
  therefore only arise from graphs assembled independently of the manager (e.g. two
  independently-built `GraphEngine`s later merged, or a graph rebuilt from an externally-modified
  snapshot) — documented and exercised directly at the `GraphEngine`/`mergeGraphs` level in
  `test/graph/graph-merge.spec.ts`, and at the manager level in
  `test/manager/knowledge-graph-manager-edge-cases.spec.ts` by seeding the conflict via direct
  `GraphEngine.addNode` calls rather than `manager.createNode`.
- **`GraphValidationReport`/`GraphValidationIssue` and `CycleDetectionResult` are exported as
  types but their producing functions (`validateGraph`, `detectCycles`) are internal** —
  consumers reach them through `AnalyticsManager.graphValidation`/`cycleDetection`, which is the
  intended path; the raw functions are not part of the curated public surface.

## Known Limitations

- In-memory only, by design (spec requirement) — process restart loses all graph state; no
  persistence adapter is provided or implied.
- `GraphConfiguration.maxTraversalDepth` is resolved and validated (`ConfigurationService`) but is
  not yet threaded into `TraversalManager`'s BFS/DFS calls as a default `maxDepth` — callers must
  pass `maxDepth` explicitly per call today. Left this way because the spec does not require an
  implicit global depth ceiling, and making one implicit risked silently truncating a caller's
  traversal without their opting in.
- `GraphStatistics.computedAt`/`GraphValidationReport.validatedAt` use `Date.now()` directly
  rather than the injectable `utils/clock.ts#now()` — a minor inconsistency with the rest of the
  codebase's clock-injection convention, harmless since neither value is asserted against a fixed
  clock in tests (only "is a number" is asserted).

## Numbered list of other non-obvious design/judgment calls

1. **`RelationshipManager` delegates to `KnowledgeGraphManager` rather than owning edge mutation
   itself** — avoids two parallel, potentially-diverging code paths for "create an edge."
2. **`TraversalManager.subGraph` delegates to `KnowledgeGraphManager.extractSubGraph`** rather
   than each Manager independently registering new graphs — same reasoning as (1); the
   traversal-shaped grouping in the spec/orchestrator instructions is honored at the _manager
   API_ level without duplicating graph-lifecycle bookkeeping.
3. **Delete Node and Move Node's cascade-deleted edges now decrement `edgeCount`/
   `relationshipCount` in the Metrics stage**, not just the registries — an early draft only
   removed the cascaded edges from `EdgeRegistry`/`RelationshipRegistry` without telling the
   metrics collector, which would have let the `edgeCount` gauge silently drift from the graph's
   actual edge count after any cascade delete. Caught by
   `test/metrics/metrics-manager-integration.spec.ts` and fixed in `knowledge-graph-manager.ts`.
4. **Copy Node does not copy the source node's edges.** An edge connects two _specific_ node
   instances within one graph; blindly copying edges alongside a copied node would either dangle
   (if the copy lands in a different graph without the neighbor) or silently duplicate
   relationships (if copied within the same graph). Documented in the method's JSDoc and verified
   by `test/manager/knowledge-graph-manager.spec.ts`'s copyNode test.
5. **Move Node cascades (removes) the node's incident edges from the source graph** rather than
   trying to carry them to the destination graph, for the same reason as (4) — an edge's other
   endpoint may not exist in the destination graph.
6. **`GraphOperationDescriptor` is a generic, operation-agnostic shape** (`validate`, optional
   `relationshipCandidate`/`checkCycles`, `execute`, optional `recordMetrics`/`emitEvents`) rather
   than one bespoke pipeline-input type per operation. This keeps `GraphOperationPipeline` itself
   tiny and reusable across all ~35 operations, at the cost of each Manager method being
   responsible for supplying the right callbacks — judged the better tradeoff since the pipeline
   is exercised uniformly by every mutating call, and the alternative (one pipeline variant per
   operation) would have meant 35 near-duplicate orchestration classes.
7. **`Contains` is treated as hierarchical (DAG-shaped, cycle-checked) but not single-target** —
   a container can contain many things (so not single-target), but "A contains B contains A" is
   nonsensical (so cycle-checked). `ChildOf`/`ParentOf` are the inverse-pair _and_ hierarchical,
   but not single-target (a node can have many children, though — see (8) — cardinality on the
   _parent_ side isn't enforced by this package; only the literal single-target types are).
8. **Single-target cardinality is enforced per source node, not semantically "at most one parent"
   for `ChildOf`.** The spec's `SINGLE_TARGET_EDGE_TYPES` judgment call scoped this to
   `VersionOf`/`DuplicateOf`/`DerivedFrom` (a node is a version/duplicate/derivation of _at most
   one_ other node) rather than also constraining `ChildOf` to one parent, since a legitimate
   multi-parent hierarchy (e.g. a Capability used by two Departments) would otherwise be
   incorrectly rejected.
9. **`InMemoryEventPublisher.getHistory()` is unbounded** — no ring-buffer/rolling eviction. Fine
   for this package's intended usage (tests, short-lived processes, or a host that periodically
   drains via `clearHistory()`); a long-running host publishing at high volume would need to call
   `clearHistory()` itself or supply its own `IKnowledgeGraphEventPublisher`.
10. **`ConfigurationRegistry` uses a sentinel key (`DEFAULT_CONFIGURATION_KEY`) rather than a
    separate "default config" field**, so it reuses the same `RegistryBucket<T>` machinery
    (`resolveFor(graphId)` = `tryGet(graphId) ?? get(DEFAULT_CONFIGURATION_KEY)`) instead of a
    bespoke two-tier lookup type.
