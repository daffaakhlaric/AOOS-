# Engineering Task 005.7G — Enterprise Knowledge Source Manager — Closing Report

## Summary

Delivered `@aos/knowledge-source-manager`, the layer that manages the **actual,
tenant-configured Knowledge Source instances** built on top of a registered
`@aos/knowledge-provider` definition. Knowledge Provider defines WHAT a provider is;
Knowledge Source Manager manages ACTUAL configured sources owned by tenants — one
Provider (Google Drive, Notion, GitHub, a database, ...) may have unlimited Sources, each
independently registered, configured, scheduled (metadata only), and governed by Policy
and Permission. The package implements no OAuth, no secrets, no connector SDKs, no Google
Drive/Notion/SharePoint/GitHub SDKs, no synchronization, no retrieval, no indexing, no
embedding, no memory, no AI, and no provider-specific logic — only registration, catalog
indexing, resolution, scheduling metadata, policy, permission, lifecycle, and validation.

**335/335 tests passing.** Coverage: **99.87% statements / 99.72% branches / 100%
functions / 99.87% lines** — exceeding the 95/90/95/95 threshold on every dimension. Full
workspace-wide verification (`pnpm -w lint`, `pnpm -w build`, `pnpm -w typecheck`,
`pnpm -w test`, `pnpm -w format:check`) passed clean across all 25 packages in the
monorepo, zero regressions.

## Architecture

```
Google Drive Provider / Notion Provider / GitHub Provider / Database Provider
(@aos/knowledge-provider — WHAT a provider is; referenced only by providerId)
        │
        ▼
KnowledgeSourceManager (manager/) — the public façade, composition root
  directly drives the Source Lifecycle State Machine around one Pipeline call
        │
        ▼
KnowledgeSourcePipeline (pipeline/) — 9 fixed stages
  Validation → Configuration → Policy → Permission → Provider Resolution →
  Registration → Catalog → Metrics → Events
        │
        ▼
KnowledgeSourceResolver — resolve by Source Id/Provider/Category/Workspace/Tenant/
                           Namespace/Collection/Policy/Permission/Metadata/Priority
        │
        ▼
KnowledgeSourceCatalog — Provider/Namespace/Collection/Workspace/Tenant Mapping
        │
        ▼
KnowledgeSourceRegistry (9 generic buckets) + KnowledgeSourceSession + KnowledgeSourceStatistics
        │
        ▼
KnowledgeSourceMiddlewarePipeline — source.use() extensibility, not auto-run
        │
        ▼
contracts/ — 13 interface-only extension points, zero implementations
```

`KnowledgeSourceManager.create()` drives the State Machine directly around one atomic
`KnowledgeSourcePipeline.run()` call — there is no separate registrar/verb class, and no
separate mid-level orchestrator class either. This is a deliberate deviation from
`@aos/knowledge-provider`, which split its equivalent responsibility between
`KnowledgeProvider` (the façade) and `KnowledgeProviderManager` (the token-keyed ledger +
Registry/Session/Statistics composition). The 005.7G prompt's Public API list has no
second name for that role, so `KnowledgeSourceManager` folds both together: it owns
`registry`, `catalog`, `session`, `statistics` directly, plus its own private
`Map<token, KnowledgeSourceExecution>` ledger — "Never scan collections. Lookup by
token."

## Source Model

Every configured Source is a `KnowledgeSource` — a concrete, read-only view class over
one `KnowledgeSourceExecution` (`instance` + `context` + `metadata` + `configuration` +
`history`). This is a genuinely new concept relative to `@aos/knowledge-provider`: there,
the top-level Public API name `KnowledgeProvider` _was_ the façade itself, with no
separate small entity class. Here, the prompt's Public API list names both
`KnowledgeSourceManager` (the façade) and `KnowledgeSource` (a distinct name), so
`KnowledgeSource` was designed as the concrete value object every façade operation
returns — `id`/`token`/`sourceId`/`category`/`providerId`/`state`/`metadata`/
`configuration`/`context`/`history` getters plus `toExecution()`.

Every Source carries one `KnowledgeSourceMetadataRecord` — the exact 24-field Zod schema
from the prompt: SourceId, SourceName, SourceDescription, SourceCategory, SourceProvider,
ProviderId, ProviderVersion, Namespace, Collection, WorkspaceId, TenantId,
OrganizationId, DepartmentId, Labels, Tags, Priority, Policy, Permission, Environment,
Owner, CreatedBy, UpdatedBy, CreatedAt, UpdatedAt — and one `KnowledgeSourceContext` (the
exact 14-field schema: ExecutionToken, SourceId, ProviderId, WorkspaceId, TenantId,
OrganizationId, DepartmentId, Environment, Namespace, Policy, Permission, Metadata,
TraceId, CorrelationId). `SourceProvider` and `ProviderId` are deliberately distinct
fields (a judgment call, since the prompt lists both without further explanation):
`SourceProvider` is the human-readable provider label a tenant sees (e.g. "Google
Drive"); `ProviderId` is the canonical identifier of the registered
`@aos/knowledge-provider` definition this Source was created from.

`KnowledgeSourceCategory` covers the 12 required buckets — Document, Repository, CMS,
Storage, Database, API, CRM, ERP, Filesystem, Cloud, Knowledge, Custom.

## Catalog

`KnowledgeSourceCatalog` — a concept 005.7F's `@aos/knowledge-provider` did not have —
was designed as a derived, secondary index over whatever Sources are registered in
`KnowledgeSourceRegistry`'s `SOURCE` bucket, not a second store of record. It maintains:

- The **Source Catalog** itself: a flat `Map<sourceId, KnowledgeSourceMetadataRecord>` —
  also satisfying the prompt's separate "Source Metadata" catalog requirement, since both
  point at the same underlying record.
- **Provider Mapping** — `Map<providerId, Set<sourceId>>`.
- **Namespace Mapping** — `Map<namespace, Set<sourceId>>`.
- **Collection Mapping** — `Map<collection, Set<sourceId>>`.
- **Workspace Mapping** — `Map<workspaceId, Set<sourceId>>`.
- **Tenant Mapping** — `Map<tenantId, Set<sourceId>>`.

`register()`/`remove()` keep all 5 mappings and the flat lookup in sync atomically; the
Pipeline's Catalog stage (stage 7) calls `register()` on every successful Source
registration. `KnowledgeSourceResolver` and `KnowledgeSourceMonitor` both read the
Catalog rather than duplicating this indexing logic.

## Registry

One generic `KnowledgeSourceRegistry` class covers all 9 required buckets — Source,
Category, Namespace, Collection, Policy, Permission, Statistics, Session, Health — as a
`Map<Bucket, Map<string, Identified>>`, structurally identical to
`@aos/knowledge-provider`'s Registry. The Pipeline's Registration stage (stage 6) stores
one combined `SourceRegistryEntry` (`{ id: sourceId, metadata, configuration }`) per
Source in the `SOURCE` bucket — a judgment call that lets the Metrics stage derive "Sync
Enabled Count" and "Schedule Count" by scanning that single bucket rather than needing a
second parallel configuration store. `KnowledgeSourceStatistics` owns its own private
per-Category counter map rather than the `STATISTICS` bucket, mirroring
`@aos/knowledge-provider`'s precedent — that bucket exists for callers registering their
own externally computed statistics providers.

## Pipeline

9 fixed stages, no short-circuiting on non-fatal issues within a stage, but a hard throw
on the first stage that fails:

1. **Validation** — `KnowledgeSourceValidator` (7 sub-stages: Source Id, Source Name,
   Provider Reference, Category, Configuration, Tenant, Execution Token) → throws
   `SourceValidationException`.
2. **Configuration** — `KnowledgeSourceConfiguration.assertValid()` → throws
   `SourceConfigurationException`.
3. **Policy** — `KnowledgeSourcePolicy.evaluate()` → throws
   `SourcePolicyViolationException`.
4. **Permission** — `KnowledgeSourcePermission.check()` → throws
   `SourcePermissionDeniedException`.
5. **Provider Resolution** — optional caller-supplied
   `IKnowledgeSourceProviderResolver.resolveProvider(providerId)`; a no-op pass-through
   when unconfigured. Deliberately interface-only — this package never imports
   `@aos/knowledge-provider` at runtime, per the prompt's "Only interface references"
   instruction (mirroring the finding, confirmed by grepping
   `@aos/knowledge-provider`'s own source, that it likewise declares its "allowed"
   Knowledge dependencies in `package.json` without importing any of them).
6. **Registration** — stores the combined `SourceRegistryEntry` in the Registry's
   `SOURCE` bucket.
7. **Catalog** — `KnowledgeSourceCatalog.register()`.
8. **Metrics** — recomputes all 10 `KnowledgeSourceMetrics` fields from the Catalog +
   Registry.
9. **Events** — publishes `knowledge.source.registered`.

One deliberate deviation from `@aos/knowledge-provider`'s Pipeline: no "failed" event is
published on a stage exception. The Source Lifecycle (see below) has no Failed state at
all, and the Events list has no matching event type — a stage exception simply propagates
to the caller without a state transition or a publish, unlike `@aos/knowledge-provider`'s
Pipeline, which does publish `FAILED` (because `KnowledgeProviderState.FAILED` and
`KnowledgeProviderEventType.FAILED` both exist there).

## Lifecycle

12 states, in the prompt's own order: Created, Registered, Configured, Validated,
Enabled, Disabled, Scheduled, Synchronizing, Paused, Archived, Deleted, Destroyed. Only
`Destroyed` is hard-terminal; Disabled/Archived/Deleted/Destroyed are "settled". The
transition table connecting all 12 states was a judgment call — the prompt lists the
states but not the edges between them (the same situation `@aos/knowledge-provider`
solved for its own 10-state lifecycle): `Created → Registered → Configured → Validated →
(Enabled | Scheduled)`; `Enabled` fans out to `Disabled/Scheduled/Synchronizing/
Paused/Archived`; `Scheduled/Synchronizing/Paused` all loop back toward
`Enabled/Disabled`; `Disabled/Archived` can re-`Enabled` or move toward `Deleted`;
`Deleted` is the only path to the hard-terminal `Destroyed`. Every one of the 12 states is
reachable from `Created` (verified by a dedicated reachability test).

`KnowledgeSourceManager.create()` drives Created → Registered → Configured → Validated in
rapid succession once the atomic Pipeline call succeeds, then onward to `Enabled` (and
stamps `instance.enabledAt`) when the supplied Configuration's `enabled` flag is `true`.
`enable()`/`disable()`, `archive()`, and `remove()` (Deleted → Destroyed, which also
clears the Catalog/Registry entries) are explicit imperative operations a caller invokes
afterward, each publishing its matching event. `KnowledgeSourceLifecycle` is a read-only,
query-only companion (`states()`/`transitionsFrom()`/`isTerminal()`/`isSettled()`).

## Configuration

"Metadata only. No OAuth. No Secret. No API Client." Support: Schedule, Namespace,
Collection, Policy, Permission, Priority, Sync Mode, Enabled, Auto Sync, Incremental,
Versioning, Retention — the exact 12-field list, modeled as
`knowledgeSourceConfigurationRecordSchema` (13 fields including the `sourceId` key
field). A judgment call: **Sync Mode reuses `KnowledgeSourceScheduleMode`**
(Manual/Cron/Interval/One Time/Future Event) rather than inventing a second, unrelated
enum, since the prompt does not enumerate Sync Mode's own values and a Source's sync
cadence is, in practice, exactly its Schedule's mode.

`KnowledgeSourceConfiguration.assertValid()` is a real, enforced runtime guard, not
documentation: Auto Sync requires Enabled; when a Schedule descriptor is present, its
`mode` must match the record's `syncMode`, and the descriptor itself must pass
`KnowledgeSourceScheduler.assertValid()`. A separate `assertValidExtraSettings()` method
(mirroring `@aos/knowledge-provider`'s `KnowledgeProviderConfiguration`) rejects any
free-form settings key that looks like a credential
(`secret`/`password`/`token`/`apiKey`/`credential`/`oauth`, case-insensitive).

## Policy

`KnowledgeSourcePolicy` evaluates every enabled, scope-matching registered
`KnowledgeSourcePolicyRecord` against a Source's `sourceCategory`
(`allowedCategories`/`deniedCategories`) — real, non-stub evaluation logic, structurally
identical to `@aos/knowledge-provider`'s `KnowledgeProviderPolicy`. This is the coarse
"may Sources of this Category exist for this tenant/workspace at all" gate.

## Permission

Unlike `@aos/knowledge-provider` (which only had a self-contained internal
`IProviderPermissionChecker` interface, no full class), the 005.7G prompt's Public API
list explicitly names `KnowledgeSourcePermission` as a top-level class distinct from
`KnowledgeSourcePolicy`. It was designed with its own real evaluation model: registered
`KnowledgeSourcePermissionGrant`s scoped to `tenantId`/`workspaceId`/`role`, each with an
`allow`/`deny` effect and an optional `namespace`/`category` narrowing. `check()`
evaluates "deny always wins" over the grants matching a Context's scope and (when
supplied) a Source's `namespace`/`category` — permissive by default when no grant matches
at all. The Pipeline runs Policy (stage 3) and Permission (stage 4) as two genuinely
separate, non-trivially-delegating evaluation steps, per the prompt's own two-stage
Pipeline listing.

## Scheduler

`KnowledgeSourceScheduler` — "Metadata only." — validates and describes a
`KnowledgeSourceScheduleDescriptor` for the 5 required modes (Manual, Cron, Interval, One
Time, Future Event): Cron requires `cronExpression`, Interval requires `intervalMs`, One
Time requires `runAt`, Future Event requires `eventName`, Manual requires none of them.
`assertValid()` throws `SourceScheduleException` for an incomplete descriptor. This class
never registers a real timer, cron job, or `@aos/scheduler` execution — no real scheduling
engine exists anywhere in this package, matching the prompt's "Metadata only" instruction
literally.

## Provider Resolver

"Resolve by Source Id, Provider, Category, Workspace, Tenant, Namespace, Collection,
Policy, Permission, Metadata, Priority" — the exact 11 dimensions.
`KnowledgeSourceResolver` reads `KnowledgeSourceCatalog`'s indexes exclusively; it owns no
Source implementation itself, and is distinct from the Pipeline's internal "Provider
Resolution" stage (which resolves a `providerId` against an injected
`IKnowledgeSourceProviderResolver`, not a Source).

## Middleware Pipeline

`KnowledgeSourceMiddlewarePipeline` — a Koa-style chain a caller extends via
`manager.use(middleware)`, with the standard double-`next()`-call guard. The 7 named
built-in slots (Validation/Permission/Policy/Tracing/Metrics/Lifecycle/Logging) are
pass-through hook points; this package registers no real tracing/logging/telemetry
behavior itself, only the extensibility mechanism — not auto-run by `create()`, the same
divergence `@aos/knowledge-provider` documented for its own Middleware Pipeline.

## Metrics

`KnowledgeSourceMetrics` — Source Count, Provider Count, Workspace Count, Tenant Count,
Namespace Count, Collection Count, Sync Enabled Count, Schedule Count, Policy Count,
Permission Count — the exact 10 required fields, all backed by real in-memory counters
recomputed by the Pipeline's Metrics stage from the Catalog and Registry, no stubs.

## Health

5 statuses — Healthy, Warning, Degraded, Unavailable, Unknown — matching the vocabulary
used across every package in this series. `KnowledgeSourceHealth.check()` derives
Registry health from whether anything is registered across all 9 buckets, and Catalog
health from whether the Catalog holds any entries (with the current count surfaced in
`details`).

## Monitoring

`KnowledgeSourceMonitor.sample()` returns one `KnowledgeSourceDashboard` combining a
Metrics snapshot and a Health report across the 8 required dashboards: Source, Workspace,
Tenant, Namespace, Collection, Provider, Health, Usage. The Workspace/Tenant/Provider
dashboards additionally break down Source counts per key (`dashboard.workspace.sources`,
etc.), derived by scanning the Catalog.

## Technical Debt

- None accepted knowingly beyond the one uncovered defensive branch noted above.
- `KnowledgeSourceMiddlewarePipeline` is not auto-run by `create()`/`enable()`/etc. — a
  caller must invoke `manager.middleware.run()` explicitly around whatever operation it
  wants wrapped, mirroring `@aos/knowledge-provider`'s own documented inconsistency with
  `@aos/knowledge-synchronization` (which does auto-run its middleware).
- `SourceRegistryEntry` (the Registration stage's combined metadata+configuration record)
  duplicates `metadata`/`configuration` that also live inside every
  `KnowledgeSourceExecution` the Manager's token ledger holds — an intentional
  denormalization so the Pipeline's Metrics stage can compute Sync Enabled/Schedule
  Counts without a dependency back onto the Manager's private ledger.

## Known Limitations

- All 13 named extension-point contracts (`IKnowledgeSource`, `IKnowledgeSourceRegistry`,
  `IKnowledgeSourceResolver`, `IKnowledgeSourceFactory`, `IKnowledgeSourceValidator`,
  `IKnowledgeSourceObserver`, `IKnowledgeSourceHook`, `IKnowledgeSourcePolicy`,
  `IKnowledgeSourcePermission`, `IKnowledgeSourceScheduler`, `IKnowledgeSourceCatalog`,
  `IKnowledgeSourceTelemetry`, `IKnowledgeSourceMetrics`) — plus the one extra
  `IKnowledgeSourceProviderResolver` this package added for Pipeline stage 5 — have zero
  implementations here, by design.
- `KnowledgeSourceResolver`/`KnowledgeSourceCatalog` ship with zero registered Sources; a
  caller must `create()` at least one Source before any `resolveBy*()` call can return
  results.
- `knowledge.source.updated`, `.metrics.updated`, and `.health.changed` are declared event
  types but never published by anything in this package — no scheduled Metrics/Health-
  diffing sampler exists here (the same limitation `@aos/knowledge-provider` documented
  for its own equivalent events).
- `KnowledgeSourceSession` is a separate access-window ledger from the Source Lifecycle
  State Machine — the two are not automatically kept in sync by this package.
- Provider Resolution (Pipeline stage 5) is a no-op unless a caller supplies an
  `IKnowledgeSourceProviderResolver` — no default adapter to `@aos/knowledge-provider` is
  wired anywhere in this package, keeping the dependency strictly interface-only.

## Readiness Checklist for 005.7H Knowledge Versioning

This package intentionally stops at the configured-Source-instance layer. The following
are explicitly **not implemented here** and are handed off as-is to 005.7H:

- [ ] Versioning any Source's Metadata/Configuration over time — this package always
      overwrites in place (`registry.replace()`); there is no history of prior
      Metadata/Configuration values beyond the State Machine's transition `history`,
      which only records lifecycle state changes, not field-level edits.
- [ ] Any diffing, snapshotting, or rollback of a Source's configuration — the
      `versioning` boolean on `KnowledgeSourceConfigurationRecord` is declared and
      validated but never acted upon; nothing in this package snapshots anything when it
      is `true`.
- [ ] Retention enforcement — `retentionDays` on `KnowledgeSourceConfigurationRecord` is
      declared and validated (must be a positive integer when present) but this package
      never expires or archives anything based on it.
- [ ] Wiring a real `IKnowledgeSourceProviderResolver` against
      `@aos/knowledge-provider`'s actual resolver — this package defines the interface
      and the optional Pipeline hook point but ships no default implementation.
- [ ] Driving `KnowledgeSourceMiddlewarePipeline.run()` around real Source operations —
      the hook points exist (Validation/Permission/Policy/Tracing/Metrics/Lifecycle/
      Logging) but nothing in this package invokes them automatically.
- [ ] Emitting `knowledge.source.updated`/`.metrics.updated`/`.health.changed` on a
      schedule — no sampler exists; a Knowledge Versioning phase (or a shared scheduler
      integration) would need to call `manager.monitorSnapshot()` periodically and
      publish the diff itself.
- [ ] Real scheduling execution against `KnowledgeSourceScheduleDescriptor` — this
      package only validates and describes Schedule metadata; actually firing a sync on
      a Cron/Interval/One Time/Future Event schedule is a future roadmap phase's
      responsibility (likely via real `@aos/scheduler` wiring).

`@aos/knowledge-source-manager` exports everything the next phase needs to build on top
of: `KnowledgeSourceManager`, `KnowledgeSourceRegistry`, `KnowledgeSourceCatalog`,
`KnowledgeSourceResolver`, `KnowledgeSourceFactory`, the 13 named extension-point
contracts, and the full Source/Metadata/Configuration/Policy/Permission/Scheduler
domain model — all contract-first, metadata-driven, event-driven, modular,
vendor-neutral, and strongly typed, per the source prompt's closing mandate.
