## 1. WDL Architecture

AOS-WDL is a **contract-first, schema-driven definition language** — every module composes
around one Zod schema (`schemas/workflow-definition.ts`), never around a runtime object:

```
                         ┌─────────────────────────┐
   Text (YAML/JSON)  ──▶ │        parser/          │ ──▶  WorkflowDefinition
                         └─────────────────────────┘         (Zod-validated,
                                     ▲                         TS-typed)
                         ┌─────────────────────────┐              │
   Text (YAML/JSON)  ◀── │       serializer/       │ ◀────────────┤
                         └─────────────────────────┘              │
                                                                   │
   Fluent API ──────────▶  builder/  ─────────────────────────────┤
                                                                   │
                                                                   ▼
                                                    ┌───────────────────────────┐
                                                    │   validator/               │
                                                    │   ValidationPipeline       │
                                                    │  (8 independent stages)    │
                                                    └───────────────────────────┘
                                                                   │
                                                                   ▼
                         ┌─────────────────────────┐   ┌───────────────────────────┐
                         │   registry/             │◀──│   bootstrap/               │
                         │  WorkflowDefinitionReg.  │   │  WorkflowDefinitionService │
                         └─────────────────────────┘   └──────────────┬────────────┘
                                     ▲                                │
                         ┌─────────────────────────┐                  ▼
                         │   versioning/           │        ┌───────────────────┐
                         │  CompatibilityChecker    │        │  events/           │
                         └─────────────────────────┘        │  workflow.definition.*│
                                                              │  → @aos/event-bus  │
                                                              └───────────────────┘
```

Design principles honored throughout: **Human readable** (YAML + JSON, both round-trip
losslessly), **Strongly typed** (every schema is `z.infer`-derived — no `any`, no untyped
`Record<string, unknown>` escape hatches except where the prompt explicitly calls for
free-form metadata), **Versioned** (SemVer-enforced `version` field + a real
`CompatibilityChecker`), **Contract First** (`schemas/`/`contracts/` exist before any
consumer), **Capability Driven** (`CapabilityNode`/`CapabilityReferenceExpression`
reference a `@aos/registry` Capability id by string — never a concrete Tool), **Event
Driven** (every Registry mutation publishes onto the real `@aos/event-bus`).

## 2. Schema Diagram

```
WorkflowDefinition (schemas/workflow-definition.ts)
├── id: string (^[a-z][a-z0-9_.-]*$)
├── version: string (SemVer x.y.z)
├── namespace?, displayName?, description?
├── labels?, tags?, tenantScope (GLOBAL|TENANT), tenantId?
├── metadata?: WorkflowMetadata (free-form record)
├── variables?: VariableDeclaration[]
├── input?, output?: Record<string,string>
├── nodes: Node[] (min 1)               ─┐
├── transitions?: Transition[]           ├─ see §3/§4
├── errorHandling?, compensation?        │
├── retry?, timeout?                     │
├── events?: string[], permissions?: string[]
```

`VariableDeclaration`: `name` (identifier regex), `type` (STRING|NUMBER|BOOLEAN|OBJECT|
ARRAY|ANY), `scope` (WORKFLOW|NODE|GLOBAL|TEMPORARY|ENVIRONMENT), `required`, `defaultValue?`,
`description?`.

## 3. Node Hierarchy

```
baseNodeSchema (id, name, description?, input?, output?, variables?, retry?, timeout?,
                compensation?, metadata?)
  ├── StartNode                 (no extra fields)
  ├── EndNode                   (no extra fields)
  ├── TaskNode                  taskRef?
  ├── CapabilityNode            capability, capabilityVersion?
  ├── ConditionNode             condition: Expression
  ├── DecisionNode               branches: {condition, transitionId}[] (min 1), defaultTransitionId?
  ├── ParallelNode               branchNodeIds: string[] (min 2)
  ├── MergeNode                  joinNodeIds: string[] (min 2), waitForAll (default true)
  ├── LoopNode                   loopCondition: Expression, bodyNodeId, maxIterations?
  ├── DelayNode                  durationMs: positive number
  ├── WaitNode                   waitCondition?: Expression
  ├── HumanNode                  assigneeRole?, formRef?
  └── SubWorkflowNode            subWorkflowId, subWorkflowVersion?
```

`nodeSchema` is a 13-way `z.discriminatedUnion("type", [...])`. Future Node Types (Event,
AI, Script) are explicitly **not** implemented — the extension point is `SchemaRegistry`
(`registry/schema-registry.ts`), which a future custom type would register into without a
core package change.

## 4. Transition Diagram

```
Transition
├── id, kind (NEXT|CONDITION|PARALLEL|MERGE|LOOP|RETRY|FAILURE|TIMEOUT|COMPENSATION)
├── fromNodeId, toNodeId
├── condition?: Expression   (required by TransitionValidator when kind = CONDITION)
├── priority?, description?
```

`TransitionValidator` resolves `fromNodeId`/`toNodeId` against the Node set; `CycleValidator`
builds a directed graph from every Transition edge plus `LoopNode.bodyNodeId` edges and runs
DFS cycle detection — a cycle that passes through a `LOOP`-type Node is the intentional Loop
construct (allowed); any other cycle is an "Unintended cycle" and rejected.

## 5. Variable Model

Five scopes: **Workflow** (`WorkflowDefinition.variables`), **Node** (`Node.variables`),
**Global**/**Temporary**/**Environment** (declarable in either location via `VariableScope`).
`VariableValidator` walks every Expression reachable from Node conditions/branches/loop/wait
and Transition conditions (`validator/expression-walker.ts`'s `collectExpressions` +
`walkExpression`) and confirms every `VariableReferenceExpression.variableName` resolves
against a declared Workflow- or Node-level variable.

## 6. Versioning Strategy

- `version` is SemVer-enforced at the schema layer (`^\d+\.\d+\.\d+$`) and again
  semantically by `VersionValidator` (`semver.valid()`, rejects `"0.0.0"`).
- `WorkflowDefinitionRegistry` composes an internal `VersionRegistry` (sorted SemVer list
  per Workflow id) — `get(id)` with no version resolves to the latest.
- `CompatibilityChecker.check(previous, next)` runs a real structural diff: same `id`,
  `next.version` strictly `semver.gt` `previous.version`, no removed `input` field, no
  removed Node id. Returns `{ compatible, breakingChanges[] }` — informational, never
  blocks registration.
- `IWorkflowMigration` (`versioning/i-workflow-migration.ts`) is an **interface only**, per
  the prompt — no migration execution engine exists in this package.

## 7. Validation Flow

`ValidationPipeline` (`validator/validation-pipeline.ts`) runs eight independent
`IWorkflowValidator`s in a fixed order, **aggregating every issue rather than
short-circuiting**:

```
Structural → Transition → Duplicate → Cycle → Variable → Expression → Version → Permission
```

- **Structural**: exactly 1 Start node, ≥1 End node, every Parallel/Merge/Loop/Compensation
  node-id reference resolves.
- **Transition**: `fromNodeId`/`toNodeId` resolve; CONDITION-kind transitions require a
  `condition`.
- **Duplicate**: duplicate Node ids, Transition ids, Variable names within the same scope.
- **Cycle**: DFS cycle detection distinguishing intentional Loop cycles from unintended
  ones (see §4).
- **Variable**: every `VariableReferenceExpression` resolves to a declaration (see §5).
- **Expression**: semantic checks Zod's shape validation cannot express — e.g. a `"between"`
  Date Expression requires `rangeEnd`; a `"not"` Boolean Expression requires exactly 1
  operand.
- **Version**: SemVer validity (see §6).
- **Permission**: every `permissions` entry matches `resource.action` shape.

`ValidationBuilder` (`builder/validation-builder.ts`) is the fluent wrapper for supplying
extra, caller-defined `IWorkflowValidator`s alongside the eight built-in stages.

## 8. Import/Export Flow

```
YAML text ──YamlWorkflowDefinitionParser──▶ WorkflowDefinition ──YamlWorkflowDefinitionSerializer──▶ YAML text
JSON text ──JsonWorkflowDefinitionParser──▶ WorkflowDefinition ──JsonWorkflowDefinitionSerializer──▶ JSON text
```

Both parsers validate the parsed object against `workflowDefinitionSchema` and throw
`ParseException` on syntax error or schema failure (message includes the field path, or
`"(root)"` when the top-level value itself doesn't match). Both serializers round-trip
losslessly against the schema (verified by dedicated round-trip tests) and throw
`SerializationException` if the underlying library cannot represent a value (e.g. a
function embedded in free-form metadata). A **BPMN Import Adapter** is explicitly listed as
Future in the source prompt and is **not implemented**.

## 9. Builder API Diagram

```
WorkflowBuilder.create(id, version)
  .withDisplayName() .withDescription() .withNamespace() .withLabels() .withTags()
  .withTenantScope() .withMetadata() .withInput() .withOutput()
  .addVariable(VariableBuilder.create(name, type, scope).required().withDefault().build())
  .addNode(NodeBuilder.create(id, type).withName()...set("capability", "...").build())
  .addTransition(TransitionBuilder.create(id, kind, from, to).withCondition().build())
  .withErrorHandling() .withCompensation() .withRetry() .withTimeout()
  .withEvents() .withPermissions()
  .build()  ──▶ validates against workflowDefinitionSchema, throws BuilderException
```

`NodeBuilder` is deliberately one generic class (not 13 per-Node-Type subclasses): shared
base fields get named `.with*()` setters, and each Node Type's own fields (e.g.
`CapabilityNode.capability`, `LoopNode.bodyNodeId`) go through a generic `.set(field,
value)` escape hatch, with `.build()` deferring correctness entirely to
`nodeSchema.safeParse()`. This trades per-type static typing for avoiding 13 near-identical
classes — documented as a scope tradeoff in the file itself (see §10).

## 10. Technical Debt

- **`NodeBuilder.set()` is untyped at the call site.** Setting a Node-Type-specific field
  (e.g. `capability`) goes through `set(field: string, value: unknown)` rather than a
  per-type typed setter — mistakes surface at `.build()` (a `BuilderException`), not at
  compile time. A future iteration could generate 13 typed builder subclasses if call-site
  type safety becomes a real pain point.
- **`WorkflowDefinitionRegistry` is in-memory only** (`Map`-backed) — no persistence
  adapter exists yet; a PostgreSQL/Redis-backed `IWorkflowDefinitionRegistry`
  implementation is future work behind the existing interface (mirrors `@aos/scheduler`'s
  `InMemoryScheduleStore` precedent).
- **`ISignatureProvider` (contracts/i-signature-provider.ts) has zero implementations** —
  it's an interface-only Security placeholder per the prompt; no Workflow Definition is
  actually signed or verified anywhere in this package.
- **`Expression` recursive Zod schema required a non-obvious workaround** (documented in
  `expressions/expression.ts`'s own comments): the type must be declared as explicit plain
  interfaces (not `z.infer`), and every composite schema must stay a bare `z.object(...)`
  with `z.lazy()` used only on the individual recursive fields — wrapping a whole composite
  schema in `z.lazy()`/`ZodType<X>` breaks `z.discriminatedUnion`'s requirement that every
  member be a literal `ZodObject`. Any future AOS package needing a recursive Zod schema
  should follow this exact pattern.

## 11. Known Limitations

- No Workflow Runtime, Executor, Agent Runtime, Tool Runtime, Planner, Reasoner,
  Reflection, Simulation Runtime, Memory Engine, or AI Gateway exists in this package — by
  design, per the prompt's explicit boundary.
- `Expression` (`expressions/`) defines shape only — no evaluator exists; a
  `ComparisonExpression`'s `operator` (`eq`/`neq`/`gt`/...) is validated as a valid string
  literal but never actually compared against anything.
- Event, AI, and Script Node Types, and a BPMN Import Adapter, are unimplemented Future
  items per the source prompt.
- `IWorkflowMigration` has no concrete implementation — no data migration between
  incompatible Workflow versions is possible yet; `CompatibilityChecker` only _detects_
  breaking changes, it does not resolve them.
- `WorkflowDefinitionSystem` (the `IModule` implementation) is not wired into any real
  Kernel `buildKernel({ modules: [...] })` call in this Engineering Task — it is
  readiness-only, matching the precedent set by `@aos/scheduler`'s `SchedulerSystem` and
  `@aos/event-bus`'s `EventBusSystem`.
