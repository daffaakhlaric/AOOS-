## Architecture

```
KnowledgeMarketplace (marketplace/) — the public façade, composition root
  owns StateMachine + Pipeline + Middleware + Manager + Resolver + Factory
        │
        ▼
KnowledgeMarketplacePipeline (pipeline/) — 9 fixed stages
  Validation → Metadata Resolution → Dependency Resolution → Compatibility Resolution →
  Category Resolution → Metrics → Lifecycle → Audit → Logging
        │
        ▼
KnowledgeMarketplaceStateMachine — the only code allowed to mutate MarketplaceListing.state
        │
        ▼
KnowledgeMarketplaceResolver — resolve Marketplace/Publisher/Category/Compatibility/
                               Dependency/Listing
        │
        ▼
KnowledgeMarketplaceRegistry (8 generic buckets) + KnowledgeMarketplaceManager
                                                    (token-keyed ledger)
        │
        ▼
KnowledgeMarketplaceMiddleware — marketplace.use() extensibility, separate from the
                                  Pipeline
        │
        ▼
contracts/ — 10 interface-only extension points + 3 future-readiness contracts,
             zero implementations
```

`KnowledgeMarketplace` is the single façade named in the prompt's Public API list. To
avoid a same-name collision at the package barrel, the read-only per-listing domain view
returned by every operation is exported as `KnowledgeMarketplaceRecord` instead —
mirroring the `KnowledgePolicy`/`KnowledgePolicyRecord` split established by
`@aos/knowledge-policy`. `KnowledgeMarketplaceManager` is a distinct, mid-level class —
composing `registry` + `session` + `statistics` + a private token-keyed execution
ledger — mirroring `@aos/knowledge-policy`'s `KnowledgePolicy`/`KnowledgePolicyManager`
split and `@aos/knowledge-versioning`'s equivalent pattern before it.

## Domain Model

`MarketplacePackage`, `MarketplaceListing`, `MarketplacePublisher`, `MarketplaceCategory`,
`MarketplaceTag`, `MarketplaceCertification`, `MarketplaceCompatibility`,
`MarketplaceDependency`, `MarketplaceVersion`, `MarketplaceStatistics`,
`MarketplaceMetadata`, `MarketplaceInstallationMetadata`, `MarketplaceAudit` — the exact 13
aggregates named by the prompt, each backed by a Zod schema (`domain/marketplace-*.ts`).

**Package-vs-Listing modeling (judgment call):** `MarketplacePackage` is the underlying
software/knowledge unit — registered once via `createListing()`'s `packageName`/
`currentVersion`/`packageDescription` inputs, keyed by `packageId` in the `PACKAGE`
Registry bucket. `MarketplaceListing` is its marketplace-facing presentation — carries the
externally addressable `KnowledgeMarketplaceToken`, the `MarketplacePackageStatus`
lifecycle state, and references the Package by `packageId`. This mirrors the prompt's own
separation of "Package Registry" and "Listing Registry" as two distinct buckets, and keeps
`MarketplaceMetadata`/`MarketplacePackage` synchronized on `marketplaceType`/`category`
(cross-checked every Pipeline run by the Integrity validator stage).

## Marketplace Structure

`MarketplaceType` (4 values: Official, Certified Partner, Community, Private
Organization) classifies both the `MarketplacePublisher` and the `MarketplacePackage`.
`MarketplacePackageStatus` (9 values) drives the Listing lifecycle. Every Listing
references exactly one Package, one Publisher, and one Category, and may accumulate
0..n Dependencies, at most 1 Compatibility record (an "Add Compatibility" call replaces
the prior one — a caller-visible upsert, not a growing collection), and at most 1
Certification record (created once, by the Certify operation).

## Categories

16 built-in category names, per the prompt: General, Marketing, Sales, HR, Finance,
Customer Service, Property, Healthcare, Education, Manufacturing, Automotive, Banking,
Insurance, Government, Software Engineering, Custom (`MarketplaceCategoryName`).
`BUILT_IN_CATEGORY_DEFINITIONS` (15 entries, `Custom` deliberately excluded) is a
metadata-only catalog array, mirroring `BUILT_IN_PROVIDER_DEFINITIONS` in
`@aos/knowledge-provider`. `isBuiltInCategory()` distinguishes the 15 always-resolvable
values from `Custom`, which requires an explicit `marketplace.registerCategory()` call
(registered into the `CATEGORY` Registry bucket) before any Listing may declare it — the
Category Resolver (`resolveCategory()`) and Pipeline stage 5 (Category Resolution) both
enforce this.

## Package Metadata

`MarketplacePackage` carries `packageId`, `name`, `publisherId`, `marketplaceType`,
`category`, `currentVersion`, and an optional `description`. The Version validator stage
requires `currentVersion` to look like a semantic version (`\d+\.\d+\.\d+…`).

## Compatibility Metadata

The exact 6 fields named by the prompt: AOS Version, Required Packages, Optional
Packages, Required Knowledge Version, Runtime Compatibility, Platform Compatibility
(`MarketplaceCompatibility`). "No installation logic" is honored literally: the Pipeline's
Compatibility Resolution stage (stage 4) performs a metadata comparison only — it reads
`context.metadata.platform`/`context.metadata.runtime` (arbitrary caller-supplied strings)
and rejects the operation (`MarketplaceCompatibilityException`) only when the registered
Compatibility record declares a non-empty allow-list that excludes the supplied value.

## Dependency Metadata

The exact 4 kinds named by the prompt: Required, Optional, Recommended, Conflicting
(`MarketplaceDependencyKind`). "Metadata only — no version-solving algorithm" is honored:
the Dependency validator stage checks for self-dependency and (when supplied) that the
target Package id is known; the Pipeline's Dependency Resolution stage (stage 3)
independently confirms each dependency is registered in the `DEPENDENCY` Registry bucket
by its own id — a presence check, not a solver.

## Lifecycle

9 states, in the prompt's own order: Draft, Submitted, Reviewing, Certified, Published,
Deprecated, Suspended, Archived, Removed. Only `Removed` is hard-terminal. The transition
table — not specified edge-by-edge in the prompt — was designed as: `Draft -> Submitted ->
Reviewing -> Certified -> Published` is the mainline publishing path; `Submitted`/
`Reviewing` may fall back to `Draft` on rejection; `Published` fans out to
`Deprecated`/`Suspended`/`Archived`; `Suspended` can re-`Publish` or `Archive`;
`Deprecated` can `Archive`; every non-terminal state has a direct edge to `Removed`. A
dedicated, independently-authored full 9×9 legality-matrix test
(`test/state-machine/state-machine.spec.ts`, 81 parameterized cases) locks these exact
edges against accidental future drift. `KnowledgeMarketplaceLifecycle` is a read-only,
query-only companion to the imperative `KnowledgeMarketplaceStateMachine`, which is the
only code in this package allowed to change `MarketplaceListing.state`, appending one
immutable history entry per legal transition and stamping `publishedAt`/`removedAt` on the
corresponding transitions.

## Registry

One generic `KnowledgeMarketplaceRegistry` class covers the exact 8 required buckets —
Package, Listing, Publisher, Category, Certification, Compatibility, Dependency,
Statistics — as a `Map<Bucket, Map<string, Identified>>`. Never scanned: every read is a
direct Map lookup by id through `KnowledgeMarketplaceResolver`; `list()`/`count()` exist
only for Metrics/Health/Search/Browse sampling. A bucket-isolation matrix test
(`test/registry/registry.spec.ts`) confirms all 8 buckets are independent. `Package`/
`Publisher` records are registered with their generic `id` field set equal to their
domain id (`packageId`/`publisherId`) rather than a separately generated UUID, so
`resolveMarketplace(packageId)`/`resolvePublisher(publisherId)` are direct Map lookups —
this was a bug found and fixed during test-writing (the factory originally generated a
random `id` distinct from `packageId`, silently breaking every resolver lookup).

## Resolver

`KnowledgeMarketplaceResolver` implements the exact 6 dimensions named by the prompt —
Marketplace (`MarketplacePackage`), Publisher, Category, Compatibility, Dependency,
Listing — as 6 method pairs on one class (`resolveX()`/`tryResolveX()`), matching how
`@aos/knowledge-policy`'s `KnowledgePolicyResolver` organizes its 5 resolvers.
`searchListings()`/`browseCategory()` are additional read-only query helpers on the same
class, sampling `registry.list(LISTING)` (Metrics/Health-style sampling, not a keyed
lookup) to back the "Search Metadata"/"Browse Category" Marketplace Operations. The
façade keeps each Listing's `LISTING` bucket entry synchronized with its live metadata on
every Pipeline run (a second bug found and fixed during test-writing: the entry was
originally frozen at `createListing()` time, so `updateListing()`/`updateMetadata()`
changes never became searchable).

## Validation

A strict 10-stage validator, in the prompt's own order: Identity, Metadata, Category,
Publisher, Dependency, Compatibility, Version, Certification, Configuration, Integrity.
Every stage runs and its issues are aggregated — no short-circuiting within the Validator
(verified directly by a test that supplies two independently-failing fields and asserts
both issues surface). The Certification stage enforces "a Listing must be Certified
before it can be Published" as a real business rule; the Integrity stage cross-checks the
Listing's metadata against its underlying Package's `packageId`/`marketplaceType`/
`category` — this is what makes `updateMetadata({ category })` also update the underlying
Package's `category` (see "Pipeline" and "Non-obvious design/judgment calls" below).

## Pipeline

Exactly 9 fixed stages, per the prompt:

1. **Validation** — the real 10-stage `KnowledgeMarketplaceValidator`, fed live-derived
   facts (resolved Publisher, category-resolvability, known Package ids) from the
   Registry → throws `MarketplaceValidationException` and records a failed
   Validation-Count sample.
2. **Metadata Resolution** — normalizes/refreshes `MarketplaceMetadata.updatedAt`.
3. **Dependency Resolution** — confirms every declared `MarketplaceDependency` is
   registered in the `DEPENDENCY` Registry bucket by its own id (real, independent check —
   distinct from Validation's target-Package-known check).
4. **Compatibility Resolution** — a real metadata comparison of the registered
   Compatibility record's platform/runtime allow-lists against caller-supplied context.
5. **Category Resolution** — a real resolve/validate of the declared Category against the
   Category Registry bucket (throws `MarketplaceCategoryException` for an unregistered
   `Custom` category).
6. **Metrics** — records a Package-Count sample.
7. **Lifecycle** — drives the State Machine to `targetState` (skipped when no
   `targetState` is supplied, or when it already equals the current state).
8. **Audit** — appends a `MarketplaceAuditEntry` (fromState/toState/reason).
9. **Logging** — appends a `MarketplaceLogEntry`.

Tracing (stamping a `MarketplaceTrace` with an incrementing `runCount`) also runs
whenever `context.correlationId` is present — every context this package constructs
always has one. Unlike `@aos/knowledge-policy`'s 3 structurally-present-but-no-op
Resolution stages, every one of this Pipeline's 4 Resolution stages (2–5) performs real,
independently testable work, per the prompt's explicit instruction for this phase ("Real,
substantive work per stage (no stubs)").

## Metrics

The exact 9 fields named by the prompt: Package Count, Published Count, Certified Count,
Category Count, Dependency Count, Compatibility Count, Publisher Count, Search Count,
Browse Count — plus internal `validationCount`/`validationFailureCount` used only to
derive domain Health, never exposed as a 10th "named" metric.

## Monitoring

`KnowledgeMarketplaceMonitoring.sample()` — exact name `KnowledgeMarketplaceMonitoring`,
per the prompt's Public API list — combines a Metrics snapshot and a Health report into
one `KnowledgeMarketplaceDashboard`, deriving domain health from the
`validationCount`/`validationFailureCount` ratio (healthy at 0% failures, warning below
10%, degraded below 50%, unavailable at or above 50%, unknown with zero samples).

## Statistics

`KnowledgeMarketplaceStatistics` maintains its own private
`Map<MarketplaceCategoryName, MarketplaceStatisticsSnapshot>` (listedCount/publishedCount/
lastActivityAt) — separate from the Registry's `STATISTICS` bucket, which exists for
callers registering their own externally computed statistics providers. The façade's
`statistics` field is the **same instance** as `KnowledgeMarketplaceManager.statistics`
(not a second, independently constructed one) — see "Non-obvious design/judgment calls".

## Non-obvious design/judgment calls made this phase

1. **Dependency mapping.** The prompt's "Allowed Dependencies" list names
   `@aos/kernel`/`@aos/shared`/`@aos/events`/`@aos/knowledge-engine`/
   `@aos/knowledge-versioning`/`@aos/knowledge-policy`. Every prior Knowledge package maps
   the Core 3 to the real workspace package names (`@aos/runtime-kernel`, `@aos/common`,
   `@aos/event-bus`), and none of them actually add the sibling Knowledge packages as
   `package.json` dependencies unless they import a concrete class from them — this
   package follows that precedent exactly: `package.json` depends on `@aos/common`,
   `@aos/errors`, `@aos/event-bus`, `@aos/runtime-kernel`, and `zod` only. No import from
   `@aos/knowledge-engine`/`@aos/knowledge-versioning`/`@aos/knowledge-policy` exists
   anywhere in `src/` — "Read contracts only. Never instantiate another runtime" is
   honored by having nothing to read yet.
2. **Event-name mapping.** The prompt lists event names without dotted namespaces
   (`MarketplaceCreated`, `ListingCreated`, …). Mapped to
   `knowledge.marketplace.created` and `knowledge.marketplace.listing.{created,updated,
submitted,reviewed,certified,published,deprecated,suspended,archived,removed}`,
   matching the `knowledge.<domain>.<entity>.<verb>` convention every sibling package
   uses.
3. **Package-vs-Listing modeling.** See "Domain Model" above — Package is the
   underlying unit (created once per `createListing()` call from `packageName`/
   `currentVersion`/`packageDescription` inputs, since the prompt's 16 Operations list has
   no separate "Create Package" operation), Listing is the marketplace presentation.
4. **Resolver shape.** One `KnowledgeMarketplaceResolver` class with 6 named
   resolve-dimension method pairs, matching `@aos/knowledge-policy`'s
   `KnowledgePolicyResolver` organization of its 5 resolvers, rather than 6 separate
   exported classes (the prompt names 6 "resolvers" as a capability list, not 6 required
   class names — only `KnowledgeMarketplaceResolver` appears in the Public API list).
5. **Category catalog design.** `BUILT_IN_CATEGORY_DEFINITIONS` mirrors
   `BUILT_IN_PROVIDER_DEFINITIONS` from `@aos/knowledge-provider`: a plain metadata array
   of `{ name, label, description }`, with `Custom` deliberately excluded from the
   always-resolvable set and requiring an explicit `registerCategory()` registration.
6. **Future Readiness interpretation.** "Prepare contracts ONLY... No implementation" for
   005.7K/005.7L/005.7M was satisfied with exactly 3 new interface files
   (`contracts/i-knowledge-generator-ai-marketplace.ts`,
   `i-knowledge-quality-engine-marketplace.ts`,
   `i-knowledge-validator-ai-marketplace.ts`), each a single-method interface named after
   its target phase, wired as optional fields on `KnowledgeMarketplaceConfig` — no
   speculative stub modules or folders were added.
7. **Token prefix chosen.** `kmkt_` (Knowledge MarKeT) — checked against every existing
   prefix in the workspace (`ptok_`, `stok_`, `ksrc_`, `kver_`, `kpol_`) before selecting
   it; collision-free.
8. **Marketplace Operations not in the named 16 but required as plumbing.**
   `registerPublisher()`/`registerCategory()` are not named as one of the 16 "Marketplace
   Operations" (Create Listing … Browse Category), but a Listing cannot legally reference
   a Publisher or a `Custom` Category that was never registered — these two setup methods
   exist on the façade, are fully tested, but are documented here as outside the 16-op
   count rather than silently smuggled in as a 17th/18th operation.
9. **`review()` semantics.** The FSM only allows `Submitted -> Reviewing` as a single
   transition; `Reviewing -> Draft` (rejection) exists as a legal edge but is not driven
   automatically by `review({ approved: false })` — the decision is recorded in the audit
   `reason` string and published on the `ListingReviewed` event payload
   (`{ approved, reviewedBy }`), and a caller models an actual rejection as a second,
   explicit operation. This keeps every one of the 16 Marketplace Operations as exactly
   one Pipeline call driving at most one FSM transition, matching the "one atomic Pipeline
   call per operation" contract established by `@aos/knowledge-policy`/
   `@aos/knowledge-versioning`.
10. **Statistics sharing.** The façade's `statistics` field is set to
    `this.manager.statistics` rather than a freshly constructed
    `KnowledgeMarketplaceStatistics` — found as a real bug during test-writing (see
    "Technical Debt") where `listedCount` and `publishedCount` were silently landing in
    two different, never-reconciled instances.
11. **Registry bucket keying for Package/Publisher.** `MarketplaceFactory.create()`/
    `PublisherFactory.create()` set the generic `id` field equal to `packageId`/
    `publisherId` (not a separately generated UUID) specifically so
    `KnowledgeMarketplaceRegistry`'s single `id`-keyed Map per bucket can serve as the
    Package/Publisher lookup key without a second indirection table — also found and
    fixed as a real bug during test-writing.
12. **Compatibility "Add" is an upsert, not an append.** `addCompatibility()` always
    `registry.replace()`s the `COMPATIBILITY` bucket entry keyed by `listingId` (not a
    generated id) — a Listing has at most one live Compatibility record; calling the
    operation twice replaces rather than accumulates, matching how a real marketplace
    listing has one current compatibility statement, not a history of them (version
    history is a separate concern, modeled by `MarketplaceVersion`, not implemented as an
    Operation in this phase since "Version Metadata" wasn't in the 16-operation list).
