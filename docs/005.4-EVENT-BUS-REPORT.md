# 005.4 — Enterprise Event Bus: Closing Report

Source prompt: `docs/PROMPT-005.4-ENTERPRISE-EVENT-BUS.md`. New package: `packages/event-bus`
(`@aos/event-bus`). This is the core, in-process Event Contract / Dispatcher / Publisher /
Subscriber infrastructure the rest of AOS's Runtime is meant to communicate through — not a
simple `EventEmitter`, not a naive Pub/Sub.

## 1. Architecture

```
                 ┌───────────────────────── EventBroker ─────────────────────────┐
                 │                                                                │
publish()  ──▶   │  EventPublisher                                               │
publishAsync() ─▶│    ├─ buildEvent()      fills Event ID/Correlation ID/        │
publishBatch() ─▶│    │                    Timestamp/Priority (PriorityResolver) │
                 │    └─ ValidationPipeline (Schema → Version → Payload → Tenant) │
                 │           │ valid                        │ invalid            │
                 │           ▼                               └─▶ reject + metrics│
                 │  EventDispatcher                                              │
                 │    ├─ SubscriptionManager.match(event)                        │
                 │    │     (EventRouter: Namespace/Topic/Pattern/Tenant/        │
                 │    │      Category/Priority + per-subscription FilterChain)   │
                 │    └─ for each match: RetryExecutor(handler, RetryPolicy)     │
                 │           │ delivered                    │ exhausted          │
                 │           ▼                               ▼                   │
                 │      metrics.recordDelivered()      metrics.recordDropped()   │
                 │      EVENT_DELIVERED                 EVENT_DROPPED            │
                 │                                       IDeadLetterQueue?.enqueue│
                 │                                                                │
                 │  EventBusMetricsCollector · EventBusHealth · BusMonitor       │
                 │  EventBusEventEmitter (internal bus notifications)            │
                 └────────────────────────────────────────────────────────────────┘
```

`EventBroker` is the composition root, mirroring `RegistrySystem` (`@aos/registry`) and
`Kernel` (`@aos/runtime-kernel`). `EventBusSystem` (`bootstrap/`) wraps it as a Kernel
`IModule`, not yet wired into any actual Kernel bootstrap call (no application does that in
this Engineering Task).

## 2. Event Flow

1. Producer calls `broker.publish(input)` with the business fields (`type`, `category`,
   `payload`, `source`, `producer`, optional `tenantId`/`priority`/...).
2. `EventPublisher.buildEvent()` fills every generated field: `eventId` (UUID),
   `correlationId` (generated if absent), `timestamp` (now), `priority` (caller value, or
   `PriorityResolver.resolve(namespace)` — e.g. `system.*` defaults to Critical,
   `analytics.*` to Low), `version`/`schemaVersion` (default `"1.0.0"`).
3. `ValidationPipeline` runs Schema → Version → Payload → Tenant, aggregating every issue
   (does not short-circuit). Any failure raises `ValidationException`, emits
   `EVENT_REJECTED`, and records the Rejected metric — dispatch never runs.
4. On success, `metrics.recordPublished()` + `EVENT_PUBLISHED` fire, then
   `EventDispatcher.dispatch(event, traceContext)` runs.
5. `SubscriptionManager.match(event)` applies Routing (criteria) then each subscription's
   own `FilterChain` (AND semantics) to find every matching subscriber.
6. Each match is delivered via `RetryExecutor` under its own `IRetryPolicy`. Success records
   Delivered + latency + `EVENT_DELIVERED`; a failed attempt before the last records Retried
   - `EVENT_RETRIED`; exhaustion records Dropped + `EVENT_DROPPED`, and — if an
     `IDeadLetterQueue` is configured — enqueues there + emits `DLQ_ENQUEUED`.
7. `publish()` resolves once every match has been attempted; `publishAsync()` resolves right
   after step 4 without waiting for step 5–6; `publishBatch()` validates the whole batch
   atomically first, then dispatches every event in Priority order (Critical → Background).

## 3. Event Lifecycle

```
  built ──▶ validating ──▶ [rejected]            (ValidationException, never dispatched)
              │
              ▼ valid
           published ──▶ routed ──▶ [no subscribers] (DispatchSummary.matchedSubscribers = 0)
              │              │
              │              ▼ matched
              │           delivering (per subscriber, under its own RetryPolicy)
              │              │
              │      ┌───────┴────────┐
              │      ▼                ▼
              │   delivered        retrying ──▶ [exhausted] ──▶ dropped ──▶ (DLQ, if configured)
              │      │
              └──────┴─────────────────────────────────────────────────────▶ done
```

Every transition is observable via `EventBusEventEmitter` (`event_bus.*` internal
notifications) and `EventBusMetricsCollector`.

## 4. Dispatcher Diagram

```
EventDispatcher.dispatch(event, traceContext?)
  │
  ├─ matched = subscriptionManager.match(event)
  │
  └─ for each `subscription` in matched:
       span = tracer?.startSpan("deliver:<type>", childSpan(traceContext), {subscriberId})
       RetryExecutor({ policy: subscription.retryPolicy, onAttemptFailed }).execute(
         () => subscription.handler(event)
       )
         │ success                         │ RetryExhaustedException
         ▼                                 ▼
       metrics.recordDelivered(latency)   metrics.recordDropped()
       events.emit(EVENT_DELIVERED)        events.emit(EVENT_DROPPED)
       span?.end({ delivered: true })      deadLetterQueue?.enqueue(...) → DLQ_ENQUEUED
                                            span?.end({ delivered: false, error })
  → DispatchSummary { eventId, matchedSubscribers, delivered, dropped, results[] }
```

## 5. Routing Diagram

```
RouteCriteria = { namespace?, topic?, pattern?, tenantId?, category?, priority? }
  (every present field is AND-ed; an absent field is a wildcard for that dimension)

EventRouter.matches(event, criteria):
  namespace  → extractEventNamespace(event.type) === criteria.namespace
  topic      → event.type === criteria.topic                 (exact)
  pattern    → compiledRegExp(criteria.pattern).test(event.type)
                 "*"  → one segment  ([^.]+)
                 "**" → any depth    (.*)
  tenantId   → event.tenantId === criteria.tenantId
  category   → event.category === criteria.category
  priority   → event.priority === criteria.priority

SubscriptionManager.match(event) = subscriptions
  .filter(s => router.matches(event, s.criteria))
  .filter(s => new FilterChain(s.filters).accepts(event))   // Tenant/Capability/Namespace/Type/Version
```

Compiled patterns are memoized (`PATTERN_CACHE`) since the same subscription pattern is
tested against every published event.

## 6. Retry Flow

```
RetryExecutor.execute(operation):
  for attempt in 1..policy.maxAttempts:
    try:
      result = await operation()
      return { result, metadata: { attempt, maxAttempts } }
    catch (error):
      onAttemptFailed?.({ attempt, maxAttempts, lastError })
      if attempt < maxAttempts:
        await sleep(policy.nextDelayMs(attempt))
  throw RetryExhaustedException(...)
```

`ExponentialBackoffPolicy(maxAttempts, baseDelayMs, maxDelayMs)`:
`delay(attempt) = min(baseDelayMs · 2^(attempt-1), maxDelayMs)`.

`LinearBackoffPolicy(maxAttempts, incrementMs, maxDelayMs)`:
`delay(attempt) = min(incrementMs · attempt, maxDelayMs)`.

`sleep` is injectable (`EventBrokerOptions.sleep`) so tests never wait on real timers — every
Retry Test in this package runs with a no-op sleep.

## 7. DLQ Flow

```
delivery exhausted (RetryExhaustedException)
  │
  ▼
metrics.recordDropped() + events.emit(EVENT_DROPPED, { eventId, reason })
  │
  ▼
IDeadLetterQueue configured? ──no──▶ dropped, nothing further happens
  │ yes
  ▼
deadLetterQueue.enqueue({ event, reason, retryMetadata?, failedAt })
  │
  ▼
events.emit(DLQ_ENQUEUED, { eventId, reason })
```

`IDeadLetterQueue` (`dead-letter/i-dead-letter-queue.ts`) is an **interface only** — no
persistence ships in this package, per the source prompt. `EventDispatcher` accepts one
optionally; without one, exhausted deliveries are simply dropped (observable via metrics and
`EVENT_DROPPED`).

## 8. Replay Flow

Two ports exist, neither implemented (interface only, no storage backs either):

- `IEventReplay` (`replay/i-event-replay.ts`) — application-facing: "replay everything
  matching this `ReplayQuery` (correlationId/tenantId/type/time range)."
- `IEventReplayProvider` (`store-interface/i-event-replay-provider.ts`) — the lower-level,
  Event-Sourcing-store-facing primitive `IEventReplay` would be implemented on top of once a
  real `IEventStore` exists: "stream events out of the store for this exact `ReplayRange`."

Together with `IEventStore`, `IEventSnapshotStore`, and `IEventArchiveProvider`
(`store-interface/`), these are the Event Sourcing readiness interfaces requested in the
005.4 addendum — they let a future durable-storage package support replaying AI Agent
activity, auditing AI decisions, re-simulating scenarios, and re-training/re-evaluating
agent strategy from event history, without another Event Bus contract change.

## 9. Metrics

`EventBusMetricsCollector` (`metrics/event-bus-metrics-collector.ts`) tracks exactly the set
requested: Published, Delivered, Dropped, Retried, Rejected (counters), Latency (average ms
across delivered events), Queue Depth and Subscriber Count (latest-set gauges).
`EventBusHealth` derives Publisher/Dispatcher/Subscriber/Router/Broker health from this same
snapshot (rejection/drop ratio thresholds at 10%/50% for degraded/unhealthy; 0 subscribers
is degraded). `BusMonitor` combines a Metrics snapshot + a Health check into one sample —
the payload shape a `monitoring.*` event would carry if the Broker were wired to
periodically publish one onto itself (the publish call itself is intentionally not wired,
to avoid `monitoring/` depending on `publisher/`).

## 10. Technical Debt

- `EventBroker.publish()`/`publishBatch()` deliver to every subscriber **sequentially**
  (`for...of` + `await`), not concurrently — correct and simple, but a very high subscriber
  count on one event will serialize their latencies. A future revision could deliver
  independent subscribers concurrently (`Promise.allSettled`) once ordering guarantees are
  decided.
- `id@versionRange` style version-pinned cross-references (the convention
  `@aos/registry`'s `RegistryKindGraph` introduced in 005.3A) has no analogue here yet —
  nothing in this package checks that a `causationId` or `correlationId` chain is internally
  version-consistent. Not requested by 005.4; flagged for future consideration only if
  Event Sourcing replay needs it.
- `PriorityQueue`/`BatchQueue`/`MemoryBuffer` (`buffer/`) are fully implemented and tested,
  but `EventDispatcher` does not buffer before dispatching — it delivers synchronously per
  `publish()` call. `EventPublisher.publishBatch()` is the only current consumer (it sorts a
  batch by Priority before dispatching each event in turn). A future high-throughput
  Broker configuration could route through `PriorityQueue`/`MemoryBuffer` for true
  asynchronous, buffered dispatch — the building blocks exist and are unit-tested standalone
  for that purpose.

## 11. Known Limitations

- **Interface-only, by explicit instruction:** Delayed Publish, Scheduled Publish, Dead
  Letter Queue, Event Replay (both the application-facing and Event-Sourcing-store-facing
  ports), Event Store, Event Snapshot Store, Event Archive Provider, and Permission
  Validation. None has a database, timer, or Scheduler backing it in this package.
- **No OpenTelemetry dependency added.** `ITracer`/`ISpan` are shaped so a real
  `@opentelemetry/api` adapter can implement them without touching any Dispatcher/
  Publisher/Subscriber call site; `InMemoryTracer` is the only shipped implementation.
- **No MessagePack/Avro serializer.** `ISerializer` is the port; `JsonSerializer` is the
  only implementation, per the source prompt's explicit "Future: MessagePack, Avro."
- **Tenant Isolation is opt-in, not default-deny.** `TenantValidator`/`TenantFilter` only
  reject a tenant-scoped event when the caller supplies an `allowedTenantIds` set; with none
  configured, every tenant is accepted. This matches "Security: Tenant Isolation" as a
  capability the Broker exposes, not a policy this package enforces unprompted.
- **No cross-service transport.** Every component (Subscription Manager, Buffer, Metrics)
  is in-process and in-memory — this is the same explicit scope boundary 005.3's Registry
  System had ("no persistence yet"), now applied to the Event Bus.
- **Not wired into `@aos/runtime-kernel`'s `Kernel`.** `EventBusSystem` implements `IModule`
  and is ready for `buildKernel({ modules: [eventBusSystem] })`, but no application code in
  this repository makes that call yet (same readiness-not-integration posture as
  `RegistrySystem`).

## 12. Checklist — ENGINEERING TASK 005.5 (Scheduler)

**Not implemented here, per explicit instruction ("Jangan membuat Scheduler").** What 005.5
can build on:

- ✅ `IScheduledPublisher` (`publisher/i-scheduled-publisher.ts`) — the exact interface a
  Scheduler-backed publish call should implement (`publishScheduled(input, cronExpression)`
  / `cancelScheduled(scheduleId)`).
- ✅ `IDelayedPublisher` (`publisher/i-delayed-publisher.ts`) — one-shot delayed publish,
  likely the Scheduler's simplest primitive to implement first.
- ✅ `scheduler.*` is already a formal Event Namespace (`contracts/event-namespace.ts`) — a
  Scheduler can publish `scheduler.triggered`/`scheduler.missed`/etc. without any Event Bus
  contract change.
- ✅ `EventPriority`/`PriorityResolver` are ready to assign a sensible default priority to
  scheduler-originated events.
- ✅ `RetryExecutor` + both Backoff Policies are directly reusable for retrying a failed
  scheduled job.
- ⬜ 005.5 will need its own persistence for schedule definitions (cron expressions, next-run
  timestamps) — nothing in `@aos/event-bus` provides that, matching this package's own "no
  persistence" boundary.
- ⬜ 005.5 should decide whether a missed/late trigger publishes a `scheduler.missed` Domain
  Event or a `system.*` Infrastructure Event — either fits the existing category schemas
  without modification.
